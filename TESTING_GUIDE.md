# Grasp — Pre-Launch Manual Testing Checklist

This is the full checklist for the "actually use it for real" step before going live on GitHub. It reflects everything built across all four implementation prompts (small UI fixes, `grasp set`/`reset`/`export`, the generation-reliability rework, and `grasp scan`) as of the current `main`.

The whole point of this step, per the original project brief, is simple: **if you turn Grasp off during real work, that's the strongest signal something's wrong with it.** So the single most important test isn't a checkbox at all — it's using Claude Code normally, in real repos, and noticing whether Grasp survives contact with real work. Everything below exists to help you notice specific things along the way, in plain terms, without needing to know how any of it works under the hood.

Work through this section by section. Where something depends on real Claude Code usage (not something you can force on demand), just keep it in mind during the week and check it off when it naturally happens.

---

## 0. One-time setup

- [ ] Check `node --version` is 22 or newer — Grasp (and its `better-sqlite3` dependency) won't install on an older Node.
- [ ] Install Grasp: `npm install`, `npm run build`, `npm link` from the project folder.
- [ ] Check `grasp --version` prints something, and `grasp --help` lists all the commands you'd expect (`init`, `review`, `scan`, `retry`, `set`, `reset`, `export`) — and does NOT list `debug:seed`/`debug:capture`/`debug:answer`/`internal:hook` (dev-only, hidden from help but still runnable by name). Run `grasp somebadcommand` too and confirm you get the same trimmed, public-only list, not an error dump.
- [ ] In a real repo you actually work in, run `grasp init`. Before it writes anything, it should show you a short summary of which hook(s) it's adding and explain — in plain language — that generating questions uses your existing Claude account (your subscription or your API billing, not some hidden third thing). **Read that message once for real.** Then say yes.
- [ ] Run `grasp init` again in a fresh repo (or delete the settings file first) and, at the "Apply these changes?" prompt, type `v` and press Enter instead of answering directly. Confirm it shows you the exact, literal JSON it's about to write (not a summary) — then confirm you can still answer `y`/`N` right after to actually apply or abort.
- [ ] Confirm it created a `.claude/settings.local.json` file with Grasp's entries in it, and that running `grasp init` again doesn't duplicate anything.
- [ ] **If you have an old `~/.grasp/history.db` from before this build** (i.e. from testing an earlier version of Grasp): run any Grasp command once and confirm it doesn't error out — the schema migration (new `source`, `scan_excerpt_*` columns on `events`, plus the new `scan_progress` table) should apply automatically and silently. Spot check with `sqlite3 ~/.grasp/history.db ".schema events"` — you should see the new columns, and old rows should read back fine via `grasp review`/`grasp export`.

## 1. Does it actually notice real work?

Just use Claude Code normally for a task. Afterward:

- [ ] Did a real, meaningful change (not a one-line tweak) get turned into a question? Check by running `grasp review`.
- [ ] Did a trivial change (fixing a typo, a one-line import fix) get correctly ignored — no question generated about it?
- [ ] Did an update to `package-lock.json` or similar generated files get correctly ignored?
- [ ] If you made a purely cosmetic change (reformatting, reindenting, no logic change — including a formatter just wrapping a `return`/assignment in parentheses to fit a line width), was it correctly ignored?
- [ ] If you have any generated files (anything headed with a "code generated by / do not edit" style comment — protobuf output, an ORM's generated types, etc.), regenerate one where only the body changes and the header stays the same. Confirm it's still correctly ignored (Grasp checks the file on disk for this, not just what's in the diff).
- [ ] If you delete an obsolete generated file, confirm that's ignored too, not treated as a meaningful change.
- [ ] **The core reliability fix — verify it directly:** give Claude Code a task that makes it edit several files in one turn (several tool calls close together, no interactive back-and-forth in between). Confirm you get ONE combined question afterward (`grasp review` shows one entry covering all the changed files), not one question per file/tool call, and not a timeout. Generation now happens at most once per turn, at `Stop`, not once per tool call — this is the actual bug this build fixed.
- [ ] Interrupt a session (close the terminal, kill Claude Code) right after it makes a real edit but before you'd expect a `Stop` firing. Start a new turn in the same session later (or just note if this happens naturally). Confirm the earlier edit's diff isn't lost — it should still turn into a question on a later `Stop` firing for that session, combined with whatever's new by then.

## 2. Are the questions actually good?

This is the most important, least mechanical thing to judge — nothing below is a pass/fail script, it's your own judgment call each time.

- [ ] Read each question you get. Does the first question actually teach you something general and useful (a concept), separate from your specific code?
- [ ] Does the second question clearly build on the first one — does knowing the answer to question 1 actually help you answer question 2?
- [ ] If you already clearly know a concept, does Grasp eventually stop re-asking you about it (across different projects too, not just the one you first learned it in, and across both `grasp review` and `grasp scan` — see §6c)? This might take a few repeats of the same concept to notice.
- [ ] Do you ever get a question about something that isn't really "AI-agent work" at all — like a question about Grasp's own settings file, or something unrelated to what Claude Code actually did?
- [ ] Try `grasp set mode --easy`, then `grasp set mode --hard`, then back to the default (`grasp reset config` or `grasp set mode --medium` if you added one). Over a few real diffs under each setting, does the concept it picks lean noticeably more foundational under `--easy` and more advanced under `--hard`, without ever forcing a question onto a diff that only really offers one reasonable concept either way?

## 3. Answering and skipping (`grasp review`)

- [ ] Run `grasp review` on a batch with more than one pending question. Before the first question appears, confirm you see a one-time banner summarizing how many questions are pending and how many sessions they span — it should not repeat on later questions.
- [ ] Run `grasp review` with exactly one pending question. Confirm the starting banner still reads sensibly for a batch of one (no "1 sessions" or other pluralization oddities).
- [ ] Run `grasp review`. Confirm it shows you the actual code change alongside the question, in a way you can read clearly.
- [ ] The moment a question appears, start typing immediately — no need to press Enter or any other key first. Confirm your keystrokes show up in the answer field right away.
- [ ] If a diff has a genuinely long line (a long condition, a long error message), confirm it wraps onto the next line instead of getting cut off — you should be able to read every character of it somewhere on screen.
- [ ] If a diff has more lines than fit on screen (look for the "N more lines below" hint), press the down arrow a few times and confirm the diff actually scrolls — try this both before typing anything and after you've already started typing an answer. Press up to scroll back. Confirm the hint row below the answer field only shows `[↑/↓] scroll diff` when there's actually more diff than fits on screen — on a short diff that fits entirely, that hint should be absent.
- [ ] Confirm the hint row also always shows `[Ctrl+C] quit anytime` — and that quitting mid-review really does leave any unanswered questions pending, nothing lost.
- [ ] Press Enter with the answer field still blank. Confirm you get a clear "a blank answer isn't accepted" message, not a silent no-op, and that this warning never appears before you've actually typed or attempted to submit anything — then just type a real answer and press Enter again; it should submit normally, with no extra keypress needed.
- [ ] Type a real answer and press Enter. Confirm you see a sample answer shown before it moves on to the next question — this is for your own comparison; it should never say anything like "correct"/"incorrect" or otherwise judge what you typed. Press any key to continue. Go check — did your own answer actually save? (`sqlite3 ~/.grasp/history.db "select answer_concept, answer_instance from events order by id desc limit 1;"`)
- [ ] Try to skip a question by doing nothing for a few seconds. Confirm nothing happens automatically — it should never disappear on its own.
- [ ] Now press Escape on purpose. Confirm it shows a short explanation of the concept, not an immediate skip. Confirm the hint row says `[Esc] stuck? see explanation` on this first attempt, and confirm the explain screen just says "Press any key to try again," with no "one more shot" framing.
- [ ] Press any key to continue past that explanation. Confirm you're back at the same question, able to type — this is your one retry. Confirm the hint row now says plain `[Esc] skip` for this retry attempt, since a second Escape here is the real, terminal decline. Type a real answer this time and confirm it's accepted normally (sample answer shown, same as any other real answer).
- [ ] On a different question, press Escape, continue past the explanation, then press Escape again instead of answering. Confirm this is what actually skips — two deliberate keypresses with a real explanation in between, not one accidental tap — and confirm you still see the sample answer for that question before it moves on, even though you didn't answer it.
- [ ] If you get a batch of several questions at once (e.g. after a long task), does working through them feel coherent — like one related batch — rather than a random jumbled list?
- [ ] If you use Grasp in more than one repo, run `grasp review` from inside just one of them. Confirm you only see that repo's own pending questions, not a mix from every repo Grasp has ever touched.
- [ ] Run `grasp review --all` instead. Confirm you now see pending questions from every repo.
- [ ] With no pending questions in your current repo but at least one pending somewhere else, run `grasp review`. Confirm it tells you plainly that nothing's pending *here* but some are pending elsewhere, and tells you to run `grasp review --all` — rather than just showing an empty "all caught up" screen.
- [ ] Resize the terminal mid-question. Confirm the TUI doesn't break or garble.

## 4. The "nudge" vs. the "hard stop"

Grasp defaults to a gentle reminder, not a hard block. Try both:

- [ ] Leave it on default settings. After Claude Code finishes a task with a real pending question, do you see a short message telling you a question is waiting?
- [ ] Turn on hard-gate mode: `grasp set gate hard` (repo-local) or `grasp set gate hard --global`. With a question still unanswered, try to get Claude Code to do more work in that same session. Confirm it actually refuses until you go answer or skip via `grasp review`.
- [ ] After answering/skipping, confirm Claude Code is immediately un-blocked again.
- [ ] Switch back with `grasp set gate soft` and confirm the blocking goes away.
- [ ] Confirm hard-gate only ever blocks based on *today's* unanswered questions from *that specific session* — an old question from a different day or different project shouldn't reach in and block unrelated work.

## 5. Cost and spend

- [ ] After a session where at least one question was generated, look for a spend total in the message Claude Code shows you: `"$0.0043 spent generating comprehension questions this session so far."`
- [ ] Confirm you're not shown a spend message on a quiet turn where nothing was generated — it should stay quiet rather than showing "$0.00" every time.
- [ ] Lower the question cap to something small (`grasp set questions-cap 2`) and confirm generation stops once you hit that many real questions in one sitting — and confirm the `Stop` message names the cap directly: `"You've hit this session's question cap (2) — start a new Claude Code session, or run \`grasp set questions-cap <n>\` to raise it."`
- [ ] Confirm there's no dollar-cost cap anymore — `questionsPerSessionCap` is the only generation limit. If you have an old config file with a `costCapUsd` key in it (from before this build), confirm Grasp rejects it with a specific, clear message telling you it was removed — not a generic "unknown key" error.

## 6. Ignoring stuff you don't want questions about

- [ ] Add a folder or filename to `"ignorePatterns"` in a repo's `.grasp.json` (e.g. a `scripts/` folder you don't care about). Touch a file there and confirm no question gets generated about it — and confirm the same file is also skipped by `grasp scan` (§6c), not just live diff capture.
- [ ] Confirm that ignore rule only applies in that one repo, not everywhere.

## 6a. `grasp set`, `grasp reset`, `grasp export`

- [ ] Run `grasp set mode --easy`, then check `.grasp.json` in that repo — confirm `difficultyMode` is set and any other keys already in that file are untouched.
- [ ] Run `grasp set gate hard --global`, then check `~/.grasp/config.json` — same untouched-other-keys check.
- [ ] Run `grasp set questions-cap 3` with a bad value (e.g. `0`, `-1`, `abc`) and confirm it's rejected with a clear usage message, not a silently-written bad config. Do the same for `grasp set scan-cap`.
- [ ] Run `grasp reset config` (no `--global`) in a repo with a `.grasp.json` — confirm the file is deleted, not left behind empty.
- [ ] Run `grasp reset config --global` — confirm `~/.grasp/config.json` is overwritten back to defaults, including `scanQuestionsCap`.
- [ ] Run `grasp reset history` with pending/answered questions in your history. Confirm it asks for `y/N` confirmation and shows the row counts about to be deleted (events, concept_tags, scan_progress, *and* scan_file_hashes); answer `N` and confirm nothing was deleted.
- [ ] Run `grasp reset history --yes`. Confirm it deletes without prompting, and reports how many rows were removed from `events`, `concept_tags`, `scan_progress`, and `scan_file_hashes` (check directly: `sqlite3 ~/.grasp/history.db "select count(*) from events; select count(*) from concept_tags; select count(*) from scan_progress; select count(*) from scan_file_hashes;"` should all be `0`).
- [ ] Run `grasp export`, `grasp export --anki`, and `grasp export --raw`. Confirm each prints the full path of a new CSV under `~/.grasp/exports/`, and that running the same command twice produces two different files (timestamped), not one overwritten file.
- [ ] Open each CSV in a spreadsheet app (or `python3 -c "import csv; print(list(csv.reader(open('<path>'))))"`). Confirm it parses cleanly — especially any row whose question/answer text has a comma, quote, or line break in it.
- [ ] Confirm `grasp export --anki`'s output message specifically mentions importing into Anki; confirm the default and `--raw` exports don't (just a location confirmation).
- [ ] After using `grasp scan` (see §6c), confirm its questions show up in `grasp export` too: a `source` column set to `scan` in the default/raw shapes, and a `source:scan` tag appended (not a new column) in the Anki shape.

## 6b. `grasp scan` — understanding existing code

`grasp scan` is a genuinely new feature, not a fix — it's a deliberate, discussed extension beyond the original brief (onboarding to existing code, not comprehension of AI-agent changes). Try it in a real repo you didn't just create with Claude Code:

- [ ] Run `grasp scan` (no Claude Code session running, nothing set up beyond `grasp init`/normal usage). Confirm it works fully standalone — no error about a missing session, no dependency on anything else running.
- [ ] Confirm the same review UI as `grasp review` appears: a concept question, then an instance question, sample answers afterward, Escape-for-a-hint-then-retry — all the same flow, including the `[Ctrl+C] quit anytime` hint. Confirm the instance question shows a short excerpt of the actual file it's about (with line numbers), and the concept question shows no code at all.
- [ ] Note that `grasp scan` generates its whole batch first, then presents it for you to answer through — it does not generate one question, wait for your answer, then generate the next. This was a deliberate build choice (logged in `DECISIONS.md`); nothing is lost or queued away, you just see the full batch at once rather than watching it grow one at a time.
- [ ] Answer or skip through a few questions, then quit (or let it finish). Run `grasp scan` again in the SAME repo. Confirm it does NOT re-ask about files you already saw — it should pick up new, previously-unscanned files instead (or, if none remain, print a clear "nothing left to scan" message pointing at `grasp reset history`).
- [ ] In a repo with more than one top-level folder (e.g. `src/`, `test/`, `docs/`), run `grasp scan` and pay attention to which files it asks about. Confirm it isn't spending its whole budget inside just one folder — you should see it touch more than one top-level directory before stopping.
- [ ] Run `grasp scan --full` in a repo with unscanned files left. Confirm you see a plain warning first ("this will scan the entire codebase and could generate a large number of questions...") — NOT a `y/N` confirmation prompt like `grasp reset history` uses — and that it proceeds without you having to answer anything.
- [ ] Lower the scan cap (`grasp set scan-cap 2`) and confirm `grasp scan` (without `--full`) stops after 2 real questions, not more — and confirm this is completely independent of `questionsPerSessionCap`/`grasp set questions-cap`, which should be untouched by anything scan does.
- [ ] With both a pending diff question (from normal Claude Code use) AND a pending scan question at the same time: run `grasp review` and confirm you only see the diff question, plus a one-line hint near the end pointing at `grasp scan` for the rest. Then run `grasp scan` and confirm the reverse — only the scan question, plus a hint pointing back at `grasp review`.
- [ ] **The concept-memoization check that matters most:** answer a concept question for real via a normal Claude Code diff review, note the concept. Then run `grasp scan` until it would plausibly hit that same concept in an existing file — confirm it does NOT ask the concept question again (instance-only). Then do the reverse: master a concept via `grasp scan` first, and confirm your next real diff review skips re-teaching it too.
- [ ] Confirm `grasp set mode --easy` (or `--hard`) visibly affects which concepts `grasp scan` favors, the same way it does for diff questions.
- [ ] Confirm Ctrl+C during a `grasp scan` review is safe — anything not yet answered stays pending for next time, same as `grasp review`.
- [ ] Confirm untracked/uncommitted files are never included in a scan — only `git ls-files`-tracked files should ever get a question.

### Chunking for large files

- [ ] Find or create a genuinely large tracked file (a few thousand lines or more). Run `grasp scan` against a repo containing it and confirm it can produce MORE THAN ONE question about that single file across one or more runs — not the old "one shot, forever" per-file limit. Each instance question's cited excerpt should show the file's real, absolute line numbers (e.g. a question about the file's later half should cite line numbers well past 1, not restart at 1).
- [ ] With a large multi-section file alongside several small files in the same repo, watch (or check `grasp review`'s ordering/timestamps for) the order questions get generated in. Confirm the large file's sections are NOT all processed back-to-back before anything else — you should see other files' questions interleaved between the large file's own sections, one section advanced per pass through the round-robin order.
- [ ] Run `grasp scan` again after answering some (but not all) sections of a large file. Confirm it resumes from the next unscanned section of that file, not from the beginning, and not skipping the file entirely just because it's already partly covered.
- [ ] Try scanning a file that's binary-ish, or a genuinely enormous one (tens of thousands of lines — comfortably past the new, much larger defensive ceiling). Confirm both are skipped (marked scanned, no judge call, no crash), and confirm the oversized case specifically prints a visible message naming the file, its line count, and the ceiling (`"Skipped <path> — N lines, over the M-line processing ceiling."`) — not a silent skip.
- [ ] If you have an old `~/.grasp/history.db` with real `grasp scan` history from before this build's chunking rework: run `grasp scan` once and confirm it doesn't error out and doesn't immediately re-ask about files you'd already fully scanned before — the schema migration should have expanded each old "fully scanned" file into all of its current chunks, already marked done.

### Hash-based re-scan for edited files

- [ ] Fully scan a small file with `grasp scan` (answer or skip its question so it's no longer pending, and confirm `grasp scan` reports it as covered — nothing left to ask about that file). Then make a genuinely meaningful hand-edit to that file (add real logic, not just whitespace) OUTSIDE of Claude Code — a plain text editor, not an agent. Run `grasp scan` again and confirm it produces a NEW, real question about that file — not silence, and not the exact same question as before.
- [ ] Make a purely trivial hand-edit to a previously-scanned file (reformatting, whitespace-only) and run `grasp scan` again. Confirm NO new question is generated for that file (it should still report nothing left to scan, assuming nothing else is outstanding) — the edit should be silently absorbed, not treated as something worth asking about.
- [ ] Confirm a file you've never scanned before still works completely normally the first time — no weirdness or errors from the new hash-check logic on a file with no prior scan history.
- [ ] Try this on a genuinely large file (a few thousand lines, comfortably past the practical hash-tracking size limit but under the much larger processing ceiling). After it's been fully covered once, edit it by hand and run `grasp scan` again — confirm it's NOT re-detected as changed (this specific size-based limitation is expected, not a bug — see [Known limitations](#known-limitations-so-you-dont-mistake-these-for-bugs)).
- [ ] Run `grasp reset history` and confirm it clears re-scan tracking too, not just the chunk-coverage/question history (check directly: `sqlite3 ~/.grasp/history.db "select count(*) from scan_file_hashes;"` should read `0` afterward).

### Run summary

- [ ] Run `grasp scan` against a repo with a couple of small, real files it hasn't seen before. Answer or skip through the questions, and confirm a short (a couple of sentences), plain-language summary of what that run covered prints AFTER you've finished the interactive review — not interrupting it partway through.
- [ ] Confirm the summary's cost appears on its own line ("$0.000X spent generating this run's summary"), visibly separate from the "$ spent generating comprehension questions this scan" line above it.
- [ ] Run `grasp scan` again immediately in the same repo with nothing new to cover (everything already scanned, no edits). Confirm you get the plain "Nothing left to scan" message with NO summary attempt and no summary cost line at all.
- [ ] Confirm the summary accurately describes what THAT run actually covered (the files/areas it just read), not a stale description of a previous run or the whole repo in general.
- [ ] Confirm none of this affects `grasp export` (no new rows, no new columns) or `grasp reset history`'s reported counts — the summary is not saved anywhere.

## 7. What happens when things go wrong

You don't need to force these, but if any of them happen naturally during testing, take note — and it's worth deliberately trying at least the first two:

- [ ] If your Claude Code session gets interrupted or you close the terminal mid-task, does Grasp recover fine afterward (no weird errors, no stuck state)?
- [ ] If a question ever fails to generate (rare, but possible — bad network, hiccup, etc.), does everything continue normally, with no crash and no confusing error message in your way? Confirm the `Stop` message now names the failure directly — something like `"A comprehension question failed to generate (timeout) — it'll retry automatically on this session's next turn, or run \`grasp retry\` now."` — rather than staying silent about it.
- [ ] Run `grasp retry` right after that failure (same still-live session). Confirm it picks up the stuck diff and either produces a real question (check `grasp review`) or reports the same failure again cleanly — it should never crash or hang.
- [ ] **The scenario `grasp retry` actually exists for:** get a diff stuck (a failed/timed-out generation attempt), then let that Claude Code session end for good — close the terminal, don't resume it. In a LATER, unrelated session (or no session at all), run `grasp retry` from the same repo. Confirm it still finds and retries the stuck diff, even though the session that originally captured it is long gone.
- [ ] Run `grasp retry` with nothing stuck (a clean repo). Confirm it prints a plain "nothing to retry" message and exits cleanly — no error, no hang.
- [ ] Put an invalid value into `.grasp.json` or `~/.grasp/config.json` by hand (e.g. a typo'd key, a bad `gateMode` value) and try to use Claude Code normally. Confirm Grasp fails quietly for hook-driven commands (no broken session, a diagnostic written to stderr only) but fails loudly with a clear message for a command you run yourself (`grasp review`, `grasp scan`, `grasp retry`, etc.).

## 8. The big-picture question

At the end of this pass, answer honestly:

- [ ] Did you keep Grasp turned on the whole time, or did you disable it at some point during real work?
- [ ] If you disabled it — why? (Too naggy? Questions felt pointless? Got in the way at a bad moment? Something broke?)
- [ ] Do you feel like you understood your codebase(s) better after this than you would have without it — both the code you were actively changing (`grasp review`) and code you were new to (`grasp scan`)?
- [ ] Is there a moment you specifically remember Grasp catching something you would have otherwise skimmed past?
- [ ] Anything that felt like a bug, a rough edge, or just "off" that isn't captured by a checkbox above? Write it down as you go rather than trying to remember it all at the end.

## Known limitations (so you don't mistake these for bugs)

- **`grasp scan` is a scope extension, not part of the original brief.** It reuses the diff side's storage, judge-call pattern, and review UI on purpose — worth knowing so its behavior is judged as its own feature, not as a bug in the original diff-comprehension design.
- **`grasp scan` presents in one batch, not one-question-at-a-time.** It generates its whole run's worth of questions first, then hands the full batch to the same review UI — see §6b.
- **`grasp scan` only sees tracked files.** It reads `git ls-files` (untracked/uncommitted files aren't included). Large files are split into ~400-line sections, each tracked and covered independently and resumably.
- **`grasp scan` re-checks a fully-covered file's content hash on each run, up to a practical size limit (5,000 lines).** A genuine edit clears that file's section coverage and lets it re-enter the walk from the start; a trivial edit just updates the record silently. Files over the size limit keep the older, fully-permanent behavior — once covered, never re-checked, regardless of later edits — since re-scan tracking would mean storing a full extra copy of that file's content. Run `grasp reset history` to start any file over, regardless of size.
- **Claude Code only.** No support for other AI coding tools yet.
- **`grasp review` and `grasp scan` are both manual.** Nothing pops up on its own — you have to run the command yourself. `grasp scan` is inherently on-demand too — there's no background scanning.
- **No answer grading.** Grasp never tells you if your answer was "right" — it never even sees your answer (nothing gets sent back to an LLM after you type it). It shows you a sample answer afterward, generated up front alongside the questions, so you can compare it against your own — that's for your own judgment, not a score from Grasp.
- **One way to generate questions, no backup plan.** If the underlying call fails, times out, or hits your question cap, Grasp skips that question and logs why — it doesn't try a second method. Generation is batched once per Claude Code turn (`Stop`), not once per tool call, and a failed/timed-out attempt isn't lost — a visible `Stop` message says so, the diffs it would have covered stay pending, and they're folded into the next attempt automatically (this session's next turn) or on demand via `grasp retry` (any session, including ones that have already ended — see §7). There's no dollar-cost cap anymore, so nothing halts an entire session over an uncosted call.
- **`cap_reached` now always means the question cap.** There's only one cap left per surface (`questionsPerSessionCap` for live sessions, `scanQuestionsCap` for scan — fully independent of each other), so `miss_reason: "cap_reached"` is unambiguous, and both surfaces name their own cap value directly when it fires.
