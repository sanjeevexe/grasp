## 2026-08-04 — Language/runtime and TUI framework

**Decision:** Node/TypeScript, with `ink` for the terminal UI.

**Reasoning:** Claude Code itself is a Node CLI, and its hooks (`PreToolUse`, `PostToolUse`, `Stop`) are plain shell commands — so the integration cost between Grasp and Claude Code is roughly equal regardless of Grasp's own language. Given that, the deciding factors are downstream: `npm install -g` keeps Grasp in the exact install path its target users (Claude Code users) already have configured, with no extra runtime to bootstrap. The Node ecosystem also maps cleanly onto what the brief actually needs — `better-sqlite3` for the local store (3.5), `execa` for shelling out to `claude -p` and parsing its JSON output (3.3), and mature diff-parsing/syntax-highlighting libraries for the TUI (3.4) — without requiring custom tooling to glue them together.

**Alternatives considered:** Python + `textual`. Also a reasonable pick (`pip install`, easy diff tooling per the brief's own 5.4 note), and `textual` arguably has more TUI polish out of the box than `ink`. It lost because it introduces a second runtime/package manager into a workflow that's already Node-centric (Claude Code, npm), for no offsetting benefit — the integration surface with Claude Code's hooks doesn't favor Python at all, so the "matches the ecosystem the user is already in" argument breaks the tie toward Node. Rust + `ratatui` was not seriously in the running for v1: best TUI polish and single-binary distribution, but steepest curve, and the brief itself flags it as "the challenge option" rather than the pragmatic one.

## 2026-08-04 — Config file format and location

**Decision:** JSON. Global defaults at `~/.grasp/config.json`, created on first run. An optional per-repo `.grasp.json` is deep-merged on top of the global file, with repo-level values winning on conflict.

**Reasoning:** JSON needs no extra parsing dependency in a Node/TS project (`JSON.parse` is enough), and it's the format Claude Code's own settings already use, so it stays consistent with the ecosystem Grasp lives in. A two-tier global + per-repo merge matches how the brief actually talks about config (ignore patterns, caps) — some of it is clearly personal/global (cost cap, gate mode) and some is naturally project-specific (ignore patterns for a given repo's generated paths), so a single flat file would force one scope to win awkwardly over the other.

**Alternatives considered:** YAML or TOML — more human-friendly to hand-edit (comments, less punctuation), but both require a parsing dependency for no functional gain, and neither is what Claude Code itself uses, so the "matches the ecosystem" argument that decided the stack also decides this. A single global-only config (no per-repo layer) was considered for simplicity but rejected because ignore patterns in particular are inherently per-project and forcing them into one global file would mean maintaining an ever-growing cross-project blocklist.

## 2026-08-04 — Diff-size thresholds for "meaningful" changes

**Decision:** Mechanically skip diffs under 3 changed lines in a single file, and skip diffs over 1500 total changed lines or 800 changed lines in any single file. Both bounds are configurable in the config schema. This is a cheap pre-filter only — the semantic "is this actually worth a question" judgment stays entirely inside the Phase 5 LLM judge call, not here.

**Reasoning:** The brief's §5.2 explicitly calls for a size threshold but gives no numbers, and also explicitly delegates "worth asking about" judgment to the model in §3.3 rather than a static list. Splitting the work this way keeps Phase 4 doing only what's mechanical and nearly free (line counting), while leaving the judgment call — which the brief is emphatic can't generalize as a static list — entirely to the one place designed to make it. The lower bound (3 lines) exists purely to avoid burning a generation call on a trivial edit (a renamed variable, a one-line import fix); the upper bound (1500/800) exists to avoid feeding an enormous vendored dump into the prompt, which would be expensive and not meaningfully "one diff" a user could answer questions about anyway.

**Alternatives considered:** No mechanical pre-filter at all — send every diff to the judge call and let it decide, including on trivial or huge diffs. Rejected because it burns a paid/rate-limited generation call on cases that are cheap to rule out mechanically first (a one-line formatting fix doesn't need an LLM to know it's not worth a question), which works against the cost-cap safety rail the brief treats as load-bearing. A more elaborate heuristic (e.g. weighting by file type or churn history) was also considered and rejected as exactly the kind of static-pattern complexity the brief already rejected for the "worth asking" decision generally — better to keep the mechanical layer dumb and push anything requiring real judgment into the one call built for it.

## 2026-08-04 — Cost cap default

**Decision:** $0.25 per session.

**Reasoning:** The brief suggests "a few cents per session" as a default without a number. $0.25 comfortably covers several judge+generate calls (a session with, say, 8 meaningful diffs) at the per-call cost a `--max-turns 1`, no-tools headless call is expected to run, while still being small enough that hitting it in a single session is a rare, noticeable event rather than a routine occurrence — which matters because the brief treats the cap being hit as a logged signal worth paying attention to, not just a silent ceiling.

**Alternatives considered:** A lower default (e.g. $0.05) was considered to hew closer to "a few cents," but rejected as likely to be hit routinely on a single long Claude Code session, which would make the cap noise rather than signal and undercut its purpose as a safety rail rather than a nuisance. A higher default (e.g. $1.00) was rejected as loose enough to stop functioning as a meaningful anxiety-reducing ceiling, which is the cap's actual job per §3.3.

## 2026-08-04 — Questions-per-session cap default

**Decision:** 8 questions per session.

**Reasoning:** The brief requires this cap (§5.2, §5.3, success criteria) but gives no number. 8 is enough to meaningfully scale content across a long unattended run (§5.3's stated goal) without producing the "unanswerable backlog" the same section explicitly warns against — a user returning to 8 queued questions is a lot but plausibly workable in one sitting; a user returning to 30+ is not.

**Alternatives considered:** A smaller cap (e.g. 3) was considered but rejected as working against §5.3's explicit point that a single question shouldn't have to represent an entire long wait — capping too low reintroduces the "one 20-second question doesn't fill a 10-minute wait" problem the brief calls out by name. An uncapped queue was rejected outright since the brief explicitly requires a cap to prevent an unanswerable backlog.

## 2026-08-04 — SQLite schema specifics

**Decision:** An `events` table with columns matching brief §3.5's fields directly — timestamp, repo, diff_hash, diff_summary, question_concept, question_instance, question_type, generation_source, miss_reason (nullable), answer_concept (nullable), answer_instance (nullable), skipped (integer/boolean), skip_reason (nullable), cost_usd (nullable) — plus a separate `concept_tags` join table (event_id, tag, answered) indexed on `tag`. Concept mastery/memoization (the §3.2 "don't re-teach" check) is scoped globally per user across all repos, not per-repo.

**Reasoning:** A join table for tags (rather than a serialized/comma-joined field on `events`) is what makes the §3.2 memoization lookup ("has this tag been answered before, anywhere") a simple indexed query instead of a table scan with string parsing. Global (cross-repo) scoping for mastery follows directly from what a "concept" actually is in this design — a mutex-vs-channel question is about a general programming idea, not something scoped to one repo, so a user who's already demonstrated understanding of it on project A shouldn't be re-taught it on project B. Re-teaching per-repo would also mean the memoization check gets weaker exactly when it matters most — someone who works across many small repos would never accumulate credit for anything.

**Alternatives considered:** A single denormalized `events` table with tags stored as a JSON array or comma-separated string column. Simpler schema, one less table/join — but the memoization check (§3.2) is the single most frequent read against this data (it runs on every generation call, per §3.3) and doing it against a string field means scanning and parsing every historical row instead of an indexed lookup. Per-repo-scoped mastery was also considered, matching how `repo` already scopes other fields in the table, but rejected for the reasoning above — it would systematically undercount what a user actually knows.

## 2026-08-04 — Flagged-pattern filtering (auth/error-handling/control-flow priority)

**Decision:** No separate regex/path-based detector for §5.2's "prefer hunks touching flagged patterns" language. This judgment is folded entirely into the Phase 5 judge+generate call. Phase 4 stays purely mechanical: size thresholds, lockfiles/generated paths, ignore patterns — no semantic pattern-matching lives there.

**Reasoning:** This is the same argument the brief already makes for itself in §3.3 when explicitly rejecting a static allowlist/denylist for the broader "is this diff worth a question" decision — a fixed list of "interesting" patterns (auth, error handling, control flow) can't generalize across real diffs any better here than it could there, and the brief already pays for a model call that reads the full diff anyway. Building a second, narrower static detector for this one sub-case would reintroduce the exact failure mode the brief spent §3.3 arguing against, just at smaller scope.

**Alternatives considered:** A standalone keyword/path heuristic (e.g. flagging diffs touching files named `auth*`, `*error*`, or new entries in `package.json`) was considered since it's cheap and requires no model call. Rejected because it's brittle across languages and naming conventions (exactly the cross-language generalization problem the brief cites when rejecting the heuristics tier entirely in Section 4), and because the judge call already has the full diff in front of it, so asking it to also weight "does this touch something structurally important" costs nothing extra beyond the generation call the system is paying for regardless.

## 2026-08-04 — Hook registration mechanics

**Decision:** `grasp init` auto-installs the Claude Code hooks (`PreToolUse`, `PostToolUse`, `Stop`), but first shows the user exactly what will be added to their Claude Code settings and asks for confirmation before writing. Idempotent on re-run — detects existing Grasp-installed hooks and doesn't duplicate them.

**Reasoning:** Manual hand-editing of Claude Code's hook config would reintroduce exactly the onboarding friction the brief works hard to eliminate elsewhere (§3.3 rejects BYOK partly on these grounds: "reintroduces exactly the onboarding friction the piggyback approach exists to eliminate"). Auto-install with a shown diff and explicit confirmation keeps install to effectively one command while still respecting that Grasp is silently intercepting the user's coding session and shipping diffs to an LLM — §3.5's "trust is load-bearing" stance means the user should see what's being changed in their own tool config, not have it happen invisibly.

**Alternatives considered:** Fully silent auto-install with no confirmation step — fastest install, but conflicts directly with the brief's own transparency requirements (§3.3, §3.5) about never burying what Grasp does with the user's setup. Fully manual (documented steps, user edits their own Claude Code settings) — safest from a "never touch the user's config" standpoint, but adds a real setup step that most users would either skip or get wrong, undermining the "installs and runs with a single command" success criterion.

## 2026-08-04 — Session definition for capping and batching

**Decision:** A "session" is one Claude Code invocation, bounded by the adapter's `onSessionComplete` (i.e., the `Stop` hook firing). This definition applies uniformly to both the cost cap (§3.3) and the question queue/batching (§5.3).

**Reasoning:** The brief already ties `onSessionComplete` to "flush queue, present before final output" in its own adapter interface sketch (§5.1), so a wall-clock or otherwise independently-defined "session" would require inventing a second boundary concept the brief never asks for, and risks the cost cap and the queue disagreeing about when a session starts/ends. Binding both to the same hook-driven boundary keeps the mental model single: one Claude Code run is one unit of spend and one unit of batched questions.

**Alternatives considered:** A wall-clock window (e.g. reset the cap/queue every N minutes of inactivity) was considered as a way to handle a user who runs several short back-to-back Claude Code invocations without ever really "leaving," but rejected as a speculative complexity the brief doesn't ask for — it would need its own idle-detection logic (which is explicitly the kind of presence-detection machinery the brief defers in Section 4's "presence-adaptive delivery" row), for a scenario that isn't described as a problem anywhere in the brief.

## 2026-08-04 — Diff summary generation

**Decision:** Generate the `diff_summary` logged field locally and deterministically — file list plus insertion/deletion counts — with no LLM call involved.

**Reasoning:** The brief is explicit and repeated on this point: v1 has exactly one generation path (§3.3, "No fallback tiers"), and every cost source is supposed to be visible through the cap the user configures. A second LLM call purely to summarize a diff for a log field would be an uncapped, unauthorized cost source running outside the one path the brief designed cost tracking around — it would also fire on every captured diff, including ones the Phase 4 filter or Phase 5 judge decide aren't worth a question, which is the opposite of "keep it cheap" (§3.3's framing for the one call that is allowed).

**Alternatives considered:** Reusing the same judge+generate call to also emit a short summary alongside its judgment/questions — cheap in theory since the model already has the diff loaded. Rejected because it couples an internal logging concern to the external-facing generation call's output contract for no real benefit: a mechanical file-list-plus-counts summary is sufficient for the log's purpose (letting a user recognize which event a row refers to) and doesn't need natural-language quality.

## 2026-08-04 — better-sqlite3 major version (13.x, not 11.x)

**Decision:** Pin `better-sqlite3` to `^13.0.2` rather than the more commonly-referenced `^11.x` line.

**Reasoning:** `better-sqlite3@11.10.0` fails to build from source on this machine's Node 26.5.1 — the native addon's V8 API usage (`v8::Object::GetPrototype`, `v8::Context::GetIsolate`, `PropertyCallbackInfo::This`) no longer matches Node 26's V8 headers, and node-gyp has no prebuilt binary for that combination, so it falls through to a source compile that errors out. `13.0.2` both ships a prebuilt binary for current Node versions and targets a V8 API generation that still matches Node 26, so `npm install` succeeds with no compiler toolchain involved at all.

**Alternatives considered:** Pin to an older Node LTS instead of upgrading the dependency — rejected because it would mean asking every future contributor/user to manage a specific Node version rather than fixing a library version pin, and the project doesn't otherwise need anything Node-26-specific. Patch or vendor `better-sqlite3@11` locally — rejected as needless maintenance burden when a newer major already solves it cleanly upstream. `package.json`'s `engines.node` was tightened to `>=22` to match `13.x`'s own stated floor (this correction from a stale `>=18` was made during the 2026-08-06 Codex fix pass; not logged as its own entry there since it had only one reasonable answer — see that pass's overview entry).

## 2026-08-04 — TypeScript compiler target and module system

**Decision:** `target: ES2022`, `module: CommonJS`, `moduleResolution: node`, `strict: true`.

**Reasoning:** CommonJS avoids the ESM/CJS interop friction that `better-sqlite3` (a native CJS addon) and a `#!/usr/bin/env node` shebang bin script would otherwise create — Node's ESM loader has extra rules around `.js` extensions in relative imports and native addon resolution that CommonJS sidesteps entirely, and Claude Code's own hook scripts are plain CommonJS-friendly Node too. ES2022 as the emit target was chosen as a spec level comfortably supported by the Node floor `engines.node` declared at the time (`>=18`; later tightened to `>=22` during the 2026-08-06 Codex fix pass — see that pass's overview entry), so it uses modern syntax (top-level `??=`, `Object.hasOwn`, etc. if ever needed) without pushing runtime support past what the package claims to support.

**Alternatives considered:** ESM (`module: NodeNext` / `"type": "module"`) — more forward-looking, and what newer Node tooling increasingly defaults to, but rejected for now given the CJS-native dependency and shebang-script friction above; revisit if a future dependency forces the issue. A lower target (ES2020) was considered for wider compatibility but rejected as unnecessary — nothing about this project targets pre-2022 Node runtimes.

## 2026-08-04 — Config deep-merge semantics: arrays replace, not concatenate

**Decision:** When a per-repo `.grasp.json` overrides a key that's an array (e.g. `ignorePatterns`) or any non-object value, the repo's value wholly replaces the global value. Only plain-object values (like `diffThresholds`) merge key-by-key; arrays and primitives never merge.

**Reasoning:** Array concatenation is the more surprising behavior for a config override — a user writing `"ignorePatterns": ["vendor/"]` in a repo almost certainly means "add this on top of whatever's global," which concatenation would give them, but concatenation also makes it impossible to *remove* a global pattern for one repo, and silently duplicates entries if the same override file is ever loaded twice. Replace-on-conflict is simpler to reason about and matches how most JSON config-merge tools (e.g. ESLint's `overrides`, ts-node's compiler options) behave by default.

**Alternatives considered:** Concatenate arrays (union of global + repo values) — appealing for `ignorePatterns` specifically (purely additive use case) but wrong for a hypothetical future array-valued setting where a repo genuinely wants to override rather than extend, and inconsistent to special-case by key name. Deep-merge arrays by index — clearly wrong for a list of independent string patterns; rejected without much consideration.

## 2026-08-04 — Per-repo config resolution: cwd only, no upward search

**Decision:** `loadConfig()` looks for `.grasp.json` only in the exact directory passed to it (defaulting to `process.cwd()`). It does not walk up parent directories looking for a git root or any other project boundary.

**Reasoning:** Phase 1 has no git/repo-detection logic yet — that machinery doesn't exist until the capture adapters in Phases 2–3 — so implementing upward search now would mean guessing at how "repo root" gets defined before the phase that actually owns that definition has been built. Resolving against the exact directory Grasp is invoked from is also simplest to reason about and test today, and does not foreclose adding upward search later: Phase 2/3 can pass whatever directory they determine to be the repo root into this same `loadConfig(repoRoot)` signature without changing this function at all.

**Alternatives considered:** Walk up from `cwd` to the nearest `.git` directory, `.grasp.json`, or filesystem root (the common pattern for tools like ESLint/Prettier) — more convenient for a user running `grasp` from a subdirectory, but requires deciding *now* what "repo root" means, which duplicates work the capture-adapter phases will need to do anyway with actual git integration. Deferred rather than rejected outright — likely to be revisited once Phase 2/3 need a real repo-root concept.

## 2026-08-04 — Malformed config/DB file handling: fail loudly, never silently overwrite

**Decision:** If `~/.grasp/config.json` or a repo's `.grasp.json` exists but fails to parse as JSON, Grasp throws a clear, actionable error (naming the file and the parse error) and exits non-zero — it never silently replaces the broken file with defaults, and never partially applies a broken config.

**Reasoning:** Silently regenerating a config file the user (or some other tool) hand-edited would be a surprising, hard-to-notice data loss — exactly the kind of "no surprises" violation brief §3.5's trust stance warns against for a tool that already has to earn trust by reading the user's code. An explicit failure that names the exact file and the parse error is more helpful than either silently discarding their edits or continuing with a half-broken config that produces confusing downstream behavior.

**Alternatives considered:** Auto-repair by renaming the broken file to a `.bak` and regenerating defaults — friendlier for a user who doesn't know why the file is broken, but it still discards their edit without an explicit ask, and was set aside in favor of the more conservative fail-loud behavior for now; worth reconsidering if real users hit this often and find the error unhelpful. Silently falling back to defaults in memory without touching the file on disk — rejected because it hides a real problem (the on-disk file stays broken and every future run keeps failing the same way) behind an apparently-working command.

## 2026-08-04 — No CLI argument-parsing framework in Phase 1

**Decision:** `grasp`'s Phase 1 commands (`--version`, `--help`, `debug:seed`) are dispatched with a plain `process.argv` switch — no `commander`, `yargs`, or similar dependency.

**Reasoning:** Three flat, mutually-exclusive commands with no options/flags of their own don't justify a parsing library; a manual switch is fewer lines and one fewer dependency to audit for an open-source tool where §3.6 already treats trust as load-bearing. This isn't meant to hold for later phases — once real commands need flags, subcommands, and `--help` text generated per-command (Phase 7+, once the TUI and gate config surface grow), a proper CLI framework is likely worth revisiting.

**Alternatives considered:** `commander` or `yargs` now, ahead of need — rejected as premature for three flat commands; adding either later is a small, isolated change when the command surface actually grows past what a manual switch handles cleanly.

## 2026-08-04 — SQLite journal mode: WAL

**Decision:** Open the SQLite connection with `PRAGMA journal_mode = WAL` (write-ahead logging) rather than leaving SQLite's default rollback-journal mode.

**Reasoning:** WAL allows concurrent readers alongside a writer without blocking, which matters here because the eventual runtime shape (Phase 2+) is a hook-triggered background process potentially writing events while a TUI or a `sqlite3` inspection command reads the same file — brief §3.5 explicitly wants the store to stay "inspectable" (e.g. via the `sqlite3` CLI) without that inspection contending with normal writes. `better-sqlite3`'s own docs recommend WAL for exactly this reason.

**Alternatives considered:** Leave the default rollback-journal mode — simpler (no extra `-wal`/`-shm` sidecar files next to `history.db`), but readers and writers can block each other, which works against the "inspectable at any time" goal. Noting the sidecar files here since a user poking at `~/.grasp/` with `ls` will see `history.db-wal` / `history.db-shm` alongside `history.db` and might wonder what they are.

## 2026-08-04 — Git-diff capture: comparison mechanism (diff against HEAD, not the index or a stored snapshot)

**Decision:** `captureGitDiff(repoPath)` diffs the working tree against `HEAD` (or, if the repo has no commits yet, against git's empty-tree object `4b825dc642cb6eb9a060e54bf8d69288fbee4904`) using `git diff -M <baseRef>`, then separately unions in untracked files (via `git ls-files --others --exclude-standard`, each diffed with `git diff --no-index -- /dev/null <file>`). "No changes" is simply `files.length === 0` on the resulting object — there's no separate empty-repo special case to detect.

**Reasoning:** Brief §5.1 only loosely specifies this ("watch git working-tree state / `git diff` between checkpoints"), leaving the actual comparison base open. Diffing against `HEAD` captures everything not yet committed — staged and unstaged changes to tracked files alike — which is the right proxy for "what the agent just did" in a coding-agent workflow, since agents essentially never run `git add`/`git commit` themselves; whatever's uncommitted *is* the work in progress. `HEAD` also requires no state of Grasp's own: a single invocation is self-sufficient, with no prior "checkpoint" to have remembered. Untracked files need separate handling because `git diff <ref>` never includes them by design; `git diff --no-index` against `/dev/null` produces a correctly-formatted unified diff for a new file's full content without touching the index (kept read-only throughout — no `git add -N` or similar mutation).

**Alternatives considered:** Diff against the index only (`git diff`, no ref) — simplest, and what the brief's own example command shows, but misses any changes an agent (or the user) happens to have staged, which a pure "diff HEAD" comparison doesn't; rejected as strictly less complete for the same complexity. A stateful "diff between checkpoints" — store a snapshot (tree hash, or full file contents) at the end of each capture and diff against it next time, matching the brief's literal "between checkpoints" phrasing more closely — was considered and set aside for this phase specifically because there's no poll loop or persistent capture-daemon yet for "checkpoints" to mean anything; `HEAD` is the closest stateless proxy available today, and a real checkpoint concept is more naturally Phase 3's problem once hooks define actual event boundaries (`PreToolUse`/`PostToolUse`/`Stop`) to checkpoint against.

## 2026-08-04 — Git access mechanism: shell out to the `git` binary directly

**Decision:** All git interaction goes through a small wrapper (`src/git.ts`) around Node's `child_process.execFileSync("git", [...args])` — no `simple-git`, `isomorphic-git`, or other git library.

**Reasoning:** `execFile` (not `exec`) passes arguments as an array rather than a shell string, so repo paths or filenames with spaces/special characters can't be misinterpreted as shell syntax — the safety property that matters without needing a library for it. Beyond that, the actual value a library like `simple-git` provides is a parsed, opinionated view of git's output; this phase needs the opposite — exact control over flags (`--no-color`, `-M`, `--numstat`, `--name-status`) and access to git's raw unified-diff text so Grasp can parse it into its own `CapturedDiff` shape, which a library's own parsed diff objects would just have to be unwound from anyway. A thin wrapper is also what Phase 3 needs regardless: Claude Code's hooks are themselves just shell commands invoking a Node script, so the same `runGit`/`captureGitDiff` functions are directly importable there with no adapter-specific glue — a library dependency wouldn't make that reuse any easier, and would add one more piece of surface area for an open-source tool where trust is explicitly load-bearing (brief §3.6).

**Alternatives considered:** `simple-git` — mature, promise-based, handles a lot of git plumbing conveniently, but its parsed output for `diff`/`log` doesn't map cleanly onto the hunk-level structure `CapturedDiff` needs, meaning raw-output access would still be required underneath, making the library mostly redundant overhead. `isomorphic-git` — a pure-JS git implementation, valuable when a real git binary isn't guaranteed to exist (browser, constrained sandboxes); irrelevant here since anyone using an AI coding agent against a git repo already has git installed, and the fallback capture path's own reason for existing (§5.1) is to work with *any* agent, not to work without git.

## 2026-08-04 — Diff-object parsing: numstat/name-status for authoritative stats, hand-split raw text for hunks

**Decision:** File-level `status` (added/modified/deleted/renamed) and `insertions`/`deletions` counts come from git's own `--name-status -M` and `--numstat -M` output (parsed as the small, well-defined tab-separated formats they are), not by counting `+`/`-` lines by hand. Only the `hunks` field — the actual `@@ ... @@` chunks and their body lines — is produced by hand-splitting the raw `git diff -M <baseRef>` text, matched back to each file by its `+++`/`---` header path.

**Reasoning:** git already computes accurate per-file stats and correctly distinguishes add/modify/delete/rename (including similarity-based rename detection via `-M`); re-deriving those by scanning raw diff text would be strictly worse (more code, more edge cases — e.g. rename detection from raw diff alone requires recognizing `similarity index` / `rename from` / `rename to` lines) for a result git already hands over in a trivially parseable format. Hunk *text*, on the other hand, has no equivalent flag-driven shortcut — the raw diff is the only source for it — so hand-splitting is the only option there, but it's a narrow, mechanical job (split on `diff --git ` boundaries, then on `@@` boundaries) rather than a full diff-semantics reimplementation.

**Alternatives considered:** Deriving everything (status, stats, and hunks) purely from parsing the raw `git diff -M` output — one source of truth, no need to correlate three separate git invocations by path. Rejected because rename detection and binary-file handling are meaningfully fiddlier to get right by hand than by reading git's own `R089`-style status codes and `-`-for-binary numstat markers, for no benefit over just asking git directly. Using a diff-parsing library (e.g. `parse-diff`) for the raw-text side — reasonable, but Phase 2's hunk shape (`{header, lines}`) is intentionally minimal and library-free for the same reason as the git-access decision above: one third-party parser fewer, and the format is simple enough (split twice) not to need one.

## 2026-08-04 — Claude Code hook payload shape: verified against live docs, not a live hook firing

**Decision:** `ClaudeCodeHookPayload` (in `src/adapters/claudeCodeAdapter.ts`) is typed from Anthropic's current official hooks reference (`https://code.claude.com/docs/en/hooks`, fetched live during this session), not from memory/assumption and not from an actual observed hook firing. `session_id`, `cwd`, and `hook_event_name` are treated as reliably present on every event (the docs list them as common fields present across all hook types, with concrete matching examples for `PreToolUse`/`PostToolUse`/`Stop`). `prompt_id` is treated as *unconfirmed* — the docs note it's "absent until first user input," which is ambiguous about whether it's reliably present by the time `PreToolUse`/`PostToolUse`/`Stop` can fire — so the code never assumes it's set (see `resolvePromptId`'s fallback, logged separately below).

**Reasoning:** The task asked for genuine empirical verification — wiring a scratch stdin-dumping hook into a real Claude Code session — the same discipline used for git output formats in Phase 2. That was attempted properly, not skipped: a probe hook (`/private/tmp/grasp-hook-probe/dump.js`) was wired into this live session's own project `.claude/settings.json` first (didn't fire — hooks appear to load once at session start, not live-reloaded mid-session, so a hook added after the session began never took effect for the rest of it); then a fresh, separate Claude Code process was attempted two ways — `npx @anthropic-ai/claude-code` (a genuinely separate install) and the exact `claude` binary bundled with the desktop app at `$CLAUDE_CODE_EXECPATH` (same binary family driving this very session). Both reported `"Not logged in · Please run /login"` / `{"loggedIn": false}` — this sandboxed environment has no standalone CLI-level authentication a subprocess can use, distinct from whatever protocol the desktop app uses to drive this session directly. Forcing a `/login` OAuth flow or hunting for credentials elsewhere on the machine was judged out of bounds (not what was asked, and risks using the user's account for a side purpose without being asked). ## 2026-08-04 — Stop fires once per conversational turn, not once per whole CLI session

**Reasoning:** A second doc fetch, asked specifically to resolve this ("does Stop fire once per turn or once per whole session? Is there a separate SessionEnd?"), confirmed: `Stop` is listed explicitly as a **once-per-turn** event, fired every time Claude finishes responding to a single prompt — and there's a *separate* `SessionEnd` event ("session terminates") that BUILD_PLAN.md's Phase 3 scope never asked for and this phase doesn't wire up. This actually turns out to still be the *right* binding for `onSessionComplete`, not a bug to route around: the `AgentAdapter` interface's own annotation for this method is "flush queue, present before final output" (brief §5.1) — "final output" most naturally reads as *this turn's* output, i.e. exactly the point where Grasp should interject with a question before the user sees what Claude just did. That's a per-turn gate, which is what `Stop` actually provides. So Phase 3's `Stop`→`onSessionComplete()` wiring is correct as built; what was wrong was the informal shorthand "session = one Claude Code invocation" in the earlier decision, which reads naturally as "the whole time the user has `claude` open," and isn't accurate for interactive use.

**Consequence flagged for Phase 5/8, not resolved here:** the cost cap (§3.3, $0.25 default) and questions-per-session cap (§5.2/§5.3, 8 default) were sized assuming a broader "session" than one turn — a $0.25 cap or an 8-question cap that fully resets on every single conversational turn would barely constrain a long interactive work session (many turns) at all, which likely isn't what those defaults were meant to protect against. Phase 5/8 will need to explicitly decide whether spend/question caps key off `(session_id, prompt_id)` (matches this phase's turn granularity, resets every turn) or off `session_id` alone (spans the whole interactive session, requiring `SessionStart`/`SessionEnd` — hooks not wired in this phase) or something else. Not decided here — out of Phase 3's scope (capture-and-install only) — but recorded so it isn't silently inherited as settled.

**Alternatives considered:** Wire `SessionStart`/`SessionEnd` now instead of/in addition to `Stop`, to get a true whole-session boundary — rejected for this phase because BUILD_PLAN.md's Phase 3 scope, and the task's own instructions for this session, explicitly name only `PreToolUse`/`PostToolUse`/`Stop`; adding a fourth hook family (with its own untested payload shape) is exactly the kind of scope growth the phase boundary exists to prevent, and the cap-boundary question it would answer belongs to Phase 5/8 anyway. Silently keep calling it "session" and hope the ambiguity doesn't matter — rejected because it's exactly the kind of gap that would surface confusingly later (Phase 5/8 quietly building on a wrong mental model) rather than now, when it's cheap to flag.

## 2026-08-04 — ClaudeCodeAdapter: session-state persistence across hook invocations

**Decision:** Cross-invocation state lives in three new SQLite tables (`cc_turns`, `captured_diffs`, `hook_invocations`), keyed by Claude Code's own `(session_id, prompt_id)` pair — not a temp file, not an in-memory daemon, and not additions to the existing Phase 1 `events` table. `cc_turns` tracks one row per turn (`started_at`, nullable `completed_at`); `completeTurn()` is an atomic, idempotent `UPDATE ... WHERE completed_at IS NULL` so a redundant `Stop` firing for an already-completed turn safely no-ops. `captured_diffs` holds the diffs a turn's `PostToolUse` firings actually captured (the adapter's real output). `hook_invocations` is a pure append-only audit trail of every hook firing observed, which is what makes "did `Stop` really fire exactly once for this turn" independently verifiable from the DB rather than trusted on faith.

**Reasoning:** Each hook firing is a separate, short-lived Node process with no shared memory with any other firing — the whole architectural problem this decision exists to solve. Three options were weighed as the task asked: (1) using Claude Code's own `session_id`/`prompt_id` as the correlating key, vs. Grasp inventing its own session-boundary heuristic; (2) SQLite vs. a temp file for where state lives between firings; (3) how this reconciles with the existing `events` table and the (now-corrected) "session" concept. On (1): Claude Code's own identifiers are authoritative, already correctly scoped by the tool that owns the actual session lifecycle, and (per the entry above) `prompt_id` gives exactly the per-turn granularity `onSessionComplete` semantically needs — Grasp has no reason to invent a parallel concept when a correct one is handed to it on every hook call. On (2): Phase 1 already put the SQLite store in WAL mode specifically anticipating "a hook-triggered background process potentially writing events while [something else] reads the same file" — this scenario was foreseen, not new; a temp-file scheme would duplicate state better expressed in the store Grasp already has, need its own hand-rolled atomicity/locking story, risk orphaned files if `Stop` never fires (session killed mid-task — verification step 3), and wouldn't show up if a user inspects `~/.grasp/history.db` directly, undermining §3.5's "plain and inspectable" goal. On (3): a new `captured_diffs` table, not new columns on `events`, because `events` rows represent question/miss events under brief §3.5's own schema (question text, type, answer, cost) — a raw capture that hasn't yet been judged "worth a question" (Phase 4/5's job) isn't that, and giving it its own table keeps `events`' existing meaning intact rather than growing it a dual purpose. `captured_diffs`/`cc_turns` do **not** touch the existing `events` table at all, so no migration of the Phase 1 schema was needed this phase — flagged for whenever Phase 5/6 starts writing real `events` rows and needs to correlate them back to a session, which will need its own `session_id` column added then (not now, since nothing writes to `events` in Phase 3).

**Alternatives considered:** A temp file per session (e.g. `/tmp/grasp-session-<id>.json`) — simplest to picture, but loses concurrent-safety and inspectability for no offsetting benefit given SQLite/WAL was already the answer to this exact problem shape. Grasp generating its own session/turn identifiers (e.g. a UUID minted on first hook firing seen) instead of using Claude Code's `session_id`/`prompt_id` — rejected as pure duplicated complexity: Claude Code already hands over a correct, authoritative identifier on every call, so inventing a second one would only risk drifting out of sync with the thing it's trying to describe. Storing captured diffs as new nullable columns directly on `events` — rejected per the schema-purity reasoning above.

## 2026-08-04 — Formatting-only detection: per-hunk normalized-line-sequence comparison

**Decision:** A hunk is formatting-only if its normalized sequence of removed lines exactly equals its normalized sequence of added lines (same content, same order). "Normalize" means: strip the leading `+`/`-` marker, trim the line, and collapse any run of internal whitespace to a single space. A file is formatting-only only if *every* one of its hunks is. Comparison is by ordered sequence, not by multiset/sorted comparison.

**Reasoning:** The task's own suggested method — "normalize each changed line by stripping insignificant whitespace and compare added vs. removed lines" — leaves two real sub-choices open: what counts as "insignificant," and whether the comparison is order-sensitive. Trim + collapse-internal-whitespace catches the common real cases (reindentation, tabs-vs-spaces, trailing whitespace, multiple-spaces-to-one) without touching anything that changes actual tokens (case, quotes, semicolons, identifiers) — a conservative, defensible line for "insignificant." Order-sensitive comparison is the safer choice for the *other* axis: a multiset/sorted comparison would treat a genuine reordering of two statements as "formatting," which it isn't (reordering can change behavior) — sequence comparison never has that false-negative. Evaluating per-hunk rather than concatenating all of a file's hunks together keeps each contiguous change region self-contained, which is the more semantically correct unit (comparing hunk 1's removed lines against hunk 2's added lines makes no sense).

**Alternatives considered:** Multiset/sorted-line comparison instead of ordered-sequence — rejected for the reordering false-negative above. A stricter normalization (only collapsing leading whitespace, not internal runs) — would miss common formatting changes like multi-space-to-single-space cleanup or tab/space conversion inside a line, which are still "formatting" by any reasonable definition. A looser normalization (e.g. also ignoring case, or stripping all whitespace including between tokens) — rejected as too aggressive; that starts erasing real content differences (`myVar` vs `myvar`, `a+b` vs `a + b` arguably borderline but `a+b` vs `ab` must never be conflated), which is exactly the false-positive risk the task's phrasing ("insignificant whitespace" specifically, not "insignificant differences" generally) warns against.

## 2026-08-04 — Diff-size thresholds: per-file minimum, "any file clears the floor," not a diff-wide sum

**Decision:** `diffThresholds.minChangedLines` is evaluated per file (after ignore-pattern and formatting-only exclusion): the diff as a whole clears the minimum if *at least one* remaining file has `insertions + deletions >= minChangedLines`. It is not evaluated as a sum across all files. The maximum thresholds (`maxTotalChangedLines`, `maxSingleFileChangedLines`), by contrast, unambiguously apply to the sum across files and to any individual file respectively — that reading was already settled by the Phase 1 "Diff-size thresholds" entry's own wording ("skip diffs over 1500 total ... or 800 ... in any single file").

**Reasoning:** The minimum threshold's job, per its own original justification, is "to avoid burning a generation call on a trivial edit (a renamed variable, a one-line import fix)" — a single tiny, isolated change. A diff that touches five different files with a one-line change each (e.g. updating a function's call sites after a rename) is a materially different, arguably more meaningful case than one file with a one-line change — it's evidence of an intentional multi-site edit, not noise — so treating it identically to a single trivial edit by summing across files would filter out real, coherent work. Requiring only that *some* file individually clears the floor lets a diff with one substantial file and several trivial companions still pass (correctly, on the strength of the substantial file), while a diff where literally every file is below the floor still gets filtered (correctly, since nothing in it individually rises above "trivial").

**Alternatives considered:** Sum `insertions + deletions` across all significant files and compare that single total against `minChangedLines` — simpler (symmetric with how the maximum's "total" reading works), but wrongly filters the multi-file-small-edits case above, and also isn't really about the *purpose* of the minimum (ruling out single trivial edits) once more than one file is involved. Requiring *every* file individually clear the floor — rejected as the opposite failure mode: a genuinely meaningful multi-file change where one touched file happens to be a tiny one-line companion edit (e.g. bumping a version string alongside a real feature change) would be filtered entirely because of that one small file, which defeats the purpose of a minimum floor meant to catch *trivial*, not *mixed*, diffs.

## 2026-08-04 — Ignore-pattern matching syntax: basename/directory-segment match, no glob library

**Decision:** `ignorePatterns` entries (both the baseline list and user-configured ones) are matched with simple, hand-rolled semantics: a pattern ending in `/` matches if that name appears as a directory segment anywhere in the file's path (e.g. `"node_modules/"` matches `"packages/a/node_modules/x.js"`); any other pattern matches by exact basename *or* exact full relative path (e.g. `"package-lock.json"` matches both `"package-lock.json"` and `"packages/a/package-lock.json"`). No glob syntax (`*`, `**`, `?`, `[...]`) is supported.

**Reasoning:** The Phase 1 baseline list itself already mixes both shapes (`"package-lock.json"` — a bare filename meant to match wherever it occurs, since lockfiles commonly exist in subdirectories in monorepos — and `"node_modules/"`/`"dist/"` — directory names meant to match at any depth), so the matcher has to support both regardless of what's chosen for user patterns; extending the same two rules to `ignorePatterns` keeps one matching function instead of two. Going further to full glob support would need a dependency (`minimatch`/`picomatch`) or a hand-rolled glob engine, for a phase whose brief (§5.2) only asks for "lockfiles, generated files ... gitignored paths" — patterns that are all expressible as plain names or directory segments — not arbitrary wildcards. This is the same "keep the mechanical layer dumb, no more machinery than the task in front of it needs" reasoning already applied to git access and diff parsing in Phase 2.

**Alternatives considered:** A real glob matcher (`minimatch`) — more powerful and more familiar to anyone who's used `.gitignore`, but adds a dependency for capability nothing in scope currently needs, and glob semantics (especially `**` vs `*`, negation with `!`) have enough edge cases to be worth deferring until a real user actually asks for a pattern the simple matcher can't express. Plain substring matching (pattern matches if it appears anywhere in the path string) — rejected as too loose: a user pattern `"test"` would then also match `"latest.js"` or `"contest/"`, which is a real false-positive risk a basename/segment match doesn't have.

## 2026-08-04 — Filtered-diff recording: extend `captured_diffs`, don't add a new table or touch `events`

**Decision:** `captured_diffs` (introduced in Phase 3) gets two new columns — `filtered INTEGER NOT NULL DEFAULT 0` and `filter_reason TEXT` (nullable) — rather than a new table, and `events` is not touched at all. Every capture gets exactly one `captured_diffs` row regardless of the filter's verdict; a filtered-out diff is `filtered=1, filter_reason=<one of the FilterReason values>`, a passed one is `filtered=0, filter_reason=NULL`. The full original `diff_json` is stored either way — filtering never truncates or rewrites what was actually captured, only annotates it.

**Reasoning:** This directly continues the reasoning already logged in Phase 3's "session-state persistence" entry for why `captured_diffs` exists separately from `events` in the first place: `events` rows represent question/miss *events* under brief §3.5's schema (question text, type, answer, cost) — a mechanically-filtered-out diff was never even considered for a question, so it isn't that, any more than an unfiltered capture was. `captured_diffs`, by contrast, was already defined as "diffs Grasp captured, pending whatever Phase 4/5 eventually does with them" — Phase 4's filter verdict *is* exactly that "what happens next" judgment for the mechanical half, so annotating the existing row is the natural continuation of the table's own stated purpose, not scope creep into it. A new table (e.g. `filtered_diffs`) would just split one capture's lifecycle across two tables for no benefit — every filtered diff is still fundamentally "a `captured_diffs` row," just one that didn't survive the mechanical gate. Storing the full diff regardless of verdict (rather than, say, only storing a summary for filtered-out ones) matches brief §3.5's "local-first, inspectable" stance: a user should be able to look at *exactly* what got filtered and why, not a redacted version of it.

**Alternatives considered:** A separate `filtered_diffs` table — considered and rejected per the "splits one capture's lifecycle in two" reasoning above; it would also need its own FK/index setup duplicating `captured_diffs`' existing shape for no real gain. Reusing `events` with `question_concept`/`question_instance` left `NULL` and a new `miss_reason`-like value for "filtered" — rejected because `events.miss_reason` already has a specific, narrower meaning under brief §3.5 (`error`/`timeout`/`cap_reached` — a *generation* call that was attempted and failed, per §3.3), and overloading it to also mean "never attempted because mechanically filtered" would blur two genuinely different situations behind one field. Silently dropping filtered diffs with no record at all — rejected outright per the task's explicit instruction and brief §3.5's inspectability stance.

## 2026-08-04 — Filter wiring scope: `ClaudeCodeAdapter` only, not `GitDiffAdapter`, this phase

**Decision:** `evaluateCapturedDiff` (the filter itself) is a pure, adapter-agnostic function taking a `CapturedDiff` and a `GraspConfig` — usable by any adapter. Wiring it into actual persistence this phase is done only for `ClaudeCodeAdapter.onChangeDetected`. `GitDiffAdapter.onChangeDetected` stays a no-op, unchanged in behavior from Phase 2/3.

Make `captured_diffs`' `session_id`/`prompt_id` columns nullable to accommodate non-hook-driven captures — rejected because it would weaken the FK relationship to `cc_turns` that Phase 3 deliberately established, for a caller that doesn't exist yet.

## 2026-08-04 — Resolving Phase 3's flagged consequence: cap accounting keys off `session_id` alone, not `(session_id, prompt_id)`

No new hook (`SessionStart`/`SessionEnd`) is required: `session_id` is already present on every `PreToolUse`/`PostToolUse`/`Stop` payload Phase 3 already observed and already stores on every `cc_turns`/`captured_diffs`/`hook_invocations` row — the cumulative-per-`session_id` query Phase 5 needs is `SELECT SUM(cost_usd) FROM events WHERE session_id = ?`, nothing more.

**Reasoning:** Phase 3's flagged entry laid out the fork plainly: key the cap off `(session_id, prompt_id)` (matches `Stop`'s own per-turn granularity, resets every turn) or off `session_id` alone (spans the whole interactive sitting). The only thing missing was a place to *read* `session_id` back off of stored `events` rows for the cumulative-sum query — which is exactly what adding the `events.session_id` column (this phase, item 3) provides. `Stop` continues to fire per-turn and continues to be what triggers presenting whatever's ready (once Phase 7/8 build presentation) — that trigger-timing question and the spend-accounting-boundary question are genuinely separate, and only the latter needed correcting.

**Alternatives considered:** Key the cap off `(session_id, prompt_id)` — rejected per the reasoning above; this is the option Phase 3's flagged entry itself already identified as the one that "wouldn't serve the cap's purpose." Introduce `SessionStart`/`SessionEnd` hooks to get an explicit whole-session boundary distinct from `session_id` alone — unnecessary: `session_id` already uniquely identifies one interactive sitting (or one headless invocation) on its own, per the hook payload's own documented semantics (Phase 3's payload-shape entry); a session-scoped `SUM(...) WHERE session_id = ?` query gets the identical boundary without adding a fourth hook family, its own untested payload shape, and the install/wiring cost that would come with it. A wall-clock or idle-timeout-based session boundary — already rejected once, in the original "Session definition for capping and batching" entry, for inventing presence-detection machinery the brief explicitly defers (Section 4); nothing about resolving this flagged item changes that reasoning.

## 2026-08-04 — Judge+generate prompt and response contract

**Decision:** One prompt (`buildJudgePrompt` in `src/generation.ts`) asks the model, in a single response, to: (1) decide `worthAsking` (boolean); (2) if worth asking, pick exactly one kebab-case `conceptTag` naming the general concept; (3) compare that tag against a list of the developer's already-answered tags *included directly in the prompt text*, and self-censor the concept question if it's already known; (4) return `questionConcept` (nullable) and `questionInstance`. The model is instructed to respond with a single bare JSON object matching `{"worthAsking": boolean, "conceptTag": string|null, "questionConcept": string|null, "questionInstance": string|null}` — no prose, no markdown fence. The diff shown to the model is reconstructed from Phase 4's `significantFiles` only (post-filter), rendered as `File: <path> (<status>, +ins/-del)` followed by each hunk's header and lines verbatim — not the full raw diff text, and not a re-serialized `git diff`-style header block, since the hunk data already carries real diff syntax and the model only needs to read it, not parse `diff --git` boilerplate. Critically, the model's own self-censoring decision is *advisory*, not authoritative: after parsing the response, Grasp independently checks the returned `conceptTag` against `getConceptTagGlobal` and strips the concept question if that tag was already answered, regardless of what the model decided.

**Reasoning:** The brief specifies the *shape* of this decision ("give the model the diff plus the user's concept-tag history and let it decide, in one shot: (a) is this diff worth a question, (b) does it need a concept question or has the user already got it, (c) generate the question(s)") but not the actual prompt text or response schema — that's this phase's own design work, and the task flagged it as expensive to get wrong later, so each sub-choice got a deliberate answer rather than the first thing that came to mind. Passing the already-answered list *in the prompt* (not just checking it after the fact) matters for quality, not just correctness: a model that knows the tag is already covered can write a *better* instance-only question — one that doesn't accidentally lean on unstated concept groundwork — than a model asked to write an instance question in a vacuum and then having its unwritten concept question silently discarded after the fact. But brief §3.2's memoization rule is a stated correctness guarantee for the product ("Grasp should not re-teach a concept the user has already demonstrated understanding of"), not a preference to leave to a single model call's judgment quality — a model can misjudge, hallucinate a tag spelling that doesn't match history, or simply get the self-check wrong under prompt pressure. Enforcing the rule a second time, deterministically, against Grasp's own authoritative DB, costs nothing extra (the tag lookup already exists from Phase 1/3) and makes the guarantee actually hold regardless of model behavior — "trust but verify," with the model doing the creative work and Grasp's own DB as the final arbiter of the one rule that must never be wrong. One concept tag per diff (not a list) keeps the memoization check a simple point lookup and matches the brief's own framing of a diff exercising "the underlying concept" (singular) that just happened, not an open-ended taxonomy walk.

**Alternatives considered:** Let the model decide the concept-question inclusion entirely on its own, with no after-the-fact enforcement — closer to a literal one-shot reading of the brief, but rejected because it makes a stated correctness guarantee (§3.2) contingent on model reliability rather than Grasp's own data, for zero savings (the lookup is already needed for the prompt's history list, or trivially cheap either way). Two separate calls — a judge call, then a conditional generate call only if worth asking — rejected because the brief explicitly frames this as "one smarter call, not two calls," and a second call would double the cost-cap exposure per diff for no benefit the single-call design doesn't already get. Ask the model to return an array of concept tags instead of one — rejected as unnecessary complexity for what the brief itself describes as one concept a diff exercises, and it would turn the memoization check into a multi-tag join instead of a single lookup.

## 2026-08-04 — Malformed/failed response handling: catch-all "error" miss, cost recorded whenever known

**Decision:** Every failure mode in the generation call — the `claude` process failing to spawn or exit cleanly, its stdout not parsing as JSON at all, the outer envelope's `is_error: true`, or the inner `result` text not matching the judge/generate contract (`parseJudgeResponse` returning `null`) — is caught and recorded as a single `events` row with `miss_reason: "error"`, never thrown, never left unlogged. The one exception is the cap-refusal path, which is its own `miss_reason: "cap_reached"` and never invokes the process at all. No timeout is added around the `claude -p` subprocess call itself in this phase. Whenever an envelope was actually obtained from the process (even one that's `is_error: true` or whose `result` doesn't parse), its `total_cost_usd` is still recorded on the miss row; only when the process/outer-JSON step itself fails outright is `cost_usd` left `null` (genuinely unknown, not assumed to be 0).

**Reasoning:** The task is explicit that full retry/timeout/error-taxonomy work is Phase 6's job, but "some baseline 'don't crash on a malformed response' handling belongs here since you can't ship generation code that assumes a perfect response" — so Phase 5's bar is specifically "never crash, never leave a real attempt unlogged," not "correctly classify every failure mode," which is why every distinct failure collapses to the single existing `error` value from brief §3.3's own vocabulary (`error`/`timeout`/`cap_reached`) rather than inventing new ones Phase 6 would then have to reconcile. Recording cost whenever it's known, even on a miss, closes a real gap: without it, a model that returns a well-formed `is_error:false` envelope but garbage `result` text would let a user's real spend climb without the cap ever seeing it (since the cap sums `events.cost_usd`, and a call that "doesn't count" because it failed to parse is still a call the user was actually charged for) — recording it is what keeps the cap honest against exactly the failure mode most likely to repeat if a model is having a bad day. Not adding a timeout here is a deliberate boundary respected, not an oversight: BUILD_PLAN.md's Phase 6 explicitly lists "a defensive timeout on the subprocess call itself" as its own deliverable, and the task for this session says not to build Phase 6 scope beyond the minimal cap-refusal path — so an unbounded (at this layer) subprocess call is the correct, intentional gap for this phase, left for Phase 6 to close.

**Alternatives considered:** Distinguish parse failures from process failures from `is_error` failures with different `miss_reason` values now — rejected as pre-empting Phase 6's own error-taxonomy work with a scheme this phase has no way to validate is the right one (e.g. whether `timeout` should be its own detected case here at all is exactly Phase 6's question to answer, once a real timeout mechanism exists to detect it). Treat malformed/`is_error` responses as `cost_usd: null` (matching the "genuinely unknown" treatment of a total process failure) — rejected because the envelope *did* report a number in that case; discarding a known figure is strictly worse for cap correctness than recording it, even though the question itself was lost. Let a malformed response propagate as a thrown exception up to the hook entrypoint's own outer catch (which already exists per Phase 3's "never crash" hook design) instead of handling it inside `runGeneration` — rejected because that path would skip writing an `events` row entirely, silently losing the record of the attempt (and its cost) rather than degrading gracefully to a logged miss, which is the whole point of brief §3.3's miss-logging requirement.

## 2026-08-04 — Generation subprocess timeout value: 20 seconds

**Decision:** `invokeClaudeJudge`'s `execFileSync` call now sets `timeout: 20_000` (ms) — `GENERATION_TIMEOUT_MS` in `src/generation.ts`.

**Reasoning:** The real constraint is the Phase 5 outer Claude Code hook timeout (45s, `src/init.ts`), inside which the whole `PostToolUse` handler — including this subprocess call *and* Grasp's own cleanup (catching the error, writing the miss row) — has to finish, or the hook process gets killed outright with no `events` row written at all (strictly worse than any miss path, since even a logged miss guarantees a row). 20s leaves a 25-second gap to the 45s ceiling — larger than the timeout value itself — for: (a) Node's own kill-and-throw sequence once the timeout elapses (empirically near-instant, confirmed while testing this phase — see the "timeout detection mechanism" entry below for the same test), (b) `recordMiss`'s single synchronous `better-sqlite3` insert (a local, WAL-mode, single-row write — consistently sub-millisecond in this project's own testing), and (c) normal process/hook wrap-up overhead. That 25s margin is generous by roughly 2 orders of magnitude versus what (a)+(b)+(c) actually need in practice, which is deliberate: the goal isn't the tightest safe value, it's a value where even a heavily loaded or slow machine has no realistic way to blow through the outer ceiling before the miss row is written. Separately, 20s is also a reasonable ceiling for the call's own *legitimate* happy path: a `--max-turns 1`, no-tools judge call reading one diff should typically finish in a few seconds; a call still running at 20s is behaving abnormally regardless of the outer-timeout math, and continuing to wait past that doesn't serve the user.

**Alternatives considered:** A tighter inner timeout (e.g. 10s) — would still work margin-wise, but risks false-timing-out legitimately slow-but-working calls (model under load, larger diffs, network variance) more than the extra margin buys in safety, given 20s vs 45s is already comfortably safe. A looser inner timeout (e.g. 35-40s) — technically still "less than 45," but rejected as cutting the margin too close: it would leave only 5-10s for the kill-and-cleanup sequence, which is still probably enough in practice but removes the deliberate, generous safety factor that protects against exactly the kind of transient slowness (disk contention, GC pause, a loaded dev machine) the margin exists for. Matching the two timeouts more tightly by formula (e.g. inner = outer − 5s) instead of picking an independent round number — considered, but the outer timeout isn't configurable either right now (it's `init.ts`'s own hardcoded constant), so there's no live value to derive from yet; revisit if the outer timeout ever becomes configurable.

## 2026-08-04 — Generation timeout: hardcoded constant, not a `GraspConfig` field

**Decision:** `GENERATION_TIMEOUT_MS` stays a hardcoded constant in `src/generation.ts`, not a new `GraspConfig` field alongside `costCapUsd`/`diffThresholds`/etc.

**Reasoning:** Every existing configurable threshold (`costCapUsd`, `diffThresholds`, `ignorePatterns`, `questionsPerSessionCap`) is a self-contained product/behavior preference — a user can change any one of them in isolation and get exactly the behavior they'd expect, with no coupling to some other value they'd also need to know about. The generation timeout isn't like that: its entire correctness depends on staying safely under the *outer* Claude Code hook timeout (45s, `src/init.ts`), which is itself currently hardcoded and not exposed anywhere the user would see it alongside this one. Exposing the inner timeout as a config knob would let a user set e.g. `generationTimeoutMs: 40000` — perfectly reasonable-looking in isolation — and silently reintroduce the exact "hook kills the process before the miss row can be written" failure this phase exists to close, with no way for the user to know the two numbers were ever related. That's a worse outcome than not offering the knob at all: a setting that looks safe to tune but quietly breaks a guarantee the user has no visibility into.

**Alternatives considered:** Add it to `GraspConfig` for consistency with every other threshold — rejected per the coupling risk above; consistency with the *shape* of other config isn't worth it when this value's safety, unlike the others, depends on a relationship with a second number the user can't see or edit. Add it to `GraspConfig` *and* validate at load time that it's safely less than the outer hook timeout — more defensible, but the outer timeout lives in `init.ts` and is only written to a per-repo `.claude/settings.local.json` at install time, not read back by the config loader anywhere; building that cross-check would be real new plumbing for a knob nothing in this session's scope asked for. Revisit if a real user actually hits legitimately-slow-but-working generation calls that 20s cuts off — that's the concrete signal (per the project's own standing preference for evidence over speculation) that would justify building the knob properly, together with making the outer timeout configurable in tandem rather than in isolation.

## 2026-08-04 — Timeout detection mechanism: `error.code === "ETIMEDOUT"`, verified empirically

**Decision:** A generation-call failure is classified as `miss_reason: "timeout"` specifically when the caught error's `code` property is the string `"ETIMEDOUT"` (`isTimeoutError` in `src/generation.ts`). Every other failure — including ones where `error.signal === "SIGTERM"` — falls through to the existing `"error"` classification.

**Reasoning:** The task explicitly named `error.killed`/`error.signal` as plausible places to check, but rather than assume either was the right one, this was tested directly against this project's actual Node version before writing any detection code: `execFileSync('sleep', ['5'], { timeout: 1000 })` was run and its caught error inspected field-by-field. The result: `error.killed` was `undefined` — **not** `true` as Node's own higher-level docs might suggest for a general "process was killed" case — while `error.code` was reliably `"ETIMEDOUT"` and `error.signal` was `"SIGTERM"`. Relying on `killed` would have meant every real timeout in this Node version silently fell through to the generic `"error"` bucket, defeating the entire point of this phase. `signal === "SIGTERM"` alone was also tested and rejected as the primary check: a companion test confirmed a plain nonzero-exit failure (no timeout at all) reports `signal: null`, so `SIGTERM` specifically *would* have worked as a marker in this instance, but `code === "ETIMEDOUT"` is the more precise, Node-documented signal for exactly this condition (a subprocess killed because `execFileSync`'s own `timeout` option elapsed) rather than an artifact of which signal Node happens to default to for it — code is what to check if the kill signal ever changed (e.g. via `killSignal`).

**Alternatives considered:** `error.killed === true` — rejected outright per the empirical test above; it's `undefined`, not `true`, for this exact scenario in this Node version. `error.signal === "SIGTERM"` as the primary/sole check — considered, since it does empirically distinguish a timeout from a plain nonzero exit in the tests run here, but `code` is the more semantically precise signal (tied to *why* the process was killed, not *how*) and doesn't depend on SIGTERM specifically remaining the default kill signal. A combined check (`code === "ETIMEDOUT" && signal === "SIGTERM"`) — redundant given `code` alone was sufficient and correctly discriminating in every test case run; adding the second condition would only create a way for a genuine timeout to be missed if some environment ever surfaces `ETIMEDOUT` with a different signal value.

## 2026-08-05 — Claude Code hooks do NOT provide interactive TTY access — Phase 7 as originally scoped is not buildable

**Finding:** Hook subprocesses (`PreToolUse`/`PostToolUse`/`Stop` — everything Grasp has run inside through Phase 6) have **no controlling terminal at all**. This is stated directly and unambiguously in Claude Code's official docs (`code.claude.com/docs/en/hooks`, fetched live): *"On macOS and Linux, command hooks run in their own session without a controlling terminal as of v2.1.139. The hook process and any child processes can't open `/dev/tty` or send escape sequences directly to the Claude Code interface."* The docs state directly that *"hooks cannot prompt interactively."* stdin is the JSON payload (already known from Phase 3); stdout/stderr are captured text relayed into Claude Code's own transcript, not a live terminal a user is watching in real time. The only channel for a hook to touch the terminal at all is a narrowly-restricted `terminalSequence` field limited to OSC window-title/bell/notification sequences — explicitly *not* cursor movement, colors, or anything an interactive UI would need. Blocking (`PreToolUse` exit code 2, or JSON `permissionDecision: "deny"`) is confirmed to be a **pass/fail signal Claude Code reads after the hook exits**, not a live session the user interacts with while the hook is running — Claude Code pauses, waits for the hook process to *exit*, and reads its exit code/stdout as the verdict.

**How this was established:** Fetched the official docs live and independently cross-checked the finding with a separate web search pulling from the same docs page plus a third-party detailed hooks guide — both corroborate the "without a controlling terminal" / "can't open /dev/tty" / "cannot prompt interactively" language verbatim. Also re-confirmed (per this task's explicit instruction to re-check, not assume it still holds) that no authenticated live Claude Code CLI is available in this sandboxed environment (`claude auth status` still reports `"loggedIn": false"`, unchanged since Phase 3) — so this finding rests on two independently-corroborated, freshly-fetched documentation sources rather than a live-fire test, which is the same evidentiary standard already used for the hook payload shape in Phase 3.

**Why this breaks Phase 7 as scoped:** BUILD_PLAN.md's Phase 7 describes rendering an `ink` TUI that captures raw keypresses and blocks the hook's own exit until the user answers or explicitly skips, most likely from `Stop` (already wired to `onSessionComplete`). An `ink` app needs a real controlling terminal to put into raw mode and render to — `Stop` (or any hook) has neither: there's no `/dev/tty` to attach to, and stdin is the JSON hook payload, not a live keyboard stream. Building the TUI to run *inside* the hook process the way Phase 7 describes would render nothing the user could see and read nothing the user could type — it wouldn't fail loudly, it would just silently not work, which is worse than not building it at all.

**Decision:** Do not build Phase 7 as originally scoped. Two concrete alternative architectures are proposed to the user rather than picked unilaterally (this is a product-shape decision, not an implementation detail) — see the session report for the options. No TUI code, no `ink` dependency, and no other Phase 7 implementation was written this session; this entry and the report back are the full output of this phase's work so far.

**Alternatives considered (for the finding itself, not the architecture):** Trust the brief's/BUILD_PLAN's original assumption that hooks have terminal access, since it was never explicitly verified in Phases 1-6 — rejected, since the task explicitly requires resolving this before writing TUI code, and every one of Phases 2/3/5/6's own "verify empirically, don't assume" precedents point the same direction. Attempt a live empirical test anyway despite the known auth constraint (e.g. trying to force a `/login` flow) — rejected for the same reasons already logged in Phase 3's payload-shape entry: out of bounds, not what was asked, and risks using the user's account for a side purpose without being asked; in this case also unnecessary, since the documentation is unusually explicit and internally consistent on this specific point (it doesn't just fail to mention TTY access — it explains the exact failure mode of trying to use it, `/dev/tty` writes failing, and provides a narrow escape-sequence-only workaround specifically because direct terminal access isn't available).

## 2026-08-05 — ink version and CommonJS/ESM interop: `ink@5` + `react@18`, loaded via `eval("import(...)")`

**Decision:** `ink@^5.2.1` and `react@^18.3.1` (plus `ink-text-input@^6.0.0` for free-text input) are used for `grasp review`'s TUI. Since these are ESM-only (`"type": "module"`) while the rest of the project stays CommonJS (per the Phase 1 "TypeScript compiler target and module system" decision, unchanged), they're loaded at runtime via `await eval('import("ink")')` — a narrow interop shim confined to the one module that needs it (`src/inkLoader.ts`) — rather than converting the whole project to ESM.

**Reasoning:** Verified empirically before committing to anything, per this project's standing discipline: a plain `await import("ink")` written directly in a `.ts` file compiled under this project's `tsconfig.json` (`"module": "CommonJS"`) gets *downleveled by TypeScript itself* into `Promise.resolve().then(() => require("ink"))` — confirmed by inspecting the emitted JS — which fails at runtime with Node's CJS loader raising `MODULE_NOT_FOUND`/`ERR_REQUIRE_ESM`-class errors, because `require()` cannot load a pure-ESM package synchronously no matter how it's wrapped. Wrapping the same call in `eval('import("ink")')` sidesteps TypeScript's static rewriting entirely (TS doesn't parse the contents of a string literal passed to `eval`), so Node's own runtime module loader receives a genuine dynamic `import()` — confirmed by testing both paths back to back and observing the second one hit Node's *ESM* resolver (`ERR_MODULE_NOT_FOUND`) instead of the CJS one. This is a well-known, narrow workaround for exactly this situation (a CJS TypeScript project needing one ESM-only dependency) and keeps the blast radius to a single loader file, rather than re-opening the Phase 1 module-system decision — which was made for reasons (native `better-sqlite3` CJS addon, shebang-script simplicity) that are still true and unrelated to `ink`. `ink@5`/`react@18` (rather than the current `ink@7`/`react@19`) was picked for peer-dependency stability: `ink@5` only requires `react >=18`, a much more broadly-compatible and battle-tested React major than the `>=19.2.0` `ink@7` demands, and `ink@5` is still a fully current, actively-used major (not the legacy `ink@3` line, which is the *only* other option with native CJS support but is four-plus years stale).

**Alternatives considered:** Convert the whole project to ESM (`"type": "module"`, `"module": "NodeNext"`) — rejected as reopening a settled, still-valid Phase 1 decision for the sake of one new dependency; would also touch every existing file's import style and the `__dirname`-based `readPackageVersion()` logic in `cli.ts` for no benefit unrelated to this phase's actual goal. Pin to `ink@3` (last version with a plain CJS build, `require("ink")` works with no interop shim needed) — rejected as needlessly stale (over four years without updates, missing the Yoga layout engine and general stability work of ink 4/5/6/7) purely to avoid a five-line interop helper. Use Node's newer "require(esm)" support directly (`require("ink")` working natively in-process on very recent Node) — rejected as version-fragile at the time this decision was made: that support had only just landed in recent Node versions and wasn't reliably available across the `engines.node` floor the package committed to at the time (`>=18`, later tightened to `>=22` during the 2026-08-06 Codex fix pass), whereas `eval`-wrapped dynamic `import()` works on any Node version with ESM support at all, well below either floor.

## 2026-08-05 — `ink`/`ink-text-input` type resolution: hand-written ambient declarations, not the packages' own `.d.ts`

**Decision:** `src/ink-ambient.d.ts` hand-declares a narrow `declare module "ink" { ... }` / `declare module "ink-text-input" { ... }` covering only the API surface `grasp review` actually uses (`Box`, `Text`, `render`, `useInput`, `useApp`, the default `TextInput` export, and their prop/option shapes) — rather than importing the packages' real, more complete `.d.ts` files.

Use `// @ts-ignore`/`any` at each ink usage site instead of real types — rejected as strictly worse: no type safety at all for the one new UI surface in the codebase, versus a few dozen lines of narrow, accurate-where-it-matters ambient types.

## 2026-08-05 — `grasp review` query scope: global across all repos, not scoped to the current working directory

## 2026-08-05 — `PreToolUse`/`Stop` gate-check scope: `session_id`, not global or per-turn

**Decision:** Both the `PreToolUse` hard-gate check and the `Stop` `systemMessage` nudge query `getPendingQuestionsForSession` — scoped to the current Claude Code `session_id` — not global across all sessions/repos, and not narrowed to just the current turn (`prompt_id`).

**Reasoning:** `session_id`-scoping (not global) matches the cost cap's own already-established boundary (Phase 5) and, independently, is the only scope that doesn't risk the exact "punishment tool" failure mode brief §3.1 warns about: if hard-gate checked *globally*, an unanswered question left over from a repo touched days ago could block work in a completely unrelated project today — a user would experience that as arbitrary and unfair, not as "teach, don't punish." Scoping to *this* session's own outstanding work is what "next command blocked until answered" (brief §3.1) actually describes — you shouldn't be able to keep telling Claude Code to do more work in the same sitting that produced an unanswered question, but an old question from a different sitting shouldn't reach into today's work at all. Not narrowing further to just the current turn (`prompt_id`) matters too: `Stop` fires once per turn, so if turn 1 generates a question and the user hasn't answered it by turn 2's `PreToolUse`, a turn-scoped check would let them simply move on and never be asked again within that sitting — checking the whole `session_id` (every turn so far) is what makes hard-gate actually mean "must engage before proceeding," not "can dodge by starting a new turn."

**Alternatives considered:** Global scope (any pending question anywhere blocks any tool call anywhere) — rejected per the cross-project-punishment reasoning above. Per-turn (`(session_id, prompt_id)`) scope — rejected because it would let a user escape an unanswered question from an earlier turn simply by continuing to a new one in the same session, undermining hard-gate's actual purpose. Repo-scoped (any pending question for this repo, regardless of session) — considered, since it's a plausible middle ground, but rejected as solving a problem `session_id`-scoping already solves more precisely: two different sessions in the same repo on different days are exactly the kind of "different sitting" hard-gate shouldn't reach across, the same reasoning that ruled out global scope.

## 2026-08-05 — "Syntax-highlighted diff" scope: diff-level (+/-) coloring, not per-language tokenization

**Decision:** `grasp review`'s diff view colors lines by their *diff role* — green for additions, red for deletions, cyan for hunk headers, default/dim for context and file headers — not by language-aware syntax tokenization (keywords, strings, types, etc. individually colored per the file's actual language).

**Reasoning:** Brief §3.4 asks for "syntax-highlighted diffs" without further specification. Diff-role coloring is what the overwhelming majority of real terminal diff tools actually mean by a "colored"/"highlighted" diff (`git diff`'s own default output, `delta`, `diff-so-fancy`, GitHub's diff view before its own optional per-language layer) — it's the legible, load-bearing signal (what was added vs. removed vs. unchanged context) that directly serves the actual goal here: helping the user read and understand a change fast. True per-language tokenization would need either a dependency capable of lexing arbitrary, often-mixed languages across a diff's files (Grasp has no way to know a file's language beyond its extension, and hunks frequently span multiple languages across one multi-file diff) or a much larger hand-rolled effort, for a benefit (keyword/string/type coloring on top of already-clear add/remove coloring) that's real but secondary to the diff-role signal. Given `ink` is already a first-time, non-trivial new dependency this phase, adding a second heavier one for a nice-to-have layer the brief doesn't explicitly require felt like the wrong place to spend that budget.

**Alternatives considered:** Full per-language syntax highlighting via a library (e.g. a terminal-targeted highlighter) — rejected per the reasoning above: real complexity (language detection, multi-language hunks) for a secondary improvement over the already-implemented, genuinely load-bearing diff-role coloring. No coloring at all (plain monochrome text) — rejected outright; that would fail brief §3.4's explicit ask and make a hunk meaningfully harder to scan at a glance, which matters more here than it would in a tool without an active-recall time-pressure angle.

## 2026-08-05 — Skipping any sub-question of a "both" event skips the whole event

**Decision:** In `grasp review`, pressing the skip key (Escape) at any point while working through a `question_type: "both"` event — whether during the concept question or the instance question, even after already typing (but not yet submitting) an answer to the other one — marks the *entire event* skipped. There's no partial state where, say, the concept question is recorded as answered but the instance question is recorded as skipped (or vice versa).

**Reasoning:** This follows directly from the existing schema, not from a new design choice made from scratch: `events` has exactly one `skipped` boolean and one `skip_reason` per row (Phase 1's schema, brief §3.5's own field list), with no equivalent per-sub-question granularity. Redesigning the schema to support a partial-skip state would be a real, non-trivial schema change this phase wasn't asked to make (and BUILD_PLAN.md's Phase 7 scope doesn't call for it either) — so the only choice actually available within the existing schema was how to collapse a partial-skip *interaction* onto the existing binary skipped/answered state, and "the whole event is skipped, whatever was typed for the other sub-question is discarded" is the simplest, least-surprising collapse: it matches what "skip" means everywhere else in the product (an explicit, deliberate act that says "not now," not a selective per-field save).

**Alternatives considered:** Silently persist whatever partial answer text existed at skip time into `answer_concept`/`answer_instance` anyway, while still setting `skipped = 1` — rejected as confusing: a row that's simultaneously `skipped = 1` and has real answer text would misrepresent what actually happened (the user didn't finish answering, they skipped) and would complicate any future logic that treats `skipped` as authoritative for "was this genuinely engaged with." Redesign the schema now to track concept/instance answer-vs-skip independently — rejected as real, unrequested scope growth in a phase whose task explicitly enumerates what to build; worth reconsidering only if real usage of `review` shows partial engagement (answer one, skip the other) is common enough to matter.

## 2026-08-05 — Questions-per-session cap miss-reason: reuse `cap_reached`, not a new value

**Decision:** When `runGeneration` (`src/generation.ts`) skips generation because the session-wide question count already meets `questionsPerSessionCap`, the resulting miss row uses `miss_reason: "cap_reached"` — the same value the cost cap already uses — rather than a new, more specific value (e.g. `"question_cap_reached"`).

**Reasoning:** Brief §3.5 defines exactly three `miss_reason` values (`error`/`timeout`/`cap_reached`), and the task for this phase explicitly warned against inventing a fourth without real justification, since that's schema drift the brief didn't ask for. `cap_reached` was originally written for the cost cap alone, but its plain-English meaning — "a configured limit was hit before generation could run" — describes the question-count cap just as accurately; nothing about the value's name is cost-specific. Distinguishing *which* cap actually fired for a given `cap_reached` row doesn't need a new column or a new enum value at all: it's already fully recoverable after the fact by comparing that session's cumulative `SUM(cost_usd)` against `costCapUsd` and its `question_type IS NOT NULL` count against `questionsPerSessionCap`, both as of that row's `timestamp` (in practice, checking the session's *current* totals is sufficient too, since a cap that was hit stays hit — sessions don't un-spend money or un-ask questions). Both queries are one-liners against data already being recorded for other reasons (`events.cost_usd`, `events.session_id`, `events.question_type`), so the distinction costs nothing extra to reconstruct, and manual verification step 2 for this phase confirms exactly that.

**Alternatives considered:** A new `miss_reason: "question_cap_reached"`, keeping `cap_reached` cost-specific — the most literal reading of "keep them distinguishable," and arguably clearer at a glance without needing to cross-reference other columns. Rejected because it's the kind of schema growth the task explicitly said needed a real justification, and "slightly more convenient to eyeball" isn't one when the same information is one cheap query away — brief §3.5's three-value vocabulary is a deliberately small, closed set, and widening it for a distinction the data already encodes elsewhere trades schema stability for a minor DX convenience. A `miss_reason: "cap_reached"` plus a new nullable `cap_kind` column (`"cost" | "questions"`) — a middle ground that keeps the brief's three values intact while making the distinction a direct column read instead of a derived comparison; rejected as still unrequested schema growth for a distinction that's already reliably derivable, and because it would need its own migration for existing databases for marginal query convenience.

## 2026-08-05 — `grasp review` batch grouping/ordering: by session, not a flat timestamp list

**Decision:** `grasp review`'s pending-question list (`groupForBatchPresentation`, `src/review.ts`) is grouped by `session_id` before rendering: all of one session's pending questions stay adjacent, session-groups themselves are ordered by when each group's earliest question was generated, and questions within a group stay oldest-first (inherited from `getPendingQuestions`' existing timestamp-ASC order — no separate re-sort needed there). Events with a null `session_id` (currently only possible via `debug:seed`) each become their own singleton group rather than being merged with each other or interleaved into a real session's group. The rendered header shows the overall position ("N of M pending") plus, whenever there's more than one question in the current session's group or more than one session in the batch, a session-context line ("session X of Y — question A of B for this session").

**Reasoning:** The task's own framing is "make a real accumulated batch read coherently, not like an arbitrary list" — a flat global timestamp order (what Phase 7 shipped, and what `getPendingQuestions` alone still returns) actively works against that whenever more than one session contributes pending questions: two sessions' questions would end up interleaved by whenever each happened to be generated, forcing the user to mentally context-switch between unrelated diffs every other question instead of working through one coherent unit of related work before moving to the next. Grouping by `session_id` is the natural unit because it's also the boundary every other cap/scope decision in this project already uses (cost cap, question cap, hard-gate check) — reusing it here rather than inventing a different grouping key (e.g. by repo, or by day) keeps "session" as the one consistent notion of "a coherent unit of related work" throughout the whole codebase. Ordering *groups* by earliest-question-in-group (rather than, say, alphabetically by session id, or by group size) preserves the same "oldest first" intuition the flat list already had, just applied one level up — a user working through a real backlog naturally expects to clear older work first. This is presentation logic, not a query concern, so it lives in `review.ts` (which already owns TUI wiring) operating on `getPendingQuestions`' existing global, timestamp-ordered result, rather than pushing a `GROUP BY`/window-function query into `store.ts` — the store's job is still just "give me every pending question," and how that gets organized for one specific presentation surface is `review`'s own concern, matching Phase 7's existing store/UI split.

**Alternatives considered:** A SQL-level `ORDER BY session_id, timestamp` in `getPendingQuestions` itself — simpler (no client-side grouping code), but rejected on two counts: it sorts session groups lexicographically by session-id string rather than by which session's work is actually oldest, which is the wrong "oldest first" for groups even though it's right within a group; and it would hardcode one specific presentation's ordering preference into a store function whose only other caller (the `PreToolUse`/`Stop` hooks' `getPendingQuestionsForSession`, technically a different function, but the same table) has no use for it. Group by repo instead of session — considered since `review`'s own header already prints `event.repo` per question, but rejected because a single session can span work the user cares about together even if it happened to touch more than one repo in one sitting, whereas two unrelated sessions in the *same* repo, days apart, are exactly the kind of thing that shouldn't be forced into one coherent-feeling batch (this mirrors the reasoning in the existing "gate-check scope" entry for why hard-gate uses `session_id`, not repo). No grouping at all, just a richer per-line label (e.g. prefixing each question with a short session id) so the user can visually track session boundaries without actually reordering — rejected as a weaker version of the same idea: it still leaves genuinely related questions scattered through the list by raw timestamp, which is the actual coherence problem being solved here, not just a labeling gap.

## 2026-08-05 — Session-end cost summary: surfaces on `Stop`'s `systemMessage`, combined with the pending-question nudge, 4-decimal formatting

**Decision:** Brief §3.3's "cumulative session spend visible to the user, not just logged" is implemented by extending the existing `Stop` handler (`src/cli.ts`) to also compute `getSessionCostUsd(db, sessionId)` and, whenever it's greater than 0, append a cost-summary sentence (`costSummaryMessage`) to the `systemMessage` — in the same message as the Phase 7 pending-question nudge when both apply, as one combined sentence, not two separate `systemMessage`s or a second hook field. Each half is independently gated: pending-count text appears only if there's a real pending question; cost text appears only if the session has actually spent anything (`> 0`, not merely "cap not yet hit" — a session that captured diffs but never had a passing one, or whose diffs were all filtered out, spent nothing and says nothing). If neither applies, `Stop` emits no `systemMessage` at all, same as before this phase. Cost is formatted to 4 decimal places (`$0.0043 spent...`), not the conventional 2.

**Reasoning:** Given Phase 7's TTY finding (hooks can't render anything interactively), `Stop`'s `systemMessage` is — as already established for the pending-question nudge — the only channel a hook has to say anything to the user at all, so it's the only real candidate for "visible to the user" in brief §3.3's sense; there is no other surface that fires automatically without the user having to remember to run something. Combining into the existing message (rather than adding a second hook output field, which doesn't exist, or firing the nudge and the cost line as separate `Stop` invocations, which isn't possible — `Stop` fires once) is simplest and avoids inventing new hook-output shape for no reason. Gating the cost line on `> 0` rather than always showing it (even as "$0.00 spent") matters because `Stop` fires on *every* turn, including turns where nothing meaningful was captured at all (a pure `Read`/`Grep` turn, or one where every diff was filtered) — showing "$0.00 spent" on every single quiet turn would be exactly the kind of low-signal noise that trains users to stop reading `systemMessage`s altogether, undermining the one channel Grasp has. 4-decimal formatting (rather than the usual 2) is a direct consequence of the numbers involved: `runGeneration`'s own real judge+generate calls cost a fraction of a cent each (see the mock-`claude` verification data from Phase 5/8's own testing, routinely `$0.001`–`$0.003`), so 2-decimal formatting would round the overwhelming majority of real per-session totals to `$0.00` even when real spend happened — defeating the entire point of a spend-transparency line by hiding exactly the number it exists to show.

**Alternatives considered:** A separate, always-present `systemMessage` on every `Stop` regardless of amount (e.g. "$0.00 spent so far") — rejected per the noise reasoning above; a cap/spend-transparency signal that fires constantly regardless of whether there's anything to say trains users to ignore it, which is worse for the brief's actual "spend transparency" goal than only speaking up when there's something to report. A dedicated `grasp cost` (or similar) command the user runs on demand, mirroring `grasp review` — considered, since it would also let a user check spend outside of an active Claude Code turn, but rejected as solving a problem the brief doesn't actually raise (brief §3.3 asks for visibility, not an on-demand ledger view) and as duplicating data `sqlite3 ~/.grasp/history.db` can already answer directly per §3.5's inspectability stance — worth adding later only if a real user asks to check spend outside of `Stop`'s cadence. 2-decimal formatting for conventional-currency-looking output — rejected per the "rounds real spend to zero" reasoning above; correctness of the actual number shown matters more here than matching typical `$X.XX` currency convention.

## 2026-08-05 — Config completeness audit: one real gap found and fixed (`.grasp.json` not baseline-ignored)

**Decision:** Testing `ignorePatterns` end-to-end (not just reading `filter.ts` and assuming it was wired) surfaced a real bug: a repo's own `.grasp.json` — an untracked file sitting in the working tree the moment a user creates one — gets swept into `captureGitDiff`'s union of untracked files (Phase 2's own, still-correct decision) like any other file. Nothing in `BASELINE_IGNORE_PATTERNS` (`src/ignoreBaseline.ts`) excluded it, so in a real test run where `.grasp.json` was the only untracked/changed file with real content, it became the diff's sole "significant file," passed the mechanical filter cleanly, and reached the judge call — which (correctly, given what it was handed) produced a real question about Grasp's own config file rather than anything the AI agent actually did. Fixed by adding `.grasp.json` to `BASELINE_IGNORE_PATTERNS`, matched by exact basename the same way `package-lock.json` and friends already are — confirmed by re-running the exact same scenario post-fix and observing the diff summary correctly contain only the real file that changed.

**Reasoning:** This is precisely the class of gap the phase's own instructions anticipated ("confirm — for real, by testing each one, not by reading the code and assuming"): reading `filter.ts` in isolation gives no signal that `.grasp.json` itself is a plausible diff input, because the bug isn't in the filter's logic (which correctly ignores whatever the baseline list tells it to) but in the baseline list's *content* — an omission only a real end-to-end run against a real repo with a real `.grasp.json` present would surface, since none of Phases 1-8's own verification runs happened to leave an uncommitted `.grasp.json` sitting in a repo at the moment a `PostToolUse` fired. The fix belongs in the baseline list (not the user-configurable `ignorePatterns`) because it's true for every install unconditionally — a user shouldn't have to know to add their own config file to their own ignore list for Grasp to not generate questions about itself, the same reasoning that already put lockfiles and `node_modules/` in the baseline rather than asking every user to add them.

**Alternatives considered:** Exclude `.grasp.json` at the git-diff-capture layer instead of the filter layer (i.e., never let `captureGitDiff` pick it up as an untracked file in the first place) — rejected because Phase 2's untracked-file union is deliberately adapter-agnostic and content-blind (it doesn't know what "Grasp's own config" means, only "files git sees"); teaching the filter layer, which already owns exactly this kind of "files that don't count" judgment for lockfiles/generated paths, keeps the special-casing in one place instead of two. Have `grasp init`/first config-write add `.grasp.json` to the *user's own* `ignorePatterns` array automatically — rejected as solving a universal problem (every install has this file) with a per-repo, user-editable mechanism a user could accidentally remove, when a baseline entry is unconditional and requires no such bookkeeping. Leave it as user-facing guidance ("remember to gitignore your `.grasp.json`") instead of a code fix — considered, since `captureGitDiff`'s untracked-file listing does use `git ls-files --others --exclude-standard` (confirmed by testing: adding `.grasp.json` to a scratch repo's `.gitignore` does stop it appearing in the untracked-file list), so gitignoring it per-repo would in fact have worked. Rejected anyway because it pushes a universal problem (every install has this file, every time) onto per-user diligence a new user has no way to know they need — the same reasoning that already put lockfiles/`node_modules/` in the baseline list rather than expecting every user's own `.gitignore` to cover them; a baseline fix protects every install unconditionally, a documentation-only fix protects only the installs that happened to read and follow it.

## 2026-08-05 — Codex fix pass: checkpoint-based incremental capture (git tree-vs-tree diffing)

**Decision:** `ClaudeCodeAdapter.checkAndCapture()` no longer diffs the working tree against `HEAD` on every `PostToolUse` firing. It now diffs against a per-`(session_id, repo)` checkpoint stored in a new `capture_checkpoints` table (`src/store.ts`), advancing that checkpoint to the current state after every capture. The checkpoint itself is a real git **tree object** built via a throwaway scratch index (`GIT_INDEX_FILE` pointed at a temp file, never the repo's real index) — `writeWorktreeTree()` in `src/adapters/gitDiffCapture.ts` runs `read-tree <base>`, `add -A`, `write-tree` against that scratch index and returns the resulting tree SHA, capturing tracked *and* untracked (non-gitignored) content in one object with no separate untracked-file-union step needed afterward. Two such snapshots are diffed against each other (`captureDiffBetweenTrees`, tree-ish vs tree-ish) using the exact same `git diff --name-status`/`--numstat`/raw invocations `captureGitDiff` already used for `HEAD`-vs-worktree, since git's diff output format is identical either way. The checkpoint baseline for a session+repo is seeded on the *first* hook firing Grasp ever observes for it (any event type — `ClaudeCodeAdapter.ensureCheckpointSeeded()`, called unconditionally at the top of every hook invocation in `cli.ts`, the same place `ensureTurnStarted()` already runs), specifically *before* `PostToolUse`/`checkAndCapture` can ever run — so the very first tool call's own changes are never silently swallowed into "already seen." `events.diff_hash` is now populated as `${fromTreeSha}..${toTreeSha}` — git's own range-diff notation, a real, reproducible identifier — instead of always `NULL`.

**Reasoning:** This directly fixes Codex's #1 critical finding: every `PostToolUse` re-diffing the whole tree against `HEAD` meant two firings with no new work between them produced the same captured diff, the same generated question, and the same charge twice, and could attribute pre-existing uncommitted work (present before the agent's session even started) to the agent. The brief itself (§5.1) describes the fallback capture path as "watch git working-tree state / diff between checkpoints," and Phase 2's own "Git-diff capture: comparison mechanism" entry explicitly flagged this as deferred rather than solved ("there's no poll loop or persistent capture-daemon yet for 'checkpoints' to mean anything... a real checkpoint concept is more naturally Phase 3's problem once hooks define actual event boundaries to checkpoint against") — Phase 3 then built the hook plumbing but never actually closed that loop, which is exactly the gap this fixes now that a real trigger (`PostToolUse`) and a real state-persistence layer (SQLite, already used for `cc_turns`/`captured_diffs`) both exist. The git-tree-object mechanism specifically (rather than a raw file-content snapshot or a plain hash comparison) was chosen after direct empirical testing, not assumption: a naive alternative — `git diff <tree>` against the live worktree — was tried first and found to **misreport untracked files as deleted**, because that form of `git diff` is actually a tree-vs-*index* comparison under the hood (augmented by worktree stat info for paths already in the index), and the real index never has untracked entries regardless of what the checkpoint tree contains. Diffing two independently-built tree snapshots against each other sidesteps the index entirely and was confirmed correct for modifications, additions, deletions, and untracked-file transitions before being wired into the adapter. Building the tree via a scratch `GIT_INDEX_FILE` (not the real index) matters because it's the standard, safe technique for snapshotting a worktree without ever making Grasp's own bookkeeping visible to `git status`/`git commit` — the repo's real index is never touched. Seeding the checkpoint on the *first hook firing of any type* (not lazily inside `checkAndCapture`) matters because `checkAndCapture` only runs on `PostToolUse`, i.e. *after* a tool call already ran; seeding there would bake that first tool call's own work into the "nothing new yet" baseline and silently lose it. In ordinary Claude Code operation `PreToolUse` fires before the first tool call, so seeding unconditionally at the top of every hook (same place `ensureTurnStarted` already runs, itself idempotent) reliably captures the true pre-agent-work state.

**Alternatives considered:** A raw file-content snapshot (e.g. a JSON map of path → content or hash, stored per session+repo) compared by Grasp's own diffing logic — rejected as reinventing git's own diff engine (rename detection, hunk splitting, binary handling) for no benefit over asking git directly, the same reasoning Phase 2 already used to justify shelling out to git rather than hand-rolling diff logic. A simple hash-of-the-cumulative-diff comparison (dedupe only when the *whole* diff-vs-HEAD is byte-identical to last time) — rejected because it only catches the exact "nothing changed at all" case Codex demonstrated; it does nothing for the equally-real "a later small change gets mixed together with every earlier uncommitted change" complaint, since the comparison base (`HEAD`) never moves, so every capture would still include all prior changes, just occasionally deduped as a whole rather than truly incremental. Keying the checkpoint per `(session_id, prompt_id)` (per turn) instead of per `(session_id, repo)` — rejected because a turn boundary isn't a meaningful "already seen" boundary: several tool calls within one turn should each surface only their own new work, and resetting the checkpoint at every turn boundary would reintroduce partial duplication (the first `PostToolUse` of turn 2 would re-report turn 1's tail-end changes if they hadn't been checkpointed yet). Not touching `captureGitDiff`/`GitDiffAdapter` at all — kept as-is deliberately: it backs `debug:capture`, a manual, one-shot "show me everything uncommitted right now" inspection command with no session concept to checkpoint against, and changing its semantics would break that command's actual purpose.

## 2026-08-05 — Codex fix pass: blank-answer submissions rejected, not silently recorded as engagement

**Decision:** In `grasp review` (`src/reviewApp.tsx`), submitting the concept or instance answer prompt with blank/whitespace-only text is now a no-op — the app stays in answering mode, shows a yellow hint ("A blank answer isn't accepted — type something, or press Esc to skip instead."), and does **not** advance state, mark the event answered, or flip any `concept_tags.answered` value. The skip-reason prompt is explicitly exempted from this check and still accepts a blank submission (pressing Enter with no text there still completes a skip with `skip_reason: NULL`) — the reason text is optional per brief §3.1; only the answer text itself must be real.

**Reasoning:** Codex reproduced a real bypass: pressing Enter with nothing typed for both the concept and instance prompts wrote empty strings into `answer_concept`/`answer_instance`, set `skipped = 0`, and flipped the linked `concept_tags.answered` to `1` — permanently marking a concept "learned" globally, across every future repo, with zero actual engagement, and via a path (blank Enter) that's easier to hit than the deliberate skip flow the whole product design (brief §3.1, "never make skipping free") is built around. Blocking submission (rather than routing a blank submission through the skip flow automatically) was chosen because silently reinterpreting "Enter with nothing typed" as an implicit skip is its own kind of surprising behavior — a user who fat-fingers Enter expects nothing to happen, not to have quietly skipped and been asked "why are you skipping?" for an action they didn't consciously take. Simply not submitting, with a visible reason why, keeps the two real actions (answer for real, or press Escape to skip on purpose) exactly as distinct and deliberate as the brief already requires skipping to be.

**Alternatives considered:** Route a blank submission through the existing skip flow instead of blocking it — the task's own suggested alternative; rejected per the "implicit skip via a typo is surprising" reasoning above, and because it would need its own state transition (jumping from "answering the concept question" straight to "skip-reason, already-blank") that reads as a stranger UX than just not submitting. Trim-and-accept (store the trimmed value even if it was originally whitespace-only, i.e. as an empty string) — rejected as identical to the original bug in effect, since an empty string is exactly what was being wrongly accepted before. Show a full validation-error style message permanently (not just while the input is blank) — rejected as unnecessary; the hint only needs to appear when it's actually relevant (current input is blank), which is what the code does by conditioning the hint on `inputValue.trim().length === 0`.

## 2026-08-05 — Codex fix pass: SQLite busy_timeout — an explicit, generous value, and what it does and doesn't close

**Decision:** `openStore()` now explicitly sets `PRAGMA busy_timeout = 10000` (10 seconds), and a real concurrency regression test (`test/concurrency.test.ts`) spawns 8 separate OS processes writing to the same store and asserts every one succeeds with every row landing — not just that the pragma value reads back correctly.

**Reasoning — the finding that shaped this:** Before writing the fix, `better-sqlite3`'s own source (`node_modules/better-sqlite3/lib/database.js`) was checked directly rather than assumed: its `Database` constructor already defaults an internal `timeout` option to `5000`ms whenever the caller doesn't pass one, which Grasp's `new Database(dbPath)` call never did — meaning a 5-second busy-wait was *already* in effect before this fix, contrary to what this project's own earlier comment here claimed ("without a busy timeout, better-sqlite3's default is to fail immediately," which was itself never verified and turned out to be wrong). Given that, the explicit pragma is not "adding retry behavior where none existed" so much as making an already-present-but-implicit 5s default into an intentional, documented, easily-tunable product decision that survives a future `better-sqlite3` major version silently changing its own default — a real, if less dramatic, reason to keep the change. The chosen value (10s, double the pre-existing default) was settled empirically, not picked round-number-style: a concurrency test spawning 8 real child processes against the *same, already-existing* database (`openStore()` called once, single-process, before the workers start — matching how `grasp init` always establishes the DB before any hook can possibly fire, see below) passed 8/8 times at both 5000ms (the pre-existing default) and 10000ms, so 10s was chosen as a modest safety margin for a slower/loaded machine rather than because 5s was observed to be insufficient for the realistic case.

**A real edge case this does NOT reliably close, and why that's an acceptable, logged tradeoff rather than a bug:** The same concurrency test, run instead against a database file that does **not yet exist** — i.e. several processes racing to call `openStore()` for the very first time simultaneously, each trying to switch a brand-new file into WAL mode via `PRAGMA journal_mode = WAL` — still produced occasional `SQLITE_BUSY` ("database is locked") failures (1-2 out of 8 workers, across several runs) even at busy_timeout values as high as 15000ms. Raising the timeout further did not reliably fix this, which points to a different mechanism than ordinary read/write lock contention: the *first* `journal_mode=WAL` switch on a not-yet-WAL database appears not to fully honor the busy-timeout retry loop the way regular statements do (a documented-elsewhere SQLite subtlety around exclusive locks taken during the journal-mode transition itself, confirmed here empirically rather than by citation). This was not chased further with a code fix because it isn't reachable in Grasp's real architecture: the only place a Grasp database file is ever created for the first time is inside `openStore()`, and the only way for *any* hook-triggered process (`grasp internal:hook`) to run at all is for Claude Code to already have Grasp's hooks registered — which only happens after `grasp init` (a single, one-shot, interactive, never-itself-concurrent command) has already run to completion and already called `openStore()` once, alone. By the time concurrent hook firings become possible, the database is guaranteed to already exist in WAL mode; the "N processes racing to create the file simultaneously" scenario this session found is real, but not something Grasp's own architecture can trigger short of a user manually deleting `~/.grasp/history.db` while other Grasp processes happen to be executing at that exact moment — accepted as an out-of-scope, self-inflicted edge case rather than something worth further engineering. `test/concurrency.test.ts` pre-creates the store before spawning workers specifically to test the *reachable* scenario, with a comment explaining why.

**Alternatives considered:** Leave the pre-existing (undocumented, unverified-by-this-project) `better-sqlite3` default alone and add no explicit pragma at all — rejected once the default was actually confirmed to exist, because leaving it implicit means a future reader (or a future dependency upgrade) has no signal that this value is load-bearing; an explicit, commented pragma is strictly more honest about what's actually relied upon. Chase the WAL-creation-race further (e.g. an even larger timeout, or a file-lock-based "only one process may create the DB" guard) — rejected as solving a problem with no real path to occurring given `grasp init`'s architectural guarantee; adding defensive machinery for a scenario that can only happen via manual file deletion mid-session isn't a good use of complexity budget. A single-process-in-process simulation of concurrency (e.g. two `better-sqlite3` handles in one Node process, one holding an open transaction) instead of real spawned processes — considered, since it would be simpler to write, but rejected per the task's own explicit instruction not to "just assert the pragma is set," and because it wouldn't match Codex's actual repro shape (independent OS processes) as faithfully; real child processes are what actually contend for SQLite's file-level lock the way concurrent `grasp` invocations genuinely would.

## 2026-08-05 — Codex fix pass: missing `total_cost_usd` treated as unknown (miss), never coerced to `$0`

**Decision:** `ClaudeEnvelope.totalCostUsd` (`src/generation.ts`) is now `number | null` instead of always `number` — `invokeClaudeJudge` sets it to `null` when the parsed `total_cost_usd` field is missing or not a number, instead of silently defaulting to `0`. `runGeneration` checks this immediately after confirming the envelope isn't already `is_error`: if the cost is `null`, the whole response — even one that would otherwise contain a perfectly well-formed question — is recorded as a `miss_reason: "error"` row with `cost_usd: NULL`, and `parseJudgeResponse` is never even called for it.

**Reasoning:** The prior behavior (`typeof envelope.total_cost_usd === "number" ? envelope.total_cost_usd : 0`) meant a response missing its own cost figure was recorded as a normal, successful, **free** generation — which is a real cap-bypass risk Codex correctly flagged: the cost cap works by summing `events.cost_usd` for a session, and `NULL`/`0` both contribute nothing to that sum, so repeated calls that happen to omit `total_cost_usd` (a malformed/unusual Claude response, not necessarily malicious) could keep generating indefinitely without the cap ever seeing real spend. Discarding the whole response rather than trying to salvage the question while just marking cost unknown was a deliberate choice: brief §3.5's own field list treats `cost_usd` as `NULL` meaning "genuinely unknown," and a response Grasp can't verify the true cost of isn't one it should present to the user as a trustworthy, costed question — this keeps the cap's accounting honest at the cost of occasionally discarding a question that might have been fine, which is the same "never let a suspicious response bypass the cap" posture already established for the `is_error`/malformed-JSON miss paths.

**Alternatives considered:** Keep the question but record `cost_usd: NULL` for that one row — rejected because it would mean cap enforcement quietly stops being accurate the moment any single response is missing its cost, while still showing the user a real question as if nothing were wrong; treating the whole thing as a miss is more conservative and keeps the failure visible (a `miss_reason: "error"` row) rather than silent. Estimate a fallback cost (e.g. the session's average cost-per-call so far) instead of `NULL` — rejected as inventing a number the response never actually reported, which is worse than admitting it's unknown; brief §3.5 already has a vocabulary for "unknown" (`NULL`) and doesn't ask for estimation. Add a fourth `miss_reason` specifically for this case — rejected for the same reason the Phase 8 question-cap entry already gave for not adding a new value: the existing `error` value already means "a response was received but couldn't be trusted/used," which this is, without inventing schema drift the brief didn't ask for.

## 2026-08-05 — Codex fix pass: `grasp init` detects stale hook installs, not just missing ones

**Decision:** `grasp init`'s idempotency check now classifies each of `PreToolUse`/`PostToolUse`/`Stop` into one of three states — no Grasp entry yet ("missing"), a Grasp entry present but structurally different from what a fresh install would write today ("stale"), or already correct — instead of only ever checking "does a Grasp entry exist at all." The confirmation message shows a `before`/`after` for every stale entry, following the same show-then-confirm pattern the original missing-entry install already used, and the prompt becomes "Apply these changes?" (covering both add and update) rather than "Add these hooks?".

**Alternatives considered:** Always silently overwrite any existing Grasp entry with the current desired shape on every `grasp init` run, no diff shown — rejected per the same "trust is load-bearing, show what's changing" reasoning that already governs the missing-entry case (the original "Hook registration mechanics" decision); a user should see a timeout value change just as much as they'd see a wholly new hook being added. Version-stamp the installed config (e.g. embed a schema/version field in the hook entry itself) and compare versions instead of structural equality — rejected as needless indirection: the entries are small and fully known ahead of time (`DESIRED`), so a direct structural comparison is simpler and can't drift out of sync with a separately-maintained version number. Detect staleness but only warn, requiring the user to manually delete and re-run — rejected as not actually fixing the underlying friction problem this fix exists to close; an automatic, confirmed in-place update is what "one command" installation is supposed to mean.

## 2026-08-06 — Atomic checkpoint claiming (fixes overlapping-hooks duplicate capture)

**Decision:** `ClaudeCodeAdapter.checkAndCapture` now performs the entire checkpoint transition — read the previous checkpoint, decide whether there's a real transition, diff, load config, filter, record the capture, advance the checkpoint — inside a single `BEGIN IMMEDIATE` SQLite transaction (`claimTransition`, `src/adapters/claudeCodeAdapter.ts`), using `better-sqlite3`'s `.immediate()` transaction variant. Only the slow part — the actual `claude -p` subprocess call in `runGeneration` — runs after the transaction commits, outside the lock.

**Reasoning:** The previous implementation read the checkpoint, then later wrote the advanced checkpoint, as two separate, non-atomic operations. Two `PostToolUse` hook firings for near-simultaneous tool calls (or, in the reported repro, eight literally-simultaneous ones) could both read the same stale "previous" checkpoint before either had advanced it, so both computed and reported the identical diff, and both went on to call `runGeneration` — the concrete failure the report reproduced: eight hooks, eight captures, eight paid `claude` calls, one real diff. `BEGIN IMMEDIATE` (rather than the default deferred transaction) acquires SQLite's single write lock at the *start* of the transaction, not lazily on first write — so a second process racing this one genuinely blocks until the first commits, rather than merely blocking on its own first write after having already made a decision based on stale data (which a deferred transaction would still allow, since two deferred transactions can both complete their reads before either attempts to write). `busy_timeout` (already set to 10s, `src/store.ts`) governs how long a blocked process waits; given the transaction body is git/fs-local work (no network, no slow subprocess), it clears well within that window even under real contention — proven by the regression test spawning 8 real concurrent OS processes against one checkpoint (`test/checkpointRace.test.ts`).

**Alternatives considered:** An application-level lock file (e.g. `flock` on a sentinel file per session+repo) — rejected as reinventing what SQLite's own locking already does correctly once used properly (`BEGIN IMMEDIATE`), and it would need its own timeout/staleness handling that SQLite's `busy_timeout` already provides for free. A compare-and-swap `UPDATE ... WHERE tree_sha = ?` instead of a transaction — considered, since it avoids holding a lock across the diff/filter/insert work; rejected because on a failed CAS the loser process would still need to decide what to do (retry? silently no-op possibly-incorrectly?), and because it doesn't solve the second real bug this same change needed to fix (see the next entry) — an error partway through still needs the checkpoint write to not have happened, which a transaction gives for free and a bare CAS doesn't. Keeping `runGeneration` inside the transaction too (fully serializing generation calls per session) — rejected: a `claude -p` call can take up to `GENERATION_TIMEOUT_MS` (20s), and holding SQLite's write lock for that long would stall every other concurrent hook firing, including ones for unrelated repos/sessions, for no correctness benefit (the capture is already durably recorded by the time generation runs).

## 2026-08-06 — Config schema validation, and checkpoint-advance ordering (fixes bad-config data loss)

**Decision:** `loadConfig`/`ensureGlobalConfigFile` now validate the *type/enum/range* of every key actually present in a parsed config file (`validateConfigOverride`, `src/config.ts`), throwing the same kind of clear, attributable error already used for malformed JSON — never silently coercing, dropping, or defaulting a bad value. Separately, `checkAndCapture`'s transaction (previous entry) only advances the checkpoint as its LAST step, after `insertCapturedDiff` has already succeeded — so a `loadConfig` throw (or any other failure in that sequence) rolls the whole transaction back and leaves the checkpoint exactly where it was.

**Reasoning:** The report found a config with `"ignorePatterns": "scripts/"` (a string, not an array) crashed the hook deep inside `Array.prototype.some` in `src/filter.ts`, with a raw stack trace — and, because the checkpoint used to advance *before* the async config/filter/generate handler ran (and that handler was invoked as an un-awaited fire-and-forget async call, so its throw surfaced as an unhandled promise rejection that could kill the Node process outright), the diff that triggered the crash was gone for good: a retry after fixing the config only picked up the config fix itself, not the original edit. Two independent problems, two independent fixes: validating at load time turns an obscure downstream `TypeError` into an immediate, specific, fixable error message at the actual source of the mistake (same philosophy already applied to malformed JSON); and reordering the checkpoint advance to be conditional on a successful capture (enforced for free by transaction rollback-on-throw, once the diff/filter/insert/advance sequence lives inside one transaction) means a bad config can no longer discard work — it just gets retried on the next successful hook firing, closing over whatever accumulated in the meantime. Validation is intentionally shallow (type/enum/range per key, not deep semantic checks like "does this ignore pattern match anything") — matching the brief's own "a few lines of error handling, not a subsystem" posture from §3.3's graceful-degradation guidance, applied here to config loading by the same spirit.

**Alternatives considered:** Coerce bad values to their nearest valid default (e.g. a non-array `ignorePatterns` silently becomes `[]`) instead of throwing — rejected: this is exactly the "invalid mode like `hadr` silently treated as soft" failure mode the report separately flagged as bad, and it would hide a real user mistake (a typo'd config) behind behavior that looks like it's working. Validate lazily, only at each individual read site (e.g. inside `evaluateCapturedDiff`) rather than centrally at load time — rejected because it would need duplicating validation logic (or at least validation *awareness*) at every call site that reads a config field, whereas a single load-time gate means every consumer downstream can trust the shape unconditionally, matching how `GraspConfig`'s TypeScript type already promises to every reader.

## 2026-08-06 — Repo-root resolution for config, hard-gate, and `grasp init`

**Decision:** Added `resolveRepoRoot(cwd)` to `src/git.ts` (`git rev-parse --show-toplevel`, falling back to `cwd` itself if it's not inside a git work tree at all). `runInternalHook` (`src/cli.ts`) resolves it once per hook firing from Claude Code's own `cwd` and uses the result — not the raw `cwd` — both to construct `ClaudeCodeAdapter` (so config loading, checkpoint keying, and captured-diff attribution are all repo-root-scoped) and for the `PreToolUse` hard-gate's own `loadConfig` call. `grasp init` and `debug:seed` do the same before writing/reading.

**Reasoning:** The report found that a repo-root `.grasp.json` — including `gateMode: "hard"` — silently stopped applying the moment a Claude Code session's `cwd` was a subdirectory of the repo (e.g. `cd src && claude`), because `loadConfig` only ever looked in the exact directory it was given, never walking up to find the actual repo root. This wasn't a bug in `loadConfig` itself — its Phase 1 design note explicitly deferred upward search until a real repo-root concept existed (`DECISIONS.md`'s original "repo-config-resolution" entry) — but that concept has existed since Phase 2/3 (`src/git.ts` already has real git plumbing), so the deferral's own stated re-entry condition is met. Resolving once in the hook entrypoint (rather than teaching `loadConfig` itself to walk up) keeps `loadConfig`'s existing contract and its own tests (`test/config.test.ts`) unchanged — it still just reads "the directory it's given" — and matches the pattern brief §5.1 already uses for `ClaudeCodeAdapter`: the adapter is what understands "repo" as a git concept, not the generic config loader. This also happens to fix `grasp init` writing to `repo/src/.claude/settings.local.json` instead of the actual repo root when run from a subdirectory, and makes `ClaudeCodeAdapter`'s checkpoint/capture keying stable against a session's `cwd` (which the same hook is otherwise trusting verbatim as an identity key).

**Alternatives considered:** Teach `loadConfig` itself to walk up looking for `.grasp.json` or a `.git` directory — rejected: it would make `loadConfig` implicitly git-aware (a dependency the module doesn't otherwise have), duplicate the git-root-finding logic `resolveRepoRoot` centralizes in `src/git.ts`, and change `loadConfig`'s tested contract (its existing tests assert it only looks in the exact directory passed in) for behavior that's really about *what directory callers should pass*, not about how `loadConfig` searches. Resolve the repo root once per Claude Code session (cached across hook firings) rather than once per firing — rejected as a premature optimization: `git rev-parse --show-toplevel` is a cheap, local operation (no network, small output), and a session's `cwd` is expected to be stable for its lifetime anyway, so the cache would save negligible work while adding a new place for stale state to hide.

## 2026-08-06 — Compact rename numstat parsing

**Decision:** `parseNumstat` (`src/adapters/gitDiffCapture.ts`) now resolves a rename's new path via `resolveNumstatNewPath`, which handles git's compact brace form (`prefix/{old => new}/suffix`) in addition to the full-paths form (`old/path => new/path`) the original naive `pathField.split(" => ")[1]` only covered.

**Reasoning:** `git diff --numstat -M` elides the shared prefix/suffix of a rename's old and new paths into a `{old => new}` fragment whenever they share one (e.g. `src/{rename-source-verbose.ts => rename-target-verbose.ts}`) — this is git's own compaction, not something Grasp controls, and it kicks in for the common case of a rename within the same directory. The naive split on `" => "` only correctly handles the (rarer) case where old and new share nothing, and on the compact form instead returns a malformed fragment (`"rename-target-verbose.ts}"` — trailing brace, missing the directory prefix) that can never match the file's real path from `--name-status`, silently dropping that file's insertion/deletion counts to 0 and making an edited rename look like a no-op change to Phase 4's size filter. Fixed with a regex that expands the brace form back to a real path (`prefix + newPart + suffix`), verified against both `git diff --numstat`'s actual output (confirmed empirically, not assumed) and an end-to-end test through the real tree-vs-tree diff path `ClaudeCodeAdapter` uses (`test/gitDiffCapture.test.ts`).

**Alternatives considered:** Parse the rename's old/new paths from `--name-status` output instead of `--numstat` (name-status already reports full, non-compacted old/new paths for `R`-status entries) and use THAT to key the numstat lookup — rejected: numstat's own path field would still need parsing correctly for the (already-working) non-rename case, and the fix is more contained and easier to verify in isolation by fixing `--numstat`'s own path resolution directly, rather than threading name-status's parsed paths through as an extra input to numstat parsing.

## 2026-08-06 — Generated-file content detection

**Decision:** Added `isFileGenerated` (`src/filter.ts`): a file is excluded (`generated_file` reason) if any of its first 5 added lines match a common "this is generated" marker convention (`auto-generated`, `do not edit`, `code generated by`, `this file is/was automatically generated`, `@generated`), checked case-insensitively. This runs independently of — and in addition to — the existing fixed baseline path list (lockfiles, `dist/`, `build/`, etc.).

**Reasoning:** The README already advertises generated files as excluded, but the only implementation was a small, fixed set of paths/directories — it missed any generated file living somewhere else, e.g. the report's concrete case, a 7-line `src/api.generated.ts` beginning `AUTO-GENERATED FILE. DO NOT EDIT.`, which isn't a lockfile and isn't under `dist/`/`build/`. Checking the file's own declared content (rather than trying to guess from its path/extension) is both more accurate and matches how most real generators actually mark their own output — these header-comment conventions are near-universal across protobuf/gRPC, OpenAPI codegen, ORMs, and plenty of hand-rolled generators. Limiting the check to the first 5 added lines (not the whole diff) keeps it cheap and avoids a false positive from the word "generated" appearing incidentally deep in an otherwise ordinary file — verified with a dedicated test for exactly that case (`test/filter.test.ts`).

**Alternatives considered:** Expand the fixed baseline path list with more filename/extension patterns (`*.generated.ts`, `*_pb.go`, `*.pb.ts`, ...) — rejected: any such list is inherently incomplete and language/tool-specific in a way content-marker detection isn't; a new codegen tool with a new naming convention would need Grasp itself updated to recognize it, whereas content-marker detection generalizes to any generator that follows the (very common) "say so in a header comment" convention without Grasp needing to know about that specific tool at all. Check the WHOLE file's content, not just the first 5 added lines — rejected as unnecessary cost (most real header comments are within the first few lines) and a slightly larger false-positive surface for no real accuracy gain.

## 2026-08-06 — Formatter-reflow detection (line-wrapping) in the formatting-only filter

**Decision:** `isHunkFormattingOnly` (`src/filter.ts`) now falls back to a whitespace-*stripped* (not just whitespace-*normalized*) whole-hunk comparison when the existing per-line comparison fails — so a formatter reflowing one line across several (or several into one), with no actual token change, is still recognized as formatting-only.

**Reasoning:** The existing check normalized each line's internal whitespace and compared the removed/added line arrays element-by-element — correct for reindentation and trailing-whitespace changes, but it requires the SAME NUMBER of lines on each side, so it missed the report's concrete case: a formatter wrapping `return input.trim();` onto two lines. Stripping ALL whitespace (not just collapsing runs) and comparing the flattened character sequences catches this because line-break placement becomes irrelevant once whitespace is gone entirely, while still correctly rejecting a change that adds/removes/changes an actual token (verified with a dedicated "false when reflowed lines also change a token" test). This is deliberately kept as a *fallback*, tried only after the cheaper, already-correct per-line check fails — most formatting-only diffs are same-line-count reindents, and this avoids doing the more expensive/riskier whole-hunk flatten on every hunk.

**Reasoning (accepted tradeoff):** Fully stripping whitespace means a change that only affects whitespace *inside* a token boundary (e.g. `"a  b"` → `"a b"` inside a string literal) would also be misclassified as formatting-only and filtered out before ever reaching a question. Accepted as a rare, low-stakes edge case for what the brief itself scopes as a *mechanical* pre-filter (§5.2) — a real parser/tokenizer per source language would be needed to close this gap precisely, which is a materially larger scope than this filter's stated purpose, and the min-changed-lines threshold already filters out most single-character-level edits like this one anyway regardless of formatting classification.

**Alternatives considered:** Collapse (not eliminate) whitespace runs to a single space when doing the whole-hunk comparison, mimicking `git diff -w`'s actual semantics more closely — considered, since it would correctly reject the `"a  b"` → `"a b"` case above (a run of 2 spaces vs. 1 space would still differ under collapse-not-eliminate, wait: no — collapsing both to a single space would ALSO conflate them, so this doesn't actually close the gap; only preserving whitespace exactly, i.e. not attempting reflow detection at all, would). Kept the simpler full-strip approach since the more "correct" collapse-based variant doesn't meaningfully narrow the accepted tradeoff anyway, for meaningfully more implementation complexity (needing to reconstruct token boundaries at line-break points that a plain string join loses).

## 2026-08-06 — Concept-first enforcement: reject a brand-new concept tag with no concept question

**Decision:** In `runGeneration` (`src/generation.ts`), when the judge model returns `worthAsking: true` for a `conceptTag` that has never been answered before (per `getConceptTagGlobal`), but `questionConcept` is `null` anyway — a direct violation of the response contract the prompt itself specifies — the whole response is now treated as malformed: recorded as an `error` miss (with cost still recorded, since the call still happened and was paid for), never accepted as a successful instance-only question.

**Reasoning:** The prompt (`buildJudgePrompt`) already tells the model the exact rule: `questionConcept` must be null ONLY if the tag is already in the answered list, otherwise it must be a real question. Before this fix, Grasp computed `includeConceptQuestion = questionConcept !== null && !alreadyAnswered` — so if the model got this wrong (returned a brand-new tag with a null `questionConcept`), Grasp silently fell back to treating it as an ordinary "already known" instance-only question, which then gets recorded with a `concept_tags` row for that tag. The moment the user answers the instance question, `markEventAnswered` marks that concept_tags row `answered = 1` — meaning the concept is now permanently memoized as "taught," everywhere, forever, without the concept question ever having been shown. This directly breaks brief §3.2's core teaching mechanism (concept before instance) for exactly the diffs where it matters most: the FIRST time a concept comes up. Every other part of this response contract is already enforced deterministically rather than trusted from the model (the `alreadyAnswered` check itself overrides the model's own claim); this closes the one direction that wasn't.

**Alternatives considered:** Repair the response instead of rejecting it — e.g. synthesize a generic concept question, or fall back to holding the event as pending-concept until a real one can be generated — rejected: fabricating a concept question that wasn't actually judged/generated by the model undermines the "one smart call decides everything" design (brief §3.3) and adds real complexity (a new pending state, a second generation path) for a case that should be rare if the model is behaving reasonably; treating it as a miss is the same "a few lines of error handling, not a subsystem" posture §3.3 already establishes for every other failure mode. Silently drop just the concept tag (record the instance question, but don't memoize the tag at all) — rejected: this still shows the user an instance question about a concept they've never had explained, the exact "unanswerable, pushes straight to frustration" failure §3.2 says a concept question exists to prevent — better to lose the question entirely (same as any other miss) than show a confusing one.

## 2026-08-06 — Stale pending question cutoff for hard-gate blocking

**Decision:** Added `getBlockingPendingQuestionsForSession` (`src/store.ts`), used ONLY by the `PreToolUse` hard-gate check — a pending question only counts as "blocking" if it's both for this `session_id` AND timestamped within the last 24 hours (`HARD_GATE_MAX_AGE_MS`). The existing `getPendingQuestionsForSession` (used by the `Stop` nudge) and `getPendingQuestions` (used by `grasp review`) are unchanged — both still show/count every pending question regardless of age; only what's allowed to actively DENY a tool call is now age-limited.

**Reasoning:** README and `TESTING_GUIDE.md` both explicitly promise hard-gate "never blocks you over something left over from a different day or a different project" — but the actual check only ever scoped by `session_id`, and a Claude Code `session_id` can genuinely be resumed long after it was first used (e.g. `claude --resume`), so session scoping alone doesn't actually deliver on that promise; the report confirmed this by rewriting a pending question's timestamp to the year 2000 and observing hard-gate still denied the (technically-same-session) resumed session. This is a gap the brief itself doesn't settle — it specifies hard-gate should be session-scoped (§3.1, §5.1) but never discusses session age/resumption — so this is Grasp's own conservative choice, not something pinned down elsewhere. 24 hours is deliberately generous: long enough that a same-day session picked back up after lunch, a meeting, or overnight is never spuriously unblocked (which would silently weaken the gate for the exact case it's meant to catch), short enough that a session abandoned and picked up on a genuinely different calendar day reliably falls outside it, matching the documented "different day" framing directly rather than trying to compute exact calendar-day boundaries (which would need timezone handling for arguable benefit).

**Alternatives considered:** Track and compare actual calendar days (local time) instead of a rolling time window — rejected as more complex (needs timezone-aware "start of day" logic) for a distinction that doesn't materially change behavior: a session resumed 3 hours after midnight is "a different day" by calendar-day comparison but is obviously still "the same sitting" in the sense the docs care about, which a rolling window handles more sensibly. Make the cutoff configurable — rejected as unnecessary surface area for a value the brief never asks to be tunable; if real usage shows 24 hours is wrong in either direction, that's a one-line constant change, not a design that needs to ship configurable on day one. Apply the same age limit to the `Stop` nudge and `grasp review` too — rejected: those are purely informational/on-demand (never block anything), so there's no "punish you for old work" failure mode to guard against there, and hiding an old-but-real pending question from `grasp review` would make it harder to ever answer, working against brief §3.1's "never make skipping free" principle by making forgetting free instead.

## 2026-08-06 — Pruned checkpoint objects self-heal instead of failing forever

**Decision:** `isMissingGitObjectError` (`src/git.ts`) detects git's `fatal: bad object <sha>` failure specifically. When `captureDiffBetweenTrees` throws this inside `claimTransition`'s transaction, the checkpoint is re-seeded to the current tree state (same as first-ever seeding) and the transition is reported as unclaimed (no diff), rather than letting the error propagate and leaving the checkpoint permanently stuck.

**Reasoning:** Grasp's checkpoint tree SHAs (`writeWorktreeTree`) are deliberately unreferenced dangling git objects — never committed, never pointed to by any ref — which is exactly what makes them cheap and side-effect-free to create on every hook firing, but also exactly what makes them eligible for reclamation by `git gc`/`git prune`. The report found that after a checkpoint object was pruned, every subsequent hook firing for that session+repo failed identically (`fatal: bad object`) with no capture or event ever recorded again — a permanent breakage from a single external event outside Grasp's control. The prior state genuinely can't be recovered once its git object is gone — there's no diff to compute against nothing — so losing that ONE transition's diff is unavoidable. But there's no reason a single pruned object should break every FUTURE firing too: re-seeding to the current state the moment this is detected means the very next real edit is captured normally, closing the gap to "one lost transition" instead of "capture broken until the user notices and manually intervenes," which better matches brief §3.3's graceful-degradation philosophy (skip and recover, never leave the user stuck).

**Alternatives considered:** Make checkpoint trees reachable (e.g. point a dedicated ref/tag at each one, or a `refs/grasp/checkpoints/<session>-<repo>` namespace) so `git gc` never reclaims them — rejected: it trades a rare, self-healing failure mode for a permanently growing set of refs in the user's own repo that Grasp would then be responsible for cleaning up itself (stale sessions never explicitly "end" from Grasp's perspective), which is a bigger footprint in someone else's repository than the brief's "local-first, inspectable, no surprises" trust posture (§3.5, §8) is comfortable with for a problem `git gc` only rarely triggers in practice. Detect the specific commit/prune event proactively (e.g. a `pre-gc` hook) and warn ahead of time — rejected as solving a problem that only matters at the moment of failure; reactive self-heal costs nothing extra and doesn't require hooking into the user's own git configuration at all.

## 2026-08-06 — Codex fix pass: atomic cap enforcement via per-session generation reservation

**Decision:** Added a `generation_reservations` table (`src/store.ts`, one row per `session_id`, PRIMARY KEY on `session_id`) plus `tryClaimGenerationSlot`/`releaseGenerationSlot`. `runGeneration` (`src/generation.ts`) now claims this session's slot BEFORE reading `getSessionCostUsd`/`getSessionQuestionCount`, holds it through the entire cap-check + `claude -p` call + event-insert sequence, and releases it in a `finally`. A claim attempt against an already-held slot polls (`Atomics.wait`-based synchronous sleep, 100ms interval) for up to `GENERATION_RESERVATION_STALE_MS + 5s`; a reservation older than `GENERATION_RESERVATION_STALE_MS` (45s — comfortably above `GENERATION_TIMEOUT_MS`'s 20s, enforced by an assertion at module load) is treated as abandoned and stolen by the next claimant, so a killed hook process can't permanently wedge a session's generation forever. If the wait budget is exhausted without acquiring, the call is logged as a `timeout` miss (not `cap_reached` — the cap itself was never actually evaluated).

**Reasoning:** An independent test pass (Codex) reproduced a release-blocking bug: `runGeneration`'s cap checks (`spentSoFar >= config.costCapUsd`, `questionsSoFar >= config.questionsPerSessionCap`) read cumulative totals, then made a slow (up to 20s) `claude -p` subprocess call, THEN wrote the result — so any number of overlapping hook processes for the same `session_id` (e.g. several near-simultaneous `PostToolUse` firings, each capturing a different diff) could all read the same pre-call totals, all decide they were under the cap, and all invoke Claude. Reproduced concretely: a 1-question cap let 6 concurrent calls each generate a real question (6 stored events, 0 `cap_reached` rows); a $0.001 cap with 6 concurrent $0.001 calls spent $0.006. This is exactly the failure mode brief §3.3 calls a safety rail ("build the cap before the first real test session"), so it's release-blocking, not cosmetic. Serializing per-session (not globally) closes the race precisely: caps are already a per-`session_id` accounting boundary (see the "Resolving Phase 3's flagged consequence" entry below), so only calls for the SAME session can race the SAME budget — different sessions' calls proceed fully in parallel, unaffected, avoiding the "holding SQLite's write lock across a 20s subprocess call would stall every other repo/session" problem `checkAndCapture`'s own design (see "Checkpoint-based incremental capture" entry) already identified and avoided for the analogous checkpoint-claim case. The reservation claim itself is a fast, single `BEGIN IMMEDIATE` transaction (same pattern as `claimTransition`) — only the FAST claim/release needs the write lock, never the slow external call.

With this fix, at most one caller per session can ever be "in flight" past the cap check at a time, so the worst-case overshoot returns to exactly what the brief and README already document and accept as intentional: the ONE call that was already running when the cap was crossed can land slightly over it (e.g. a $0.25 cap plus one ~$0.002 call landing at $0.252) — not N concurrent calls compounding that overshoot N-fold.

**Alternatives considered:** Reserve an estimated cost up front (before knowing the real `total_cost_usd`) and correct it after the call — rejected: there's no reliable estimate to reserve (`total_cost_usd` varies with prompt/response size and isn't knowable in advance), and an estimate that's too low reopens exactly the race being closed while one that's too high would under-utilize the real cap. Hold SQLite's write lock for the whole check+call+insert sequence in one transaction — rejected outright: identical to a rejected alternative already logged for the checkpoint-claim case, since it would stall every unrelated repo/session's hook firings for up to 20 seconds each time, not just this session's. Add a new `MissReason` value (e.g. `"lock_timeout"`) for a failed slot acquisition — rejected as unnecessary enum growth for a case that's semantically a timeout (waited too long for a resource to free up) and practically unreachable in normal use (would require a claim to be neither released normally nor stolen as stale for 45+ seconds); reusing the existing `"timeout"` value costs nothing and stays accurate.

## 2026-08-06 — Codex fix pass: unknown config keys are rejected, not silently ignored

**Decision:** `validateConfigOverride` (`src/config.ts`) now rejects any top-level key not in `KNOWN_TOP_LEVEL_KEYS` (`gateMode`, `costCapUsd`, `ignorePatterns`, `questionsPerSessionCap`, `diffThresholds`) and any nested `diffThresholds` key not in `KNOWN_DIFF_THRESHOLD_KEYS`, with the same throw-a-clear-error posture already used for wrong-typed known values — including the misspelled key name and a "did you mean" list of the real keys in the error message.

**Reasoning:** An independent test pass found that `"gateMod": "hard"` (a plausible one-letter typo of `gateMode`) loaded successfully, was retained verbatim as inert dead data in the merged config object, and left the real `gateMode` silently at its default (`"soft"`) — the user believes hard-gating is on, Grasp is actually running soft. Fuzzy-match unknown keys to the nearest known one and auto-correct — rejected as too clever for a config file a human is expected to hand-edit and trust literally; silently rewriting what the user wrote reopens exactly the "no surprises" trust concern brief §3.5/§8 cares about, just in the other direction.

## 2026-08-06 — Codex fix pass: generated-file detection is position-in-FILE aware, not position-in-diff

**Decision:** `isFileGenerated` (`src/filter.ts`) no longer checks "the first 5 added lines of the diff, wherever they fall." It now parses each hunk's own `@@ -a,b +c,d @@` header to get that hunk's new-file starting line, walks the hunk tracking each line's real position in the resulting file, and only tests a marker against added lines whose position is within `GENERATED_FILE_HEADER_LINE_LIMIT` (5) lines of the top of the FILE. A hunk whose header start is already past line 5 is skipped entirely, regardless of its content.

**Reasoning:** An independent test pass found a broad false positive: a completely ordinary hunk around line 100 of an existing file, whose first added line was `throw new Error("Do not edit locked state")` — a normal runtime guard, not a generator's header comment — was classified `generated_file`, discarding the whole real change. The bug was a category error: the original implementation checked position-in-the-DIFF (first 5 added lines across whatever hunks happen to be in this particular diff), but the actual convention these markers rely on (protobuf/gRPC, OpenAPI, ORMs, `git` itself) is position-in-the-FILE — a header comment at the top. A diff's first hunk has no necessary relationship to the file's first lines; a single-hunk diff touching line 100 puts that hunk's content in "first 5 added lines of the diff" even though it's nowhere near the file's actual header. Tracking real new-file line numbers via the hunk header (already available, already parsed elsewhere in this codebase for insertion/deletion counts) closes this precisely: the existing `isFileGenerated: true when...auto-generated`/`@generated` tests (whole-new-file hunks starting at line 1) still pass unchanged, and a new regression test pins the exact repro (hunk header `@@ -95,10 +100,10 @@`, marker text in its first added line) to `false`.

**Alternatives considered:** Widen the existing "check first 5 added lines of the diff" to also require the file's `status` be `"added"` (i.e. only ever flag brand-new files) — rejected: real generators also regenerate EXISTING files in place (e.g. re-running `protoc` after editing a `.proto` file touches an already-tracked `.ts` file), so restricting to `status === "added"` would miss the common re-generation case, not just the false positive. Lower the marker check to only the literal first hunk's first line — rejected: still position-in-diff, not position-in-file; a diff with an unrelated earlier hunk before the real header hunk (e.g. two separate hunks in one file, header hunk second) would still miss the real case while a single deep hunk would still false-positive, so it doesn't actually fix the category error, just narrows its symptoms.

## 2026-08-06 — Generated-file marker must appear on a comment/docstring line, not any line

**Decision:** `isFileGenerated` (`src/filter.ts`) now only treats a marker phrase (`DO NOT EDIT`, `@generated`, etc.) as a real generated-file declaration when the added line it appears on is itself a comment or docstring opener — matched via a new `COMMENT_LINE_PATTERN` covering common single-line comment prefixes (`//`, `#`, `--`, `;`, `%`), C-style block-comment delimiters (`/*`, a continuation `*`), HTML/XML (`<!--`), and Python/doc-string triple quotes (`"""`, `'''`). A marker on a line that doesn't open a comment no longer counts, regardless of its position in the file.

**Reasoning:** An independent test pass found that even after a prior pass made the header-window check position-in-FILE aware (only the first 5 lines of the resulting file, not the first 5 added lines of the diff), a genuinely ordinary small file could still false-positive: a 5-line file whose third line was `throw new Error("Do not edit locked state")` — an executable runtime guard, not a generator's header comment — fell within that 5-line window and matched the `do not edit` marker regex against its raw string content. The position-in-file fix closed the "which lines get checked" half of the bug but not the "what counts as a match" half: every generator convention these markers are actually modeled on (protobuf/gRPC, OpenAPI, ORMs, `git` itself) states the declaration in a comment, never in an ordinary string literal or statement. Requiring the matched line to itself be a comment opener directly encodes that convention instead of pattern-matching on phrase content alone, and closes the false positive precisely: `isFileGenerated` returns `false` for the repro case now, while a real header comment (`// Code generated by protoc-gen-ts. DO NOT EDIT.`) still returns `true`.

**Alternatives considered:** Require the marker to be the ONLY content on its line (stripped of comment punctuation) — rejected: real headers often mix marker phrasing with other text on the same line (`// Code generated by protoc-gen-ts. DO NOT EDIT.`), so an exact-line-content match would itself be a new false-negative source. Track actual multi-line block-comment state (open at `/*`, closed at `*/`) instead of a per-line prefix check — rejected as more machinery than a mechanical pre-filter needs; a continuation line inside a block comment conventionally still starts with `*` (already covered by `COMMENT_LINE_PATTERN`), and the marginal case this would additionally catch (a block-comment continuation line with no leading `*`) is rare enough not to justify carrying real lexer state through this function for a heuristic filter that already logs its exclusions and is documented as a heuristic, not a parser (README §"Generated-file and formatting-only detection are heuristics").

## 2026-08-06 — Slot-wait budget bounded by the outer hook timeout, not by reservation staleness alone

**Decision:** `runGeneration` (`src/generation.ts`) now computes a single wall-clock deadline for the ENTIRE call — `TOTAL_CALL_BUDGET_MS` (40s: the 45s outer Claude Code hook timeout `grasp init` installs, minus a 5s safety margin) — and reserves `GENERATION_TIMEOUT_MS` (20s) off the end of it for this call's own `claude -p` attempt, leaving only the remainder as the deadline `acquireGenerationSlot` will actually wait for another overlapping call (same session) to release the mutex. Previously the wait deadline (`SLOT_ACQUIRE_MAX_WAIT_MS`) was sized purely off `GENERATION_RESERVATION_STALE_MS` (45s, so a genuinely abandoned reservation is always eventually reclaimed) with no accounting for the fact that the CALLER still has its own up-to-20s generation call left to run after acquiring the slot.

**Reasoning:** An independent test pass reproduced the resulting failure directly: three overlapping `PostToolUse` hooks for the same session, each backed by a 16s mock `claude` call, finished at roughly 16s/32s/48s under the old serialization — the third would be hard-killed by Claude Code's own 45s hook timeout before it could record anything at all. This is strictly worse than a normal logged miss: capture and checkpoint-advancement happen before generation starts (a deliberate, already-logged tradeoff — see the "narrow process-kill window" entry from an earlier pass), so the killed worker's diff is gone with zero record, not even a `timeout` miss row. That's a self-inflicted version of the exact failure mode brief §3.3 says Grasp must never produce ("never gates the user on nothing" implies "never silently loses a diff with no trace either"), caused by Grasp's own serialization fix (needed to close the cap-enforcement race — see the earlier "Atomic cap enforcement" entry) rather than by anything external. Bounding the wait deadline by the caller's OWN remaining budget instead of by the reservation's staleness window means a caller that can't realistically finish in time gives up early, records a normal `timeout` miss, and exits cleanly well before Claude Code's kill would land — verified directly: rerunning the exact three-worker/16s repro against the fix, all three processes exit by ~32s (well under 45s), with the one caller that couldn't fit in the queue producing a proper `missReason: "timeout"` row instead of being killed with nothing recorded.

**Alternatives considered:** Raise `HOOK_TIMEOUT_SECONDS` in `src/init.ts` instead (e.g. to 90s) to give queued calls more room — rejected: it doesn't fix the underlying issue, only moves the threshold, and a long-enough queue (more overlapping tool calls, or a slower `claude -p` response) reproduces the exact same failure at whatever new ceiling is picked; it also makes every hook — including ones that never touch generation at all — wait longer before Claude Code gives up on a genuinely hung process. Increase `GENERATION_RESERVATION_STALE_MS` margin instead of adding a separate outer-budget concept — rejected: that constant governs a different concern (when a reservation is presumed abandoned by a dead process) and conflating it with "how long should THIS live caller queue behind others" would make both harder to reason about independently. Drop serialization back to a shorter per-call wait and accept the small residual cap-race window instead — rejected: that reopens the release-blocking bug an earlier pass fixed (overlapping calls all reading the same pre-call cost/question totals); the fix here preserves full serialization correctness and only changes how long a queued caller is willing to wait before bailing out gracefully.

## 2026-08-06 — Generation reservation ownership token

**Decision:** `generation_reservations` (`src/store.ts`) gained a `token` column. `tryClaimGenerationSlot` now generates a random token (`crypto.randomUUID()`) on claim and returns it (or `null` if the slot is already held); `releaseGenerationSlot` takes that token as a required parameter and only deletes the row if it still matches — `DELETE ... WHERE session_id = ? AND token = ?`, not the previous unconditional `WHERE session_id = ?`. Existing databases are migrated with an empty-string default `token`, which can never match a real (non-empty) claimer's token, so a pre-migration row can only be cleared by the existing staleness-theft path, never a legitimate release.

**Reasoning:** An independent test pass identified a real (if narrow) race: because the old `releaseGenerationSlot` deleted "whatever row is there for this session_id" unconditionally, a worker that genuinely paused past `GENERATION_RESERVATION_STALE_MS` (machine sleep, process suspension — not just a slow call) and then resumed would find its reservation already stolen by a second worker; the FIRST worker's own release, running in its `finally` block on resume, would then delete the SECOND worker's still-active reservation, letting a third worker claim the slot while the second is genuinely still running and defeating the mutex's entire purpose. Verified directly: claim as worker A, force its claim stale, let worker B steal it, then call worker A's release with A's own (stale) token — the row (still B's) survives; B's own release with B's real token then correctly clears it. A token is the standard, minimal fix for "only the actual current holder may release" — it doesn't change normal-path behavior at all (the common case is claim → use → release by the same call, same token throughout), it only changes what happens in the already-abnormal case a stale claim was stolen out from under a still-running caller.

**Alternatives considered:** Have the claim holder periodically "renew" its reservation (heartbeat) so it's never seen as stale while genuinely still running — rejected as solving a different, narrower problem (a slow-but-alive call) while adding real complexity (a timer/renewal loop in a synchronous, single-threaded call path that has no natural point to interleave one); the token fix instead makes the CONSEQUENCE of a mistaken steal harmless, which covers the heartbeat's case too (a live caller that gets wrongly stolen from still can't have its slot yanked by the original holder's stale release) without needing the call to do anything differently while it runs. Compare `claimed_at` timestamps instead of a random token (only release if `claimed_at` still equals what this caller originally read) — workable but strictly worse: timestamps have coarser resolution and a real (if astronomically unlikely) collision risk if two claims landed in the same instant, where a random UUID has neither concern and costs nothing extra to generate or store.

## 2026-08-06 — Judge prompt explicitly frames the diff as untrusted data

## 2026-08-07 — Codex fix pass: generated-file detection also reads the CURRENT file off disk, not just the diff's added lines

**Decision:** `isFileGenerated` (`src/filter.ts`) now runs two checks and treats a file as generated if either fires: the existing diff-only check (`isFileGeneratedFromDiff`, unchanged — a marker among the diff's own added lines, within the first `GENERATED_FILE_HEADER_LINE_LIMIT` lines of the resulting file, on a comment line), plus a new disk-based check (`isFileGeneratedOnDisk`) that reads up to `HEADER_READ_BYTES` (4096) from the start of the actual file at `<repoRoot>/<file.path>` and checks its first few lines the same way. `evaluateCapturedDiff` now passes `diff.repo` through as the new optional `repoRoot` parameter. The disk read never throws — a missing file, a deleted file, or no `repoRoot` given at all (e.g. existing unit tests that exercise pure diff content with no real file on disk) all just fall back to the diff-only result.

**Reasoning:** An independent test pass found this release-blocking: a file's generated-header comment is written once, by the generator, and then normally stays byte-for-byte unchanged across every later regeneration — only the generated body below it changes. The diff-only check can only ever see a marker when the header itself is part of THIS diff's added lines, which is true exactly once (the moment the file is first added) and false for every subsequent regeneration — the common case a generated-file filter actually needs to handle, per the report's own framing ("Regenerating an existing generated file is the normal case"). Reading the live file directly is the only way to see a header that predates the current diff; the diff object itself has no field for "unchanged file content," so there's no way to answer this question from `CapturedDiff` alone. Kept as an additive OR with the existing diff-only check (rather than replacing it) specifically so every existing test in `filter.test.ts` — which constructs synthetic `DiffFile` fixtures with no corresponding file on disk — keeps passing unchanged: those cases have no `repoRoot` or no real file at that path, so the disk check silently no-ops and the original diff-only logic still decides, exactly as before.

**Alternatives considered:** Require the diff itself to always include the header line as unchanged context (i.e. widen hunk context so headers are always visible even when only the body changed) — rejected as not Grasp's call to make; hunk context is git's own `-U` behavior applied to the *whole* diff capture, not something this one filter function can special-case, and would bloat every diff sent to the judge model for files that never touch the filter at all. Only check the disk file and drop the diff-only path entirely — rejected because it would require every unit test in `filter.test.ts` to be rewritten to write real temp files instead of constructing `DiffFile` objects directly, a much larger, riskier change for no behavioral gain (the two checks are logically OR'd, so keeping both costs nothing at runtime and preserves the cheaper, no-disk-I/O path for the common "already caught by the diff" case). Cap the disk read at exactly 5 lines via streaming instead of a fixed byte buffer — rejected as needless complexity; a flat 4096-byte read comfortably covers 5 lines even for verbose header comments, and reading a bounded prefix (not the whole file) already avoids the real cost concern (a multi-MB generated file).

## 2026-08-07 — Codex fix pass: `internal:hook` no longer runs `ensureInitialized()` ahead of its own error-swallowing dispatch

**Decision:** `main()` (`src/cli.ts`) now branches to `runInternalHook()` immediately, before the `ensureInitialized(process.cwd())` call that every other command still runs first. `runInternalHook()` already does its own initialization (`openStore()` unconditionally, `loadConfig()` where the code path actually needs it) inside its existing all-swallowing `try/catch` — it just needed to never have `ensureInitialized()` run ahead of it and outside that protection.

Move config validation inside `runInternalHook` to happen lazily/best-effort instead of via the shared `ensureInitialized`/`loadConfig` — rejected as unnecessary; `runInternalHook`'s existing code paths already call `loadConfig(repoRoot)` exactly where they need it (the `PreToolUse` gate-mode branch), already inside the protective try/catch — the only bug was the redundant extra call in `main()` ahead of it. Verified with a new regression test (`test/internalHookConfigError.test.ts`) that spawns the real built CLI: `internal:hook` now exits 0 on the exact realistic-typo reproduction (`"gateMod": "hard"`) across `PreToolUse`/`PostToolUse`/`Stop`, while ordinary foreground commands against the same broken config still exit 1 with the clear validation message — proving the fail-loud behavior for real commands didn't regress.

## 2026-08-07 — Generated-file detection: deletion case uses OLD-file line numbers over removed lines

**Decision:** `isFileGeneratedFromDiff` now branches on `file.status === "deleted"`: for a deletion, it walks each hunk's REMOVED lines using OLD-file line numbers (from the hunk header's `-a[,b]` side) and tests the same marker/comment-line rules against them, within the same `GENERATED_FILE_HEADER_LINE_LIMIT`-line window. ## 2026-08-07 — Codex fix pass: formatting-only detection recognizes grouping-parenthesis wraps, but only at a provably-safe boundary

**Decision:** Extended `isHunkFormattingOnly` (`src/filter.ts`) with a third comparison tier, tried only after both the exact per-line match and the existing whitespace-only-stripped match fail. The new tier (`isRedundantExpressionWrap`) recognizes a formatter wrapping the entire trailing expression of a statement in one redundant grouping-parenthesis pair — e.g. `return greet(name);` -> `return (\n  greet(name)\n);` — as formatting-only, but *only* when the inserted `(` immediately follows one of a short, fixed set of safe boundaries (`return`, `throw`, `yield`/`yield*`, `=>`, or a bare/compound assignment `=` that isn't part of `==`/`!=`/`<=`/`>=`) and the matching `)` sits at the very end of the (whitespace-stripped, optional-trailing-`;`-ignored) content. Both orderings (added-wraps-removed and removed-wraps-added, for the rare case a formatter *unwraps* redundant parens) are checked.

**Reasoning:** CODEX_TEST_REPORT.md (2026-08-07, section 2/9) reproduced this live: a pure line-wrap of a `return` expression, adding only grouping parentheses with no token change, was not recognized as formatting-only, reached the Claude judge call, and generated a real paid `$0.006` question — directly contradicting the README's (now-corrected) claim that formatter line-wrapping is recognized. The existing whitespace-stripped fallback only catches reflow that changes *no* characters at all (moving a token onto a new line); it can't catch this because the added parentheses are two extra characters that survive whitespace-stripping. The obvious blanket fix — strip all parentheses from both sides before comparing, same as the existing whitespace-stripping — was considered and rejected as unsafe: parentheses are not always redundant. `a && (b || c)` is not `a && b || c` (verified by hand: with `a=false, b=true, c=true`, the two evaluate to `false` and `true` respectively), and the *only* difference between them, character-for-character once whitespace is stripped, is an inserted paren pair — indistinguishable from a harmless formatter wrap under a blanket strip-and-compare rule. That would trade one bug (an unnecessary question) for a strictly worse one (silently missing a real logic/precedence change with no question and no record of it, since it never touched the size filter after being misclassified formatting-only). The chosen fix is narrower but still closes the reported gap: the specific pattern formatters actually produce when reflowing a `return`/assignment/arrow-body statement is to wrap *everything remaining in the statement* — and wrapping the *entire* remainder of an expression in parens, at a point where nothing to its left binds tighter (a keyword, an arrow, or an assignment operator, none of which have an "outside" precedence to protect), is always semantically redundant regardless of what operators live inside the wrapped span. A binary operator (`&&`, `==`, `+`, etc.) does not qualify as a safe boundary for exactly this reason — its parenthesized operand has real precedence relative to what's *outside* the parens, which the keyword/assignment cases never do.

Verified directly against the report's own reproduction: rebuilt the exact diff (`return \`Hello, ${name}\`;` -> the 3-line grouped-return form) through the real `captureGitDiff` -> `evaluateCapturedDiff` pipeline in a scratch git repo; it now returns `passed: false, reason: "formatting_only"`, so it never reaches `runGeneration`/`claude -p`. A same-shaped edit that also changes the string content still returns `passed: true` (regression check: a real change in the same shape must still surface a question). Added four permanent regression tests to `test/filter.test.ts`: the exact reported return-wrap, an assignment-RHS wrap (generalizing beyond `return`), and two adversarial cases (`a && (b || c)` and `a == (b || c)`, both real precedence changes) confirming the narrow boundary check correctly refuses to classify them as formatting-only.

**Alternatives considered:** Blanket "strip all parentheses, then compare" (rejected above — provably unsafe, demonstrated with the `&&`/`||` counterexample). A real expression parser/AST diff (e.g. via a lightweight JS/TS parser) to determine true semantic equivalence — would handle this and more (reordered object keys, equivalent boolean rewrites, etc.) correctly and generally, but brief §5.2/§3.3 and this file's own "Flagged-pattern filtering" entry already establish that Phase 4 is deliberately a cheap, mechanical, language-agnostic pre-filter with real semantic judgment left to the Phase 5 model call; a real parser is also inherently language-specific (this codebase's own diffs span TS, JS, JSON, Markdown, shell), which cuts against a filter meant to work across arbitrary repos. Restricting the safe-boundary list even further (e.g. `return` only, since that's the literal reported case) — rejected as needlessly narrow: the assignment and arrow-body cases share the exact same safety argument (nothing binds to the left of the wrapped span) and are at least as common a formatter behavior as wrapping a `return`, so excluding them would leave an easily-closable, equally-safe gap in place for no benefit.

## 2026-08-07 — Hunk-line `+++`/`---` false-positive fix (formatting-only misclassification)

**Decision:** Removed the `&& !line.startsWith("+++")` / `&& !line.startsWith("---")` guards from every place in `src/filter.ts` (`isFileGeneratedFromDiff`, `normalizedRemovedLines`, `normalizedAddedLines`) and `src/adapters/gitDiffCapture.ts` (`countInsertions`) that filtered a hunk's own added/removed body lines. These guards were meant to skip diff *file-header* lines ("`--- a/file`" / "`+++ b/file`"), but `DiffHunk.lines` (populated by `extractHunks` in `gitDiffCapture.ts`) never contains those header lines in the first place — `extractHunks` only starts collecting into `current.lines` after it has already seen the hunk's own `@@ ... @@` line, and the file-header lines always precede the first `@@` in a git diff chunk. The guards were therefore dead code for their intended purpose, but not harmless: a hunk body line whose own source content starts with `--` or `++` (e.g. `--a;` decremented to `++a;`) becomes, after the diff's single-character `-`/`+` marker is prepended, a line starting with the literal string `---`/`+++` — indistinguishable by this check from a real header line. `isHunkFormattingOnly` (which calls `normalizedRemovedLines`/`normalizedAddedLines`) would then see both sides reduced to empty arrays and misclassify a genuine logic change (decrement -> increment) as formatting-only, silently dropping it before it ever reached the filter's size thresholds or Phase 5's judge call. Reproduced exactly as CODEX_TEST_REPORT.md described (`--a;`/`--b;`/`--c;` -> `++a;`/`++b;`/`++c;`) via `grasp debug:capture` before the fix (`FILTERED — reason: formatting_only`) and confirmed the same repro now returns `PASSED` after removing the guards, plus added a regression test (`test/filter.test.ts`) covering the exact scenario.

**Reasoning:** This is a straightforward correctness bug, not a design choice with more than one reasonable resolution — the guards can only ever fire on data they were never meant to match (real hunk-body content), since the data they were actually meant to match (file headers) structurally cannot appear in this field. Deleting the incorrect condition is the only change that both fixes the false positive and keeps the code's own stated intent (skip file-header lines, which don't exist here) honest — keeping some narrower version of the check (e.g. requiring a following space, `"+++ "` vs `"+++"`) would still be solving a problem that doesn't exist in this data shape, and would reintroduce the same risk the moment a real hunk line's content happened to match whatever narrower pattern was chosen.

**Alternatives considered:** Narrow the guard instead of removing it (e.g. match `"+++ "` with a trailing space, since real file headers are always `"+++ b/path"` with a space) — considered but rejected: it still encodes a check against a case (`DiffHunk.lines` containing a real file-header line) that cannot happen given how `extractHunks` populates that field, so it would be defending against a phantom while adding a false sense of one more edge case handled. Better to remove logic that has no reachable legitimate purpose than to make it merely less likely to misfire.

## 2026-08-07 — Review diff view: line wrapping instead of truncation

**Decision:** In `grasp review`'s diff panel (`src/reviewApp.tsx`), long diff lines are now hard-wrapped to the box's actual content width (terminal columns minus the round-border/padding chrome) *before* being handed to ink, with each wrapped chunk becoming its own entry in the already-existing `RenderLine[]` array that the up/down scroll pagination counts against. `<Text wrap="truncate-end">` (which silently dropped everything past the terminal width, with no way to reveal it) is gone entirely — every character of every line is now guaranteed to be on screen somewhere, just possibly split across more than one visual row. `scrollOffset` is also now clamped in a `useEffect` keyed on `[lines, maxDiffRows]`, so a terminal resize (which changes both the wrap width and the row-per-logical-line count) can't leave scroll position pointing past the end of the (now different-length) rendered list.

**Reasoning:** CODEX_TEST_REPORT.md's section 5 reproduced a real usability bug: `wrap="truncate-end"` plus up/down-only scrolling meant a line's hidden tail was permanently unreachable — the report's own example (long validation conditions, a long thrown error message) is exactly the kind of content a real diff line contains regularly, and Grasp's whole premise is asking the user to explain code it's simultaneously hiding from them. Pre-wrapping into discrete `RenderLine` rows (rather than leaving wrapping to ink's own `<Text wrap="wrap">`) was chosen specifically so the scroll math stays exact: `maxDiffRows` is a row budget, and the existing pagination (`hasMoreAbove`/`hasMoreBelow`, `scrollOffset` clamping) already assumes one array entry equals one rendered terminal row. If wrapping happened inside ink instead, a single long logical line could silently consume 2-3 terminal rows that the row-counting pagination logic has no visibility into, breaking the "N more lines below" count and letting scrolled content run off the bottom of the visible box. Verified by reproducing the report's own scenario: seeded an event with a long condition and a long thrown-error message, ran `grasp review` inside an 80-column pty, and confirmed both lines now render in full (wrapped across two rows each, reassembling byte-for-byte to the original line) with no `…` truncation anywhere in the captured output.

**Alternatives considered:** Keep truncation but add real left/right horizontal scrolling (matching what the report's phrasing might imply "reveal the hidden end of a line" most literally) — rejected as meaningfully more UI-state complexity (a second scroll axis, per-line vs whole-box horizontal offset, extra keybindings to document) for a worse reading experience than wrapping: a user would have to scroll sideways through every long line one at a time rather than just reading top-to-bottom, which is a strictly worse fit for "read this diff and answer a question about it." Rely on ink's built-in `<Text wrap="wrap">` without pre-computing wrapped rows — simpler (delete a prop, done) but rejected because it decouples the row-budget math (`maxDiffRows`, scroll-offset clamping, the "N more lines" indicators) from what's actually rendered, silently breaking pagination accuracy exactly when it matters most (files with several long lines).

## 2026-08-08 — `grasp review` input bugs: root cause and fix (immediate focus, working scroll, no premature blank warning)

**Decision:** Removed `QuestionScreen`'s `mode: "viewing" | "answering"` state entirely from `src/reviewApp.tsx`. `TextInput` is now unconditionally rendered and focused from the moment a question mounts, and there is a single, always-active, `useCallback`-memoized `useInput` handler (`handleGlobalInput`) covering Escape (-> skip-reason) and up/down-arrow scroll, coexisting with `TextInput`'s own separate `useInput` registration on the same underlying stdin listener. A new `blankSubmitAttempted` boolean (cleared whenever the user starts typing again, set only by a real Enter-on-blank submit) replaces the old "warn whenever the field is currently empty" check, so the blank-answer warning only ever appears after an actual rejected submit. The `'j'`/`'k'` scroll shortcuts from the old viewing-mode handler were dropped (not reassigned) since a handler that's active while a text field is also live can't safely treat ordinary letters as hotkeys.

**Reasoning:** A real dogfooding session reported three symptoms in the same input step: (1) the footer claimed `[↑/↓] scroll diff` but scrolling did nothing, (2) typing did nothing until the user pressed Enter once first, (3) after that, a correct-but-confusingly-reachable blank-answer rejection. All three traced to one root cause each, confirmed by reading source rather than guessing: (2) was the old `mode` state itself — `TextInput` was only rendered once `mode === "answering"`, which only happened after an explicit Enter/'a' keypress in viewing mode, so the very first keypress was consumed just switching modes rather than reaching the input. (1) was `useInput`'s own re-subscription behavior (confirmed in `node_modules/ink/build/hooks/use-input.js`: the listener effect's dependency array includes the handler reference itself) combined with the pre-fix code passing a fresh inline arrow function on every render — every re-render (including ones caused by a keystroke) tore down and re-added the stdin listener, dropping keys that arrived in that window; reproduced empirically pre-fix (5 down-arrow presses 150ms apart registered only 2 scroll steps) and confirmed fixed by `useCallback`-memoizing the handler with a stable dependency list. (3) was that the old blank-warning condition was `inputValue === ""`, true both "user hasn't typed yet" and "user tried to submit blank" — conflating a passive state with an event. Removing the mode split fixes (2) directly, memoizing the handler fixes (1), and tracking a dedicated `blankSubmitAttempted` flag fixes (3) without touching the (already-correct) underlying rejection logic. Coexistence of `TextInput`'s own listener and the new global handler on the same shared event emitter was verified safe by reading `node_modules/ink-text-input/build/index.js`: its internal `useInput` explicitly returns early (ignores) on up/down-arrow, ctrl+c, and tab, so it never competes with the global handler for those keys, and `EventEmitter.on()` semantics mean both listeners simply both receive every keypress independently — not a fragile assumption, an already-established pattern this codebase's own prior comments (now removed with the mode split) relied on for Escape.

Verified with 4 new pty-driven regression tests in `test/reviewAppPty.test.ts` (see that file's own header comment for why a real pseudo-terminal — not `child_process.spawn`'s plain pipes — is required to catch this class of bug at all: ink's raw-mode input handling behaves differently, or not at all, outside a real TTY): typing immediately on question mount with no prior keypress; up/down arrow scroll actually changing the visible window after the user has already started typing (not just from a pristine, just-rendered screen — the earlier, weaker version of this test passed on both old and new code because old code's scroll only ever broke once "answering" mode was entered); no blank-warning before any submit attempt; and blank-Enter-then-real-answer still working end to end. Each of the 4 was confirmed to fail against the pre-fix code (the last-committed `src/reviewApp.tsx`, i.e. `git show HEAD:src/reviewApp.tsx` prior to this session's uncommitted fix) and pass reliably (2 consecutive full runs, no flakes) against the fix.

Checked whether the same root cause reaches the skip-reason phase, per this task's instruction to flag rather than silently expand scope: it doesn't need a separate fix. The mode split that caused (2) was never phase-gated to begin with — removing it entirely means `TextInput` and the single global handler are active in all three phases (`concept`/`instance`/`skip-reason`) uniformly, so skip-reason already gets the same immediate-focus and working-scroll behavior as a side effect of the fix, with no additional gap found.

A secondary, purely test-infrastructure finding surfaced while building the scroll regression test, logged here since it isn't specific to this fix and could bite future pty-based tests: raw pty writes do not preserve message boundaries on the read side. Sending "typed text" as several separate `send` steps with deliberate sleep delays between each character, followed by an arrow-key escape sequence, was still observed (via direct debug tracing added to the handler) to sometimes coalesce the tail of the typed text with the arrow key into one unrecognized `'data'` chunk (e.g. `input="art\x1b[B"`, which ink's single-regex `parse-keypress.js` doesn't parse into two keypresses) — a sleep-based delay, however generous, is a guess, not a guarantee. The fix was to replace timing-based pacing with `wait_for`-based confirmation: send the typed text as one `send` step (ink treats any multi-character `input` as a single paste event by design, per its own documented behavior, so this doesn't misrepresent real usage), then `wait_for` that exact text to actually appear in the rendered output before sending the next input — closing the race by construction instead of by guessing a delay is long enough.

**Alternatives considered:** Keep the `viewing`/`answering` mode split but auto-transition into "answering" on mount instead of removing it — rejected because it keeps two states doing the job of one and leaves the same class of bug (a mode gate blocking input) available to reintroduce by accident later; deleting the state entirely removes the failure mode rather than papering over one instance of it. Keep `'j'`/`'k'` as scroll shortcuts alongside the arrow keys — rejected because they were only ever safe in the old design's viewing-only mode where no text field could consume ordinary letters; with the field always live, treating 'j' as a hotkey would silently eat that letter out of anyone's typed answer. Debounce/throttle the stdin handler instead of memoizing it — would have masked the listener-churn symptom without fixing the actual defect (a stale handler reference on every render), and would still drop the *first* keystroke in any burst rather than none. For the flaky scroll test: keep sending individual keystrokes with longer sleeps and hope the gaps are wide enough — rejected as the same fragile "guess a big enough number" approach that had already failed twice at different delay values during actual investigation; a `wait_for`-confirmed synchronization point has no timing constant to eventually get unlucky with.

## 2026-08-08 — `grasp review`: explain-then-retry skip flow, per-phase disposition, and legacy fallback

**Decision:** Replaced the old immediate "why are you skipping?" free-text prompt on Escape with a six-phase state machine in `reviewApp.tsx`'s `QuestionScreen`: `"concept"` / `"instance"` (the two answerable questions, unchanged in spirit), each paired with its own `"-explain"` phase (shows the event's one shared `conceptExplanation`, offers exactly one retry at that same question) and `"-reveal"` phase (shows that question's own sample answer — reached either after a real answer or after a terminal decline — "press any key to continue"). Per-question, not a single shared/generic phase name, because the explain/reveal CONTENT and the "which question does continuing return to" logic both genuinely differ by which question is active; a shared name would need a separate side-variable to disambiguate what a distinct phase name already encodes directly in the state itself. The concept and instance phases resolve independently now: `markConceptAnswered`/`markInstanceAnswered` (new, granular `store.ts` functions) are called the moment EACH phase concludes with a real answer — not just once at the very end — so a concept answered for real on a retry stays recorded and the concept tag stays marked learned even if the instance phase is later declined. `markEventSkipped` (simplified to take no reason — see below) is called once, only when the instance phase — always the last phase, since every real question always has an instance question — is declined for good; this is the sole thing that flips the whole event's `skipped` column, matching the pre-existing "one `skipped` flag per event" schema shape without needing to change it. Legacy fallback (pre-migration rows, all three new columns NULL): Escape skips straight past a phase with no `conceptExplanation` to show — the pre-existing immediate-skip behavior, verbatim, no retry ever offered — and a `-reveal` step is skipped silently whenever that phase's own sample answer is NULL, independently per phase (a legacy row could theoretically have one field but not another; each check is its own `if`, not a single all-or-nothing legacy flag).

**Reasoning:** Splitting concept/instance disposition tracking, rather than keeping one "was this whole event answered" outcome, is what actually implements the task's explicit rule that concept-tag memoization tracks "did THIS question get a real answer" independent of what happens to the other one — without it, a user who genuinely explains their understanding of the concept on a retry, then legitimately can't yet connect it to this specific diff and declines the instance question, would lose credit for the concept they DID demonstrate, which is a worse outcome than the status quo this feature is meant to improve. Tying `skipped` to the instance phase specifically (not a new three-state disposition column) works because the schema's existing invariant — `answer_instance IS NULL` is exactly what `getPendingQuestions`'s own `PENDING_QUESTION_WHERE` already relies on to mean "still pending" — is preserved automatically: an event only ever leaves pending state via the instance phase concluding one way or the other, so `skipped`'s existing single-flag meaning ("the instance phase, and therefore the whole event, was never really finished with a real answer") still holds without redefinition. The explain-then-retry design itself (rather than an immediate skip, or a free-text "why" prompt) is what the task specified; the reveal-after-every-conclusion symmetry (answered OR terminally-declined, both show a reveal step if available) was this session's own extension of that spec, justified by the spec's own explicit "the user should never leave a question without having seen at least the reference answer" line for the declined-instance case — applying that same principle uniformly to a declined concept, rather than only to the literal case the spec's prose happened to describe, avoids an arbitrary inconsistency where the concept phase's decline is treated differently from the instance phase's for no functional reason. New render states (explain/reveal) deliberately do NOT render `TextInput` — unlike the prior session's "immediate focus" fix, which was specifically about not gating the ANSWER FIELD itself behind a hidden mode, these are genuinely non-input "press any key" screens, not a text-collection UI with an extra keypress required first; `handleGlobalInput` stays the single memoized `useInput` handler throughout (no new hook, no new listener), so the actual bug class that fix addressed (listener churn from an unmemoized handler) has nothing new to regress. Arrow keys still scroll (not treated as "continue") on explain/reveal screens specifically so a user can scroll back up to re-read the diff while reading an explanation or sample answer, matching how scrolling already behaves during the answering phases — treating literally every key including arrows as "continue" would have been simpler code but a strictly worse reading experience for exactly the moment (stuck, or double-checking an answer) this feature exists to help with.

Verified with 4 new pty-driven tests in `test/reviewAppPty.test.ts`: a real concept answer reveals its sample answer before advancing to the instance phase; Escape-explain-retry-real-answer marks the concept tag answered (checked directly against `concept_tags`) and still shows the sample answer; declining both attempts on both phases (concept AND instance) records the event skipped, leaves the concept tag unanswered, and still shows each phase's sample answer before advancing/closing; a legacy event (all three columns genuinely NULL, not just empty strings) reviews without error and never renders a broken/blank explain or reveal screen. All 4 were confirmed to fail against the pre-feature code (checked by reverting `src/` to `HEAD` while keeping the new tests in place — the new tests don't even type-check against the old `EventRecord`/`JudgeResponse` shapes, let alone pass at runtime) and pass reliably (2 consecutive full runs, no flakes) against the feature. A pty-testing-methodology note surfaced while writing these: the pty driver's captured-output buffer accumulates for a whole test run and never resets, so `wait_for` on a string that's genuinely repeated within one run (the shared explain-screen heading, or the one `conceptExplanation` text reused across both phases by design) can pass immediately on an earlier occurrence rather than actually waiting for a later one — those specific transitions use a plain `sleep` (0.3-0.4s) instead, which is safe here since Escape/Enter are each a single byte, unlike the prior session's multi-byte-arrow-after-bulk-typed-text case that genuinely needed `wait_for`-based synchronization to dodge OS-level input coalescing.

**Alternatives considered:** Keep a single "why are you skipping?" free-text prompt alongside the new explain/retry flow (asking both) — rejected because the task was explicit that the free-text prompt is removed, not supplemented, and stacking both would mean two separate "extra step before this event closes" interruptions instead of one coherent one. A generic shared `"explain"`/`"reveal"` phase name with a separate `activeQuestion: "concept" | "instance"` variable, instead of six distinct phase values — considered as marginally fewer enum values, but rejected because it reintroduces exactly the kind of "one piece of state can't fully describe what's currently rendering" ambiguity a phase-based design exists to avoid; six explicit values keep every render/transition decision a simple switch on one variable. Treat a declined-twice concept phase as skipping straight to the end of the WHOLE event (matching the older, simpler mental model of "skip = done") rather than continuing on to the instance phase — rejected as directly contradicting the task's own point 6 example ("if the user skips the concept question... then LATER ALSO skips the instance question"), which only makes sense if declining concept doesn't end the event early. A single combined "was this event answered or skipped" boolean/enum outcome instead of two independently-nullable `conceptAnswer`/`instanceAnswer` fields on `ReviewOutcome` — rejected because it can't actually represent the real "concept answered, instance declined" mixed state this design explicitly needs to support; two independently-null fields are the minimal shape that can.

## 2026-08-08 — `grasp review` defaults to the current repo, `--all` restores the old global view

**Decision:** Reverses the 2026-08-05 "`grasp review` query scope: global across all repos" entry. `runReview()` now resolves the current repo root via `resolveRepoRoot(process.cwd())` (the same helper `grasp init`/`internal:hook` already use, not a second implementation) and, by default, passes it to `getPendingQuestions(db, repoRoot)`, which now takes an optional `repoRoot` and adds a plain `WHERE repo = ?` condition on top of the existing `PENDING_QUESTION_WHERE` definition — the "what counts as pending" logic itself is completely untouched. `grasp review --all` passes no `repoRoot`, reproducing the old global query byte-for-byte (`getPendingQuestions(db)` with no second argument behaves exactly as it always did). Concept-tag memoization (`concept_tags`, looked up globally by tag in `runGeneration`) is explicitly out of scope and unchanged — this only narrows what a review *batch* shows, not what counts as *learned*; a concept answered in one repo still counts as answered everywhere.

**Reasoning:** The prior entry's reasoning was internally consistent but got outrun by a real dogfooding session: a user working in one small test repo ran `grasp review` and was served a pile of unrelated leftover pending questions from entirely different repos (in that case, this very build's own past manual-verification scratch repos), with no indication they weren't about the repo the user was actually sitting in. The old entry treated "each question labels its own `repo`" as sufficient disambiguation, but in practice a wall of differently-repo'd questions reads as noise, not as a clearly-scoped inbox — the failure mode it was trying to avoid ("losing track of a pending question in a repo you're not currently in") turned out to be less costly in practice than the failure mode it created (a user unable to tell, at a glance, whether what's in front of them is even relevant to what they're doing right now). Scoping by default without discarding the global view entirely resolves both: the common case (someone sitting in one repo, wanting to know what's pending *here*) gets a focused batch, and `--all` is one flag away for the cross-project sweep the old default optimized for. Repo-scoping reuses the event's existing `repo` column (already the exact field the earlier dogfooding session used to *diagnose* the mixing problem) rather than adding any new schema — the fix is a filter on data already being recorded correctly, not a data-model gap.

**Alternatives considered:** Keep the global default and only add `--repo`/`--mine` as an opt-in narrower view — rejected because it inverts the actual usage pattern the dogfooding session revealed: the common case is "what's pending in the repo I'm sitting in right now," so that should be the zero-flag path, with the less common "show me everything" case behind a flag instead. A config-file toggle (`.grasp.json`'s `reviewScope: "repo" | "global"`) instead of a CLI flag — rejected as heavier than the problem needs; a single boolean the user reaches for occasionally (when they actually want the full sweep) doesn't justify a persistent per-repo setting, and a flag is discoverable in `--help` in a way a config key isn't. Silently dropping the global view entirely (no `--all` at all) — rejected because the old default's own reasoning wasn't wrong so much as incomplete: someone genuinely working across many repos in one sitting still has a real use for the full picture, and removing it outright would just trade one transparency gap for another.

## 2026-08-08 — "Nothing pending here, but N pending elsewhere" message: wording, placement, and `--all` argument parsing

**Decision:** When the repo-scoped query returns empty AND the unscoped (global) query is non-empty, `runReview()` prints `` No pending questions for this repo. N question(s) pending in other repos — run `grasp review --all` to see them. `` and returns before ever touching `ink` — this check only runs when `--all` wasn't already passed (an `--all` run that's genuinely empty everywhere just falls through to the existing plain "you're caught up" message, since there's no "elsewhere" left to point to). Detecting "elsewhere" costs one extra unscoped `getPendingQuestions(db)` call, made only on this already-rare empty-scoped path — not on every invocation. `--all` itself is parsed the same hand-rolled way this codebase's existing argument handling works (see the 2026-08-04 "No CLI argument-parsing framework" entry): `args.slice(1).includes("--all")` in `cli.ts`'s `review` dispatch, producing a plain `{ all: boolean }` passed into `runReview`.

**Reasoning:** The whole reason this task exists is a user being confused about what Grasp was showing them — silently rendering the existing "all caught up" message when the *scoped* view is empty but pending work genuinely exists elsewhere would recreate a milder version of the exact same transparency gap, just inverted (now hiding real pending work instead of mixing in irrelevant work). Naming the count and the exact command to see it (`grasp review --all`) rather than a vaguer "you have other pending questions somewhere" message means the user never has to guess how to actually get to that view. Placing this check before `ink` ever loads (rather than, say, having the ink app itself render an "elsewhere" banner) keeps it consistent with the existing empty-state handling, which already short-circuits before touching `ink` for the same reason — no terminal UI needs to be spun up just to print one line and exit. Reusing `args.slice(1).includes("--all")` rather than reaching for a parsing library follows the 2026-08-04 entry's own stated update path ("once real commands need flags... a proper CLI framework is likely worth revisiting") literally: this is the first real flag `grasp` has ever needed, and a single boolean doesn't yet meet the bar that entry set for pulling in a dependency — worth reconsidering again once `review` or another command needs more than one or two flags.

**Alternatives considered:** Always eagerly run both the scoped and unscoped queries on every `grasp review` invocation (not just the empty-scoped path) so the "N elsewhere" count is available unconditionally — rejected as two DB round-trips on the common (non-empty, most frequent) path for a number that's only ever displayed on the empty path; the extra query is cheap enough to defer to exactly when it's needed. Show the "N pending elsewhere" count as a permanent footer/header on every scoped `grasp review` run (even a non-empty one), not just the empty-scoped case — considered, since it's arguably useful context every time, but rejected as scope creep beyond what the dogfooding finding actually asked for and as visual noise on the common path where the user already has their own repo's questions in front of them; revisit if real usage shows the empty-only version still leaves people surprised by a stash of old questions elsewhere. A `commander`/`yargs`-style parsed `--all=true`/positional-flag mix — rejected as needless for one boolean flag, consistent with the existing no-framework precedent.

## 2026-08-12 — `grasp review` starting banner: placement and content

**Decision:** A small `StartBanner` component in `src/reviewApp.tsx`, rendered inside `App` gated on `index === 0` (alongside the existing per-question `"{index + 1} of {items.length} pending"` line, not replacing it), showing the total pending count, the number of distinct sessions/batches those questions span (only when more than one), and a restatement that Ctrl+C is always safe to quit with. It reads `items` — the same array `App` already has in scope — rather than fetching or recomputing anything; session/batch counting reuses each item's existing `sessionId`/`batchIndex` fields (`new Set(items.map(item => item.event.sessionId ?? item.batchIndex)).size`) instead of a new grouping pass.

**Reasoning:** `index === 0` is simplest correct way to render something exactly once "before the first question" in this component's existing render loop: `App` already re-renders per index via `setIndex`, so gating on `index === 0` naturally disappears the moment the user advances past the first question, with no separate "have I shown this yet" state needed. Keeping it as a small component (rather than inlining the JSX into `App`) matches this file's existing pattern of one component per distinct render concern (`DiffView`, `QuestionScreen`). Restating the Ctrl+C safety line here, in addition to the persistent per-question hint added by fix #4, means a user who quits mid-way through skimming the diff on question 1 — before ever reaching the hint row inside `QuestionScreen` — has still seen the message once, since the banner renders above `QuestionScreen` on that exact first render.

**Alternatives considered:** A one-time flag (`hasShownBanner` state, set on first render and never reset) instead of `index === 0` — considered, but rejected as unnecessary state for a condition the render loop already expresses for free; `index` never goes backward in this component, so `index === 0` is already "exactly the first item, never again," a strict subset of what a separate flag would track. Rendering the banner as a wholly separate mounted tree ahead of `App`/`QuestionScreen` (e.g. its own top-level state machine step) — rejected as more structure than a one-line summary needs, and it would have needed to duplicate the `items`/session-grouping data `App` already has rather than just reading it in place. Showing the banner as a blocking "press any key to continue" screen (matching the explain/reveal screens' pattern) — rejected as unnecessary friction for a summary line the user doesn't need to act on; unlike the explain/reveal screens (which show new content the user needs a moment to read before the input field reappears), this is peripheral context that can just sit above the first question without gating input.

## 2026-08-12 — `difficultyMode` naming and scope

**Decision:** New `GraspConfig` field named `difficultyMode: "easy" | "medium" | "hard"`, defaulting to `"medium"`, wired only into `buildJudgePrompt`'s concept-SELECTION instructions (`generation.ts`'s `difficultyModeInstruction`). `"medium"` adds no extra instruction text at all, so the shipped default prompt is byte-for-byte unchanged from before this field existed. `"easy"`/`"hard"` append one soft-preference sentence, explicitly framed as overridable when a diff only really offers one reasonable concept.

**Reasoning:** The brief and this prompt's own spec are explicit that this is a preference over which concept gets picked among multiple reasonable candidates, NOT a lever on how rigorously a chosen concept's question is written (that's FUTURE_IDEAS.md item 2, deliberately out of scope here). Naming it `difficultyMode` (rather than e.g. `conceptPreference` or `selectionBias`) matches the user-facing vocabulary the prompt spec itself uses (`grasp set mode --easy/--medium/--hard`) and reads naturally next to `gateMode`, this config's other enum-shaped field. Keeping `"medium"`'s effect at "no-op" (rather than e.g. writing an explicit "no preference" sentence) was the safest way to guarantee the "must leave the judge prompt's existing behavior completely unchanged" requirement is actually true, not just approximately true — an unconditionally-appended neutral sentence still risks nudging the model in ways the existing, already-validated prompt wasn't tested against.

**Alternatives considered:** Threading a numeric 1-3 scale instead of an enum — rejected, no use case needs finer granularity than the three CLI flags the prompt spec already names, and an enum keeps `validateConfigOverride`'s check identical in shape to `gateMode`'s. Applying the preference as a hard filter (e.g. re-prompting or rejecting a judge response that picked an "off-mode" concept) — explicitly rejected by the spec itself ("never a hard filter that could make an otherwise-good diff produce no question at all"), so implemented purely as prompt text the model can override.

## 2026-08-12 — `grasp reset config` (local): delete `.grasp.json` vs. overwrite with `{}`

**Decision:** `grasp reset config` (no `--global`) deletes `<repoRoot>/.grasp.json` if it exists, rather than overwriting it with an empty JSON object.

**Reasoning:** An empty `{}` override file left behind after a reset is indistinguishable in effect from no file at all (both fully fall back to global config via `deepMerge`), but it isn't indistinguishable in kind — it's a file a future `grasp set ...` run, a stray `ls`, or a confused user re-reading their repo would still trip over, with no information content to justify existing. `loadConfig`'s own `repoConfigPath: null` vs. a real path distinction (already used elsewhere, e.g. `debug:seed`'s printed config summary) is also more honest post-reset: "no repo override present" is literally true after a delete, and only approximately true (technically-present-but-empty) after an overwrite. Since a repo that never had `.grasp.json` is the intended end state of "reset to defaults," deleting is the more literal implementation of that promise.

**Alternatives considered:** Overwriting with `{}` — kept parity with the global case's "always end up with a valid, present file on disk" shape, but rejected: unlike the global config (which must always exist for `ensureGlobalConfigFile`'s "create with defaults on first run" contract to mean anything), a repo-level override file existing at all is optional by design, and there's no code path that depends on `.grasp.json` being present-but-empty rather than absent. Overwriting with `DEFAULT_CONFIG` in full (mirroring the global case exactly) — rejected as actively worse than either option above: it would make the repo's `.grasp.json` silently pin every field to today's defaults, permanently shadowing any FUTURE global config change (e.g. tomorrow's `DEFAULT_CONFIG.costCapUsd` update) that the user would otherwise have picked up for free — exactly the kind of silent, hard-to-notice divergence "reset to defaults" should not introduce.

## 2026-08-12 — `grasp export --anki`: no dedup by concept tag

**Decision:** `grasp export --anki` includes one row per concept-question occurrence (answered or skipped), with no deduplication by concept tag — a tag asked about more than once across different events produces more than one Anki row.

**Reasoning:** The schema's own memoization model already treats "answered once" as the completion signal for a tag (`getAllAnsweredConceptTags`) — but the export's job is to hand the user real flashcard material, not to re-derive or enforce that memoization policy a second time in a different format. Two occurrences of the same tag can carry genuinely different instance context (different diffs, different phrasing) even when the underlying concept question text is identical, and a user reviewing in Anki loses nothing by seeing a duplicate card (Anki itself handles repeated near-identical cards fine) but would lose real information if Grasp silently decided which occurrence "wins" and discarded the rest.

**Alternatives considered:** Dedup by `conceptTag`, keeping only the first (or most recent) occurrence — rejected: picking a winner requires a policy call (oldest? newest? most complete sample answer?) the export command has no principled basis to make on the user's behalf, and it would make two runs of `grasp export --anki` diverge in row count from the user's own `events` table row count in a way the "don't curate it" spirit of this whole export feature argues against.

## 2026-08-12 — CSV export: quoting, dialect, and file layout

**Decision:** Hand-rolled RFC-4180-style CSV writer (`csvField`/`toCsv` in `export.ts`) — quote a field whenever it contains a comma, double quote, or any newline, doubling embedded double quotes, `\r\n` line endings, one file per shape written to `~/.grasp/exports/<name>-<ISO-timestamp-with-colons-stripped>.csv`.

**Reasoning:** No new dependency is justified for CSV writing that's this small and well-specified (same "don't reach for a library/framework where hand-rolling is simple and testable" posture as this codebase's existing no-CLI-framework decision) — the full quoting rule is a few lines and directly testable. `\r\n` matches the CSV spec's own recommended line ending and is what several real-world importers (including Anki's) are most conservatively tested against, avoiding any ambiguity from bare `\n`. Timestamped filenames (rather than one fixed name per shape, always overwritten) mean re-running `grasp export` after answering more questions never destroys a previous export a user might still have open or have already imported into Anki — colons are stripped from the ISO timestamp because they're invalid in Windows filenames and needlessly risky elsewhere.

## 2026-08-12 — Remove `costCapUsd` and the unknown-cost-halt mechanism: keep `cost_usd`/`cost_unknown` as informational metadata

**Decision:** `costCapUsd` is removed entirely from `GraspConfig`/`DEFAULT_CONFIG`/`KNOWN_TOP_LEVEL_KEYS`/`validateConfigOverride` (`src/config.ts`), the `spentSoFar >= config.costCapUsd` check is removed from `runGeneration`'s successor (`executeGenerationAttempt`, `src/generation.ts`), and `hasUnknownCostFailure` is removed from `store.ts` along with its call site — `questionsPerSessionCap` is now the sole generation safety rail. An old config file with a leftover `costCapUsd` key doesn't just fail the generic "unknown config key" check — `validateConfigOverride` special-cases it (`REMOVED_TOP_LEVEL_KEYS`) with a message naming what changed and what to do about it ("costCapUsd was removed ... questionsPerSessionCap is now the sole generation safety rail. Delete this key from your config file."), not a bare "did you mean one of: ..." that would leave someone who never made a typo guessing why a key that used to work no longer does. `cost_usd`/`cost_unknown` stay on the `events` table and `EventRecord` — nothing gates on them anymore, but they're kept as informational/audit metadata: brief §3.5 lists spend as a field worth logging for transparency independent of any cap, `Stop`'s `systemMessage` still surfaces a running cost total for exactly that reason (`costSummaryMessage`, `src/cli.ts`), and `cost_unknown` still records a real, meaningful fact about a row (its true cost genuinely couldn't be determined) even though nothing halts generation over it anymore.

**Reasoning:** This whole removal exists because a single timeout could permanently and silently blackhole a session — `hasUnknownCostFailure` treated an unknowable-cost failure as equivalent to a real cap hit and halted every subsequent diff in that session, including the most significant one, recording it identically to (and indistinguishable from) an actual cap hit. Once the dollar cost cap is gone, the entire "is this session's spend still knowable" question is moot — there's nothing left to protect the accuracy of. Keeping `cost_usd` rather than dropping it as dead weight follows directly from the brief's own field list (§3.5: "cost (if LLM-generated) | spend transparency") — transparency about spend was never solely in service of enforcing a cap; it's a standing product principle (§3.6/§8: "trust is load-bearing... transparent about cost"), and a user on API billing still benefits from seeing what a session actually cost even with no ceiling being enforced. Dropping the columns would also mean rewriting `grasp export`'s existing `sample_concept_answer`/cost-adjacent columns and the `Stop` cost summary for no functional gain, just to save two nullable `TEXT`/`INTEGER` columns nothing else depends on. The specific removal message (rather than the plain "unknown key" error) matters because `validateConfigOverride`'s existing unknown-key rejection was designed for genuine typos ("did you mean one of: ...") — a real, no-longer-existing key deserves a different answer than a fuzzy-match suggestion list that doesn't include the key the user actually typed.

**Alternatives considered:** Drop `cost_usd`/`cost_unknown` entirely as dead weight, on the theory that a field nothing gates on is noise — rejected because it isn't actually dead: it's read by `grasp export`'s default/raw shapes, `Stop`'s cost summary message, and `getSessionCostUsd` (still used for the same summary), so removing it would be a second, unrelated breaking change bundled into this one, and would erase real spend-transparency information the brief explicitly asks for. Leave `costCapUsd` in the schema as a harmless, silently-ignored no-op (stop enforcing it but keep accepting the key) — rejected: this codebase's own standing policy (`validateConfigOverride`'s "Unknown config keys are rejected, not silently ignored" entry, 2026-08-04) is exactly the failure mode this would reintroduce, just for a formerly-real key instead of a typo — a user who still has `"costCapUsd": 0.05` in their config would reasonably but wrongly believe it's doing something. A generic deprecation-only warning (log to stderr, don't throw) instead of a hard validation error — rejected for consistency with every other invalid-value case `validateConfigOverride` already hard-rejects (wrong type, out-of-range, unknown key); a config file is either fully valid or it errors, no silently-degraded middle state.

## 2026-08-12 — Batched-at-Stop generation: resolved tracking, retry scope, and slot-mutex composition

**Decision:** `captured_diffs` gains two columns: `resolved INTEGER NOT NULL DEFAULT 0` and `significant_files_json TEXT` (the Phase 4 filter's `significantFiles` verdict for a passed capture, persisted verbatim AT CAPTURE TIME — not recomputed later, since the generated-file detector reads up to 4KB off disk and a working tree can have moved on by the time `Stop` fires). `ClaudeCodeAdapter.checkAndCapture` (`PostToolUse`) now only captures — diff, filter, `insertCapturedDiff`, advance checkpoint — and never calls generation. `runBatchGeneration` (`src/generation.ts`), called once from `Stop` in `cli.ts`'s `runInternalHook`, gathers every `captured_diffs` row for the CURRENT (`session_id`, `repo`) pair — not `session_id` alone — where `filtered = 0 AND resolved = 0`, runs at most one judge+generate attempt covering all of them (labeled "=== Change i of N ===" sections in the prompt for N>1, one combined concept+instance pair back, same response contract), and marks every covered row `resolved = 1` if the outcome's `missReason` is `null` or `"cap_reached"` (a real question, a legitimate "not worth asking", or a genuine question-cap hit — all final verdicts), leaving them `resolved = 0` for retry if `missReason` is `"error"` or `"timeout"` (a failed attempt — process failure, malformed response, contract violation, or a slot-acquire timeout). A session that never gets another `Stop` firing simply leaves its unresolved diffs unresolved forever — the minimum bar the task itself sanctioned as acceptable, not a more robust cross-hook retry. `acquireGenerationSlot`'s existing per-session mutex is unchanged in shape; both `runGeneration` (single diff, kept for the existing diff-by-diff test suite and any future direct caller) and `runBatchGeneration` funnel through one shared internal `executeGenerationAttempt`, so the slot is still acquired/released exactly once per attempt regardless of how many diffs that attempt covers — a batch of five diffs takes the same one slot-hold a single diff used to, not five.

**Reasoning:** Scoping the gather query to (`session_id`, `repo`), not `session_id` alone, follows directly from what a `Stop` firing actually has available: `runInternalHook` already resolves exactly one `repoRoot` per firing (from that firing's own `cwd`), and every other per-firing resolution — config, the hard-gate check — is already scoped to that same repo root. A session-only scope would need to answer an ill-defined question the moment a session's tool calls span more than one repo (rare, but the checkpoint/config/capture machinery already treats `(session_id, repo)` as the natural key elsewhere): which repo does a COMBINED event spanning two repos' diffs even belong to, for `grasp review`'s per-repo default scoping to make sense of later? Diffs captured under a repo a `Stop` firing's `cwd` doesn't currently resolve to simply wait for a future firing that does — the same "retried on the next opportunity, permanently-abandoned work is a documented no-op, not a loss" story the task's own multi-repo framing already anticipates. Persisting `significantFiles` at capture time (rather than re-running `evaluateCapturedDiff` against the diff at `Stop` time) matters for correctness, not just convenience: the generated-file detector does a real disk read, and re-running it minutes later against a working tree the agent kept editing could silently produce a DIFFERENT verdict than what `PostToolUse` actually saw and filtered — the judge should see exactly what was captured, not a re-derived approximation. Reusing `missReason` (rather than inventing a separate "should this batch resolve" flag) to decide resolution is deliberate: the resolved/unresolved question and the miss-reason taxonomy are actually the same question asked two ways — an `error`/`timeout` miss already means "this attempt didn't produce a trustworthy verdict," which is exactly retry-worthy, and `cap_reached`/`null` already means "this attempt DID produce a final verdict," which is exactly resolve-worthy — a second flag would just be a redundant, driftable encoding of information `missReason` already carries. Choosing Stop-only retry (not also attempting a batch opportunistically on `PreToolUse`/`PostToolUse`) is the more conservative of the two options the task explicitly named as acceptable, and it's the one that actually protects the fix this whole prompt exists to ship: generating from ANY hook type other than `Stop` reintroduces exactly the per-tool-call competition for one shared slot that caused the original timeout bug, just with a smaller blast radius — Stop-only keeps the "generate at most once per turn" invariant absolute, not "usually once per turn, occasionally more."

**Alternatives considered:** A `captured_diffs.resolved_at_event_id` (or similar) foreign key back to the covering `events` row, instead of a bare boolean — rejected as unneeded complexity: nothing in `grasp review` or `export` needs to trace a captured diff back to which specific event resolved it (the event's own `diff_files_json` already carries the union of covered files forward), so a boolean carries exactly the information anything actually reads. Recomputing `significantFiles` fresh at `Stop` time via `evaluateCapturedDiff` instead of persisting it at capture time — rejected for the staleness reason above, and also because it would mean a `Stop` firing needs the ORIGINAL diff object it never itself computed (only `PostToolUse` has that in hand naturally) reconstructed some other way, adding real complexity for a strictly worse correctness story. Scoping the gather query to `session_id` alone (a literal reading of the task's own prose) and picking one arbitrary `repo` for the combined event (e.g. the first covered diff's) — rejected because it silently mislabels a combined event's `repo` for any diff captured under a DIFFERENT repo in that batch, which would then never show up under the repo it actually belongs to in `grasp review`'s default per-repo view — worse than just deferring that diff to a later, correctly-scoped attempt. A more robust "retry on ANY hook firing for this session, not just Stop" design (PreToolUse/PostToolUse also opportunistically draining unresolved diffs) — seriously considered per the task's own "or something more robust" invitation, but rejected: it directly reintroduces the multi-firing-competes-for-one-slot shape this entire prompt sets out to remove, trading a small, documented, harmless edge case (a permanently-abandoned session's last diffs never get asked about — no different from being filtered out) for a real regression risk on the actual bug being fixed.

**Alternatives considered:** A CSV library (e.g. `csv-stringify`) — rejected per this codebase's stated dependency-minimalism preference for functionality this size. A single fixed filename per shape (overwritten each run) — rejected: it directly contradicts this prompt's own "filename should include a timestamp so repeated runs don't clobber each other" requirement, and losing a previous export silently on a second run is a worse failure mode than an `exports/` directory slowly accumulating files a user can clean up themselves.
