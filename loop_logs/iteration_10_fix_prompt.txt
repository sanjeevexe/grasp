Grasp builds, installs as a command, runs, and passes all 113 automated tests. Independent scratch-repository testing also confirmed that the main workflow is largely sound: checkpoint-based diff capture, lockfile/generated-file/custom-ignore filtering, mock-Claude question generation, cross-repository concept memory, session-wide cost and question caps, deliberate answer and skip handling, blank-answer rejection, soft and hard gates, repository overrides, and graceful model failures and timeouts.

This run still found one real filtering bug, so the verdict is FAIL.

A formatting-only rewrite was sent to Claude and turned into a paid question. The only change was wrapping a return expression over multiple lines with grouping parentheses:

```diff
-  return `Hello, ${name}`;
+  return (
+    `Hello, ${name}`
+  );
```

The behavior of the function did not change. Grasp captured this transition by itself, classified it as meaningful, invoked the mock Claude binary, stored a `both` question, and added `$0.006` to the session cost. The current filter only recognizes line wrapping when removing all whitespace makes both sides identical; grouping parentheses or other harmless tokens inserted by a formatter defeat that check. This conflicts with the stated goal of filtering formatting-only changes and with the README's claim that formatter line-wrapping is recognized.

### What is broken

The formatting-only return-expression wrap shown in the summary was not filtered. Its isolated checkpoint transition was stored as `+3/-1`, passed the filter, invoked Claude, generated a real pending event, and cost `$0.006`.

This is not merely a theoretical parser limitation: adding grouping parentheses while wrapping a long expression is a normal formatter-style rewrite. Grasp currently detects only wraps whose non-whitespace character sequence stays exactly identical. The result is avoidable questions and cost for code whose behavior did not change.

Git filenames containing tabs, newlines, or unusual surrounding whitespace remain a documented edge case because parsing is not NUL-delimited.
