# Codex independent test report

## Summary

Grasp builds and runs, and all 98 automated tests pass. Most of the product also held up in independent command-line testing: incremental diff capture, lockfile and formatting filtering, question generation through a mock Claude executable, cross-project concept memory, session-wide caps, the answer/skip interface, both gate modes, per-repository configuration, and ordinary Claude errors and timeouts all worked.

This run still found one release-blocking filtering bug and two smaller but real reliability/transparency bugs.

The main problem is generated files. Grasp recognizes a generated-file header when a file is first added, but it does not recognize that same file on later regenerations if the header itself is unchanged. In a clean reproduction, a tracked file began with `// Code generated by a tool. DO NOT EDIT.`. Changing three lines below that header passed the filter, was sent to Claude, and produced a question about `generated.ts`. Regenerating an existing generated file is the normal case, so the README's claim that these files are filtered is materially misleading.

Separately, an invalid repository config makes `grasp internal:hook` exit with code 1 before its protective error handler runs. Current Claude Code behavior allows the tool action to proceed on exit 1, but displays a hook-error notice on every firing. That is not the quiet, graceful failure promised by Grasp. Also, `grasp init` says it previews exactly what it will write, but its preview omits the arrays that actually surround each hook entry in the settings file.

I would hesitate to rely on Grasp for real work while routine generated-file updates are treated as meaningful handwritten work and sent out for paid question generation. The final verdict is FAIL.

## 1. Build, automated tests, packaging, and basic CLI — PASS

`npm install` and `npm run build` succeeded. The built CLI printed version `0.1.0`, displayed help that matches the current on-demand review architecture, and initialized all state under the disposable home.

`npm test` passed all 98 tests with no failures. These include real multi-process regressions for checkpoint claiming, SQLite writes, concurrent cap enforcement, generated-file false positives, Git stderr handling, stale hard gates, and generation-reservation ownership.

`npm pack --dry-run --json` showed the executable, runtime modules, README, license, and package metadata expected in the package. The built entry point was executable.

Running `grasp init` from a nested directory found the repository root, disclosed Claude usage and possible cost before writing, installed 45-second `PreToolUse`, `PostToolUse`, and `Stop` hooks, and was idempotent on a second run.

## 2. Diff capture and mechanical filtering — FAIL

### What worked

- Manual capture included staged, unstaged, and untracked changes together, with the correct three paths, statuses, line counts, and hunks.
- Hook capture used a pre-change checkpoint. A meaningful edit plus a lockfile produced one capture and one generation event containing only the meaningful file. Repeating `PostToolUse` without another edit created no duplicate capture, model call, or cost.
- A lockfile, a small formatting-only reindent, a one-line change, a file over the configured maximum, Grasp's own config files, and a repository-specific ignored directory were filtered.
- The same `ignored/` path in another repository without that override reached generation, proving the ignore setting is repository-specific.
- A newly added file with a generated-code header was filtered as `generated_file`.
- The previous run's false positive is fixed: an ordinary executable line containing `throw new Error("Do not edit locked state")` near the top of a file was not mistaken for a generator header.

### What is broken

Generated-file detection only checks added lines in the current diff. It does not inspect an unchanged header already present in the file.

The clean reproduction was:

1. Commit a file whose first line is `// Code generated by a tool. DO NOT EDIT.`.
2. Start a fresh Grasp checkpoint.
3. Change three non-header lines in that file, as a normal generator rerun would.
4. Fire `PostToolUse`.

Grasp recorded the capture as unfiltered and created a real question event with this summary:

```text
1 file changed (+3/-3): generated.ts
```

This is a common case, not an obscure filename edge case: generated headers normally stay unchanged while the generated body changes. It means the filter reliably catches a generated file when it first appears, but usually misses later updates to it. Users can add known paths to `ignorePatterns`, but the built-in generated-file claim does not hold.

Grasp's exact command-line flags were accepted by the installed unauthenticated Claude binary before it returned its login error.

## 4. Cost cap and question-count cap — PASS

Both caps accumulated across the whole Claude `session_id`, not per turn:

- With a $0.01 cost cap and $0.006 mock calls on three different turns, the first two calls ran and recorded $0.012 total. The third turn logged `cap_reached` without invoking Claude. This matches the documented one-call crossing behavior.
- With a one-event question cap, the first turn generated one question event and the second logged `cap_reached` without invoking Claude.
- Mock invocation counters confirmed the capped turns never called Claude.
- The automated six-process cap races passed: overlapping calls did not exceed either cap.

The exact overlap that failed the previous run is fixed. Three same-session workers, each using a 16-second mock call, finished with two successful calls and one properly logged `timeout` miss at approximately 16, 20, and 32 seconds. Every process finished below the installed 45-second outer hook limit, and no generation reservation was left stuck in the database.

## 5. `grasp review` answer, skip, and batch flow — PASS

The real Ink interface was exercised in a pseudo-terminal.

- It rendered the repository, summary, colored diff, question type, and progress count readably.
- Doing nothing for several seconds did not advance or dismiss a question.
- Blank submissions were rejected for both concept and instance answers. The event and concept tag remained unchanged in SQLite.
- Real concept and instance answers were saved, and only the completed answer marked the linked concept learned.
- Escape deliberately opened the optional skip-reason step. Submitting a blank reason stored a real skip and did not mark the concept learned.
- In a seven-question, five-session batch, questions from the same session stayed adjacent even when later questions from other sessions had earlier raw timestamps. The displayed overall and per-session counts were accurate.
- Running `grasp review` without an interactive terminal exited clearly instead of hanging.

Terminal resizing during a live question was not reliably controllable through the unattended pseudo-terminal harness, so resize behavior remains unverified.

## 6. Soft and hard gate modes — PASS

- Soft mode emitted no denial while a recent question was pending.
- A hard-mode repository override loaded correctly from a nested working directory and returned the documented `PreToolUse` denial JSON for a recent question from the same session.
- Answering that event immediately removed the denial.
- A pending question from another session did not block.
- The passing automated tests confirm a question older than 24 hours does not block a resumed session, while it remains visible to review and the `Stop` nudge.
- A `Stop` message combined the correct pending count and four-decimal cumulative cost. A timeout-only session with no pending question and no known spend stayed quiet.

## 7. Failure, timeout, and interrupted-session handling — FAIL

### What worked

- A nonzero mock executable produced an `error` miss, no pending question, and no raw child-process error in hook output.
- A mock sleeping beyond the generation limit was killed after about 20 seconds, logged a `timeout` miss, and did not create a phantom gate.
- A new Git repository with no commits seeded its checkpoint without leaking Git's expected `fatal: Needed a single revision` message. This fixes the previous report's Git stderr bug.
- The three-overlapping-call timeout case now exits gracefully and records a miss instead of being killed after capture.
- Interrupted turns do not leave the CLI waiting for a `Stop` event; the hook processes are independent and state is durable.

### What is broken

An invalid `.grasp.json` is handled correctly by ordinary foreground commands—they exit with a clear validation message—but not by the internal hook path. `main()` calls `ensureInitialized()` before dispatching to `runInternalHook()`, so the invalid config throws before the hook's catch block can keep the hook quiet and successful.

In the reproduction, a realistic typo (`"gateMod": "hard"`) caused `grasp internal:hook` to exit 1 and print the full validation error. According to the current [Claude Code hook documentation](https://code.claude.com/docs/en/hooks-guide), exit 1 is non-blocking, so the tool action proceeds, but Claude Code displays a hook-error notice. Every matching hook will keep doing this until the config is repaired. That contradicts the implementation's own promise that internal hooks never exit nonzero and the user-facing expectation that soft mode stays out of the way.

## 8. Configuration loading and per-repository overrides — PASS

- The disposable global config was created with all documented defaults.
- Repository overrides changed gate mode, cost cap, question cap, ignore behavior, and nested diff thresholds.
- Overrides resolved from a nested working directory to the Git repository root.
- An ignore rule applied only to its own repository.
- Arrays replaced rather than concatenated, while nested objects merged key by key, as documented.
- Invalid JSON, invalid values, unknown top-level keys, and unknown nested threshold keys were rejected with clear messages.
- A typo such as `gateMod` named the valid alternatives instead of silently leaving soft mode active.

The hook-specific handling of invalid config is reported separately in section 7; the loader and override behavior themselves are correct.

## 9. Fresh-eyes code and documentation review — FAIL

The source is generally readable, and the README is unusually candid about Claude usage, local storage, on-demand review, no answer grading, one-call cost-cap crossing, stale hard gates, checkpoint pruning, and the narrow hard-kill window.

Three inconsistencies remain:

1. The README says generated files are recognized by self-declaring header markers. In practice an unchanged header is invisible to the added-line-only detector, so normal later regenerations are not recognized and can be sent to Claude. This is the release-blocking issue from section 2.
2. `grasp init` says it shows exactly what it will add, but the preview prints each event as a single object. The settings file actually written correctly stores each event's hook entries inside an array. The preview and the write are therefore not the same JSON shape.
3. The source comment above `runInternalHook()` says the hook must never throw or exit nonzero, but invalid config fails earlier in `main()` and exits 1, as reproduced in section 7.

The original product success criterion requiring a person to keep Grasp enabled during real work for a full week remains unverified, as the README acknowledges.

## Additional bugs and risks found

1. Simultaneous processes racing to initialize a completely brand-new SQLite file can still hit `SQLITE_BUSY` while enabling WAL mode. A direct three-worker reproduction against a nonexistent database produced one success and two lock failures. Normal Grasp setup creates the database before installing hooks, and a separate three-hook fresh-home reproduction succeeded, so this is mainly a risk if the user deletes `~/.grasp/history.db` while installed hooks are still active. It is not the reason for the failing verdict, but initialization is not as concurrency-safe as steady-state writes.
2. The documented hard-kill window after checkpoint capture remains real. Normal errors, timeouts, and cap misses are logged, but forcibly killing a hook process after capture commits and before generation records its result can still lose that question.
3. Git diff parsing uses line-based rather than NUL-delimited output. Ordinary names, spaces, and renames worked, but filenames containing tabs, newlines, or leading/trailing whitespace remain a likely parsing edge case.
4. Live authenticated Claude behavior, real question quality, mid-question terminal resizing, and full-week human dogfooding could not be verified in this unattended environment.

FINAL_VERDICT: FAIL
