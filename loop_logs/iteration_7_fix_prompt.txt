# Codex independent test report

## Summary

Grasp builds and its normal, sequential workflow mostly works. It captures incremental edits, invokes the expected headless Claude command, records questions and costs, enforces both limits across sequential turns in one session, presents a readable review screen, rejects blank answers, saves answers and deliberate skips, and applies the basic soft and hard gate decisions.

This run still found release-blocking defects. Most seriously, overlapping `PostToolUse` hooks can all claim the same change and all make a paid Claude call. Twelve simultaneous hooks created twelve copies of one question, exceeded the eight-event question limit, and spent $0.12 despite a $0.05 cost limit. The two advertised safety limits are therefore not reliable during process overlap.

Other material failures remain: edited nested-path renames can be counted as zero lines and discarded; common formatter wrapping and an explicitly marked generated file reach paid generation; repository settings disappear when Claude runs from a subdirectory; invalid settings can terminate the hook; a new concept can be presented without the required concept-first question; hard mode can block on an old question from a resumed session despite the documentation; and Git cleanup can remove Grasp's checkpoint object and leave capture stuck.

I would not rely on this build for real work yet.

### Test environment and isolation

- Tested commit `7d09210` with Node `v26.5.1` and npm `11.17.0`.
- The completed functional tests used scratch homes under `/private/tmp/grasp-codex-test.b5AmPh`, disposable repositories under `.codex-test-harness/`, and controlled mock Claude binaries. Those scratch items were removed after testing.
- The real `claude` executable reported `loggedIn: false` under a scratch home, so live question quality and authenticated Claude Code hook compatibility could not be verified.
- Isolation was not perfect: one accidental `grasp --version` smoke invocation ran without the scratch `HOME`. Because Grasp initializes storage even for `--version`, that invocation opened the developer's real `~/.grasp/history.db` and ran its normal schema/pragma setup. It did not insert an event or query stored history, but it may have changed database metadata. I did not inspect or touch that database again.

## 1. Build, automated tests, and basic CLI — PASS

`npm install` and `npm run build` succeeded. All 51 automated tests passed with an explicit scratch home. The built CLI printed version `0.1.0`, displayed help, created the documented scratch config/database, rejected non-interactive review with a clear message, and produced the expected package contents in `npm pack --dry-run`.

`grasp init` showed the cost and privacy disclosure before writing, installed one 45-second hook for each required event, did not duplicate hooks on a second run, and detected and updated a deliberately stale 15-second hook.

One packaging defect is listed under additional risks: the checked-in lockfile is stale, so the documented `npm install` changes a tracked field.

## 2. Diff capture and mechanical filtering — FAIL

### What worked

- A normal validation change was captured as `app.ts +5/-1`, passed the filter, and reached generation.
- A second sequential hook with no new work produced no duplicate capture or Claude call.
- A later turn in the same session captured only the new edit, and Grasp's own `.grasp.json` was excluded from the generated-question summary.
- A one-line change was rejected as below the minimum, a simple indentation/trailing-space change was rejected as formatting-only, and a lockfile update was baseline-ignored.
- A repository-specific `scripts/` rule prevented capture from reaching Claude in one repository, while the same path generated normally in another.
- The automated maximum-size, Git-ignore, baseline-ignore, and ordinary formatting tests all passed.

### What is broken

**Overlapping hooks duplicate one change.** Twelve simultaneous hooks produced twelve captures with the same checkpoint range and twelve paid question events. Reading and advancing the checkpoint are separate operations, so every process can read the same old checkpoint before another process claims it.

**Nested-path edited renames lose their line counts.** Git reported `6/0 src/{rename-source-long.ts => rename-target-long.ts}`. Grasp kept the old and new names but stored `+0/-0`, then discarded the change as below the minimum. Its statistics parser does not correctly expand Git's compact brace form for rename paths.

**Common formatter wrapping passes as meaningful work.** Reformatting one function call from one line to several lines, without changing behavior, was recorded as `+8/-1` and passed. The detector only recognizes formatting where removed and added lines match one-for-one after whitespace normalization.

**Obvious generated code passes.** A new `src/api.generated.ts` beginning `AUTO-GENERATED FILE. DO NOT EDIT.` was recorded as `+8/-0` and passed. Grasp has a fixed path list, not general generated-file detection, despite the broader documentation claim.

## 3. Question generation and concept memoization — FAIL

### What worked

- Grasp invoked exactly `claude -p <prompt> --output-format json --allowedTools "" --max-turns 1`.
- The prompt contained only the significant application diff plus answered concept tags. The mock returned a related concept question followed by an instance question, and both were stored in the intended order.
- After `validation-before-mutation` was answered in repository A, a later response using that tag in repository B was forced to instance-only. Cross-repository memoization works.
- Automated tests confirmed conservative handling of error envelopes, malformed result text, and missing cost values.

### What is broken or unverified

For a never-before-answered `brand-new-concept`, the mock returned no concept question and one instance question. Grasp accepted it as a successful instance-only event. That violates the core teaching rule: instance-only is valid only after the concept has already been answered.

Grasp also accepted `Not Kebab Case!` as a concept tag even though its response contract requires short kebab-case tags. Inconsistent tags can defeat memoization, and arbitrary tag text is copied into later prompts.

Because no authenticated Claude CLI was available, this run verified the command, prompt, parsing, storage, and memoization logic with controlled responses but could not judge real generated-question quality or current live-Claude compatibility.

## 4. Cost cap and question-count cap — FAIL

### Sequential behavior passed

- With a one-event question limit, the first turn generated one event and a later turn under the same `session_id` logged `cap_reached` without calling Claude.
- With a $0.01 cost limit, the first turn recorded $0.01 and a later turn under the same `session_id` logged `cap_reached` without calling Claude.
- Changing `prompt_id` did not reset either total. Both limits accumulate across the whole session during sequential use.

### Parallel behavior is broken

- With an eight-event question limit, twelve simultaneous hooks produced twelve real question events and no cap misses.
- With `costCapUsd: 0.05` and a mock cost of $0.01 per call, the same twelve hooks recorded $0.12 and no cap misses.

SQLite's lock waiting prevents ordinary database-write failures, but it does not make checkpoint claiming, cap checks, Claude invocation, and event insertion one protected operation.

## 6. Soft and hard gate modes — FAIL

The core decisions worked in simulated hook calls:

- Soft mode allowed a tool call while that session had a pending question.
- Hard mode emitted the expected Claude Code denial for the session with pending work.
- A different session was not blocked.
- Answering or explicitly skipping the pending question immediately removed the denial.
- A `Stop` hook combined the correct pending count with the correct `$0.0100` session-spend message.

However, the documented age boundary is not implemented. After changing a pending event's timestamp to the year 2000 and simulating the same Claude session being resumed, hard mode still denied the tool call. The testing guide says hard mode only blocks on today's questions, and the README says it will not block over something left from another day. The query checks only `session_id`, not age.

These were simulated hook payloads because an authenticated live Claude Code session was unavailable.

## 7. Failure, timeout, and interrupted-session handling — FAIL

### What worked

- A mock Claude process exiting with status 7 logged `error`, created no pending question, and left the Grasp hook exit status at zero.
- A hanging process was killed after 20 seconds, logged `timeout`, created no pending question, and left the hook exit status at zero.
- A session that never received `Stop` left no waiting process and did not prevent a later session from working.

### What is broken

The raw child-process message `controlled claude failure` appeared directly on hook stderr rather than being replaced by a short Grasp notice.

A malformed repository config made a realistically launched `grasp internal:hook` exit 1 before the hook's protective handler began. A syntactically valid config with `"ignorePatterns": "scripts/"` caused an uncaught `TypeError` and also exited 1. The latter escapes because the asynchronous change handler is started without being awaited. In hard mode, configuration failure also prevents a reliable gate decision.

## 8. Configuration loading and per-repository overrides — FAIL

### What worked

- The global file was created with the documented defaults.
- Repository-root settings changed actual cost-cap, question-cap, gate, and filtering behavior when the hook's working directory was exactly the repository root.
- Nested settings merge by key and arrays replace the global array, matching the documented behavior and automated tests.
- Invalid JSON produced a clear path-specific message and was not overwritten.
- An ignore rule in repository A did not leak into repository B.

### What is broken

**Root settings vanish in subdirectories.** A root `.grasp.json` set hard mode, both limits to zero, and ignored `sub/`. With the hook running from `repo/sub`, Grasp still generated and charged for a question about `sub/app.ts`, and stored the repository as the subdirectory.

**`grasp init` targets the wrong directory from a subdirectory.** Running it from `repo/sub` proposed `repo/sub/.claude/settings.local.json` instead of discovering the Git root.

**Types, values, and ranges are not validated.** Grasp accepts misspelled gate modes, negative limits, and wrong field types. A wrong `ignorePatterns` type later crashes capture. Invalid settings should be rejected once, with the file path and bad field named, before any hook runs.

## Additional bugs and risks found

1. **Checkpoint objects can be removed by Git cleanup.** Grasp stores non-committed working-tree checkpoints as unreferenced Git tree objects. After `git prune --expire now` removed one, the next hook failed with `fatal: bad object`, recorded no capture or event, and left the session pointing at the missing object. Normal Git cleanup usually has a grace period, but Grasp relies on objects Git is allowed to delete.
2. **The concurrency race covers the entire paid pipeline.** Fixing only SQLite lock waits will not prevent duplicate capture or overspend. Grasp needs a serialized claim before the model call, plus recovery if the claiming process dies.
3. **The checked-in `package-lock.json` is out of sync with `package.json`.** Running the documented `npm install` changes the root package's Node engine metadata from `>=18` to `>=22`. That test-created change was restored after the build.
4. **Automated coverage misses the release-blocking cases.** All 51 tests pass, but there are no regression tests for concurrent checkpoint/cap claiming, compact rename statistics, formatter wrapping, repository-root discovery, config schema validation, concept-first enforcement, concept-tag validation, old-question gate age, or checkpoint survival/recovery.
5. **Live integration and week-long use remain unverified.** No authenticated Claude Code CLI was available, and an unattended test cannot satisfy the brief's requirement that a real person keep Grasp enabled during normal work for a week.
