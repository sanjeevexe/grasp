# Codex independent test report

## Summary

Grasp builds and its normal, sequential path is substantially functional. It captures incremental changes, calls the expected headless Claude command, stores questions and costs, presents a usable review screen, rejects blank answers, saves deliberate answers/skips, and applies soft and hard gates as designed.

This run still found release-blocking defects. Most seriously, simultaneous `PostToolUse` hooks can all claim the same change and all make a paid Claude call. In a fresh reproduction, twelve hooks created twelve copies of one question. That exceeded the default eight-question limit; in a separate test with a $0.05 cost limit, Grasp spent $0.12. The safety limits therefore are not reliable under realistic process overlap.

Other material failures remain: edited renames can be counted as zero lines and discarded; common formatter wrapping and an explicitly marked generated file reach paid generation; root repository settings disappear when Claude is launched from a subdirectory; a new concept can be presented without the required concept-first question; invalid configuration can crash the hook; and concept tags are not validated. A scratch-only Git cleanup test also deleted Grasp's checkpoint objects and left that session unable to capture later changes.

I would not rely on this build for real work yet.

### Test environment and isolation

- Tested commit `7d09210` with Node `v26.5.1` and npm `11.17.0`.
- Every Grasp command used an explicit scratch `HOME`; the developer's real `~/.grasp/history.db` was neither opened nor modified.
- Scratch state lived under `/private/tmp/grasp-codex-fresh.0oh6WR` and disposable repositories under `.codex-test-harness/`. Both were removed after testing.
- The installed real `claude` executable reported `loggedIn: false` under the scratch home. Generation tests therefore used a controlled mock `claude` binary following the repository's established test pattern.

## 1. Build, automated tests, and basic CLI — PASS

`npm install`, `npm run build`, and all 51 automated tests succeeded. The built CLI printed version `0.1.0`, displayed help, created the documented scratch config/database, and produced a package containing the CLI, README, and MIT license.

`grasp init` showed the cost/privacy disclosure before writing, installed one 45-second hook for each required event, and did not duplicate them on a second run.

One packaging problem is listed under additional risks: the checked-in lockfile is stale, so the documented `npm install` changes a tracked field.

## 2. Diff capture and mechanical filtering — FAIL

### What worked

- A normal edit was captured as `src/app.ts +7/-2`, with its real hunk and a reproducible checkpoint range.
- A second sequential hook with no new work produced no capture and no model call.
- A later edit was captured incrementally instead of being mixed with earlier work.
- A lockfile-only change was recorded as filtered with reason `baseline_ignore` and never reached Claude.
- The automated tests passed for ordinary whitespace-only changes, minimum/maximum sizes, Git-ignored files, user ignore rules, and Grasp's own config/hook files.

### What is broken

**Overlapping hooks duplicate one change.** Twelve simultaneous hooks produced twelve captures with the same checkpoint range and twelve paid question events. The checkpoint is read and updated in separate operations, so all processes can read the same old value before any one advances it.

**Edited renames lose their line counts.** Git reported an 82%-similar rename with `+2/-1`. Grasp stored the correct old/new paths but recorded `+0/-0`, then discarded it as below the minimum. Its parser does not expand Git's compact `src/{old => new}` statistics path.

**Common formatter wrapping passes as meaningful work.** Reformatting one function call from one line to several lines, without changing its tokens, was recorded as `+6/-1` and triggered generation. The formatter detector only recognizes cases where removed and added lines match one-for-one after whitespace normalization.

**Obvious generated code passes.** A file named `src/api.generated.ts` beginning `AUTO-GENERATED FILE. DO NOT EDIT.` triggered a paid question. The implementation ignores a fixed path list, not generated files generally, despite the broader project and README claim.

## 3. Question generation and concept memoization — FAIL

### What worked

- Grasp invoked exactly `claude -p <prompt> --output-format json --allowedTools "" --max-turns 1`.
- The prompt contained the filtered application diff and answered concept tags, but not Grasp's settings file. Tool access was disabled.
- A controlled concept question followed by a related instance question was stored in the intended order.
- After `validation-before-mutation` was answered in one repository, a later event using that tag in another repository was forced to instance-only. Global memoization works.
- A model decline created no pending question while still recording its reported $0.007 cost.
- Malformed output, error envelopes, and missing cost are covered by passing automated tests and do not become questions.

### What is broken

For a never-before-answered `brand-new-concept`, the mock returned no concept question and one instance question. Grasp accepted it as a successful instance-only event. This violates the core teaching rule: instance-only is valid only after that concept has already been answered.

Grasp also accepted `Not Kebab Case!` as a concept tag even though its own model contract requires a short kebab-case tag. Inconsistent spelling and punctuation can defeat memoization, and arbitrary tag text is inserted into future prompts.

Because no authenticated Claude CLI was available, this run verified the command, prompt, parsing, storage, and memoization logic but could not judge the quality or compatibility of current live-Claude questions.

## 4. Cost cap and question-count cap — FAIL

### Sequential behavior passed

- With a one-question limit, turn 1 generated one event and turn 2 under the same `session_id` logged `cap_reached` without calling Claude.
- With a $0.01 limit, turn 1 recorded $0.01 and turn 2 under the same `session_id` logged `cap_reached` without calling Claude.
- Changing `prompt_id` did not reset either total. Both limits correctly accumulated across the whole session in sequential use.

### Parallel behavior is broken

- With the default eight-question limit, twelve simultaneous hooks produced twelve real questions and no cap misses.
- With `costCapUsd: 0.05`, `questionsPerSessionCap: 100`, and a mock cost of $0.01 per call, twelve simultaneous hooks recorded $0.12 and no cap misses.

Each process checks old totals before its peers record their calls. SQLite's wait-on-lock behavior prevents database-write errors, but it does not make checkpoint claiming, limit checks, model invocation, and event insertion one atomic operation.

- Hard mode returned the expected Claude Code deny object for the session with pending work.

## 7. Failure, timeout, and interrupted-session handling — FAIL

### Generation failures worked

- A mock process exiting with status 7 logged `error`, created no pending question, and did not make the hook exit nonzero.
- A hung process was killed after 20 seconds, logged `timeout`, created no pending question, and left the hook exit status at zero.
- Sessions that never received `Stop` did not leave a waiting process or prevent unrelated later sessions from working.

### Configuration failures are not graceful

A malformed repository config made `grasp internal:hook` exit 1 before the hook's protective error handler started. A syntactically valid config with `"ignorePatterns": "scripts/"` caused an uncaught `TypeError` and also exited 1.

The second crash exposes a broader problem: `checkAndCapture()` starts its asynchronous change handler without awaiting it. A rejected promise escapes the surrounding `try/catch`, despite the code's promise that internal hooks never exit nonzero. In hard mode this also fails open because no deny decision is emitted.

The raw child-process error text (`controlled claude failure`) also appeared on hook stderr instead of being replaced by a short Grasp message. The database behavior is graceful, but the visible failure is less quiet than the docs imply.

## 8. Configuration loading and per-repository overrides — FAIL

### What worked

- The global file was created with the documented defaults.
- Repository-root settings changed actual cap, gate, and filtering behavior when the hook's `cwd` was exactly the repository root.
- Nested config objects merge by key, while arrays replace the global array, as documented and covered by tests.
- Invalid JSON produced a clear path-specific message and was not overwritten.

### What is broken

**Root settings vanish in subdirectories.** A root `.grasp.json` set hard mode, both limits to zero, and ignored `sub/`. With the hook's `cwd` set to `repo/sub`, Grasp still generated and charged for a question about `sub/nested.ts`, and stored the repository as the subdirectory. Normal work launched below the root can therefore bypass gate, cost, question, and ignore preferences.

**`grasp init` installs in the wrong directory from a subdirectory.** Running it from `repo/sub` created `repo/sub/.claude/settings.local.json` even though the real repository already had a root hook file. The command called the subdirectory “this repo,” contrary to the README's repository-root wording.

**Types, values, and ranges are not validated.** Grasp accepted `gateMode: "hrad"`, negative cost/question limits, and a string in place of `ignorePatterns`. The string later crashed capture. Invalid settings should be rejected once, with the file path and bad field named, before any hook runs.

## 9. Fresh-eyes code and documentation review — FAIL

The code is generally readable and the README is unusually direct about Claude usage, local storage, manual review, no grading, and plain non-glob ignore matching. Several material claims remain false or incomplete:

- “Captures just what's new” and “won't re-ask about the same diff twice” are false when hooks overlap.
- The documented cost and question limits are not enforced when hooks overlap.
- “Formatting-only changes” and “generated files” are described as excluded without explaining the narrow implementations that allow common examples through.
- Per-repository setup and overrides are described as repository-root features, but the code uses the exact current directory.
- The concept-first teaching contract and kebab-case concept tags are requested from the model but not enforced by Grasp.
- Failure handling is described as quietly logging a miss, but configuration errors can crash the hook and raw child stderr can leak through.
- Config is described as strict JSON, but only JSON syntax is checked; allowed values, field types, and numeric ranges are not.

## Additional bugs and risks found

1. **Checkpoint objects can be removed by Git cleanup.** Grasp stores checkpoints as unreferenced Git tree objects. In a disposable repository, `git prune --expire now` deleted a checkpoint still referenced by Grasp's database; the next hook failed with `fatal: bad object`, recorded no new capture, and left that session stuck on the missing checkpoint. Normal Git cleanup usually has a grace period, so this is not an every-session failure, but Grasp relies on objects Git is allowed to delete.
2. **The concurrency race spans the entire paid pipeline.** Fixing only SQLite lock waits will not prevent duplicate capture or overspend. The operation needs a serialized claim before the model call, with safe recovery if the claiming process dies.
3. **The checked-in `package-lock.json` is out of sync with `package.json`.** Running the documented `npm install` changed the root package's Node engine metadata from `>=18` to `>=22`, dirtying the tracked lockfile. The test restored that unrelated change afterward.
4. **Automated coverage misses the release-blocking cases.** All 51 tests pass, but there are no regression tests for concurrent checkpoint/cap claiming, edited rename statistics, formatter wrapping, repository-root discovery, config schema validation, or concept-first enforcement.
